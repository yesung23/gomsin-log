## 0. 이 문서의 목적

이 문서는 플랜 버전 2의 기술적인 내용을 실제로 진행할 수 있는 순서로 바꾼 실행 안내서다.

곰신로그는 현재 화면과 주요 기능의 뼈대는 갖춰져 있지만, 바로 일반 사용자에게 공개할 수 있는 완성 상태는 아니다. 먼저 코드가 정상적으로 빌드되게 만들고, 개인정보가 다른 사람에게 노출되지 않는지 검증한 뒤, 소수의 테스트 사용자에게 공개하는 순서로 진행해야 한다.

가장 중요한 원칙은 다음 네 가지다.

1. 기능을 더 추가하기 전에 현재 빌드 오류부터 해결한다.
2. 비공개 기록 보호는 화면이 아니라 Supabase 권한 정책에서 강제한다.
3. 실제 서비스 공개 전에 테스트용 환경에서 먼저 검증한다.
4. 한 번에 모두 개발하지 않고, 단계마다 통과 조건을 확인한 뒤 다음 단계로 넘어간다.

## 1. 먼저 알아둘 아주 간단한 용어

| 용어 | 쉬운 의미 | 곰신로그에서의 역할 |
|---|---|---|
| 프론트엔드 | 사용자가 보는 앱 화면 | React로 만든 홈, 기록, 우리, 마이 화면 |
| 백엔드 | 로그인과 데이터를 처리하는 뒤쪽 시스템 | Supabase 인증, 데이터베이스, 파일 저장소 |
| 데이터베이스(DB) | 사용자 기록을 보관하는 표들의 모음 | 프로필, 커플, 기록, 일정, 여행 등 |
| RLS | 로그인한 사람이 어떤 데이터까지 볼 수 있는지 정하는 DB 문지기 | 상대의 비공개 기록과 타 커플 데이터 차단 |
| Storage | 사진과 음성 파일을 보관하는 공간 | `couple-media` 비공개 버킷 |
| 마이그레이션 | DB 구조와 보안 규칙을 순서대로 변경하는 파일 | `supabase/migrations/` 아래 SQL 파일 |
| 환경변수 | 코드에 직접 적지 않는 서비스 연결 정보 | Supabase URL과 publishable key |
| 빌드 | 작성한 코드를 실제 배포 가능한 파일로 변환하는 과정 | `npm run build` |
| 배포 | 사용자가 앱을 설치하고 이용할 수 있게 공개하는 작업 | HTTPS 호스팅 후 Google Play 앱으로 제공 |
| 스테이징 | 실제 사용자 공개 전 테스트하는 별도 서비스 | 테스트용 Supabase와 테스트용 배포 주소 |
| 프로덕션 | 실제 사용자가 이용하는 운영 서비스 | 최종 공개된 곰신로그 |
| PWA | 웹사이트를 휴대폰 홈 화면에 앱처럼 설치하는 방식 | 곰신로그의 현재 앱 제공 방식 |

## 3. 1단계 — 현재 상태를 안전하게 보존하기

### 목표

현재 수정 중인 코드와 Supabase 상태를 잃지 않도록 기준점을 만든다.

### 해야 할 일

- 현재 Git 변경 파일을 검토한다.
- 진행 중인 변경을 의미 있는 단위로 정리한다.
- 안전한 작업 브랜치를 만든다.
- 중요한 변경을 커밋한다.
- Supabase에 실제 적용된 마이그레이션과 RLS 정책 목록을 확인한다.
- `.env`가 Git에 포함되지 않는지 확인한다.
- 가능하면 Supabase 프로젝트의 백업 또는 스키마 덤프를 준비한다.

### 현재 특별히 주의할 점

현재 저장소에는 이미 수정된 파일과 새 문서·마이그레이션이 존재한다. 이 변경은 기존 작업이므로 임의로 삭제하거나 초기화하면 안 된다.

또한 `002`로 시작하는 마이그레이션 파일이 두 개 존재한다. 파일명만 보고 어느 것이 운영 DB에 적용됐는지 추측하지 말고 Supabase의 실제 상태와 대조해야 한다.

### 완료 기준

- 현재 변경사항이 Git에 안전하게 보존되어 있다.
- Supabase에서 현재 사용 중인 테이블, 함수, RLS, Storage 정책 목록을 확인했다.
- 문제가 생기면 이전 상태로 돌아가는 방법이 문서화되어 있다.

### 비전공자인 담당자가 확인할 것

- “현재 코드가 백업되었나요?”
- “DB에 적용된 보안 규칙을 파일이 아니라 실제 Supabase 화면에서 확인했나요?”
- “문제가 생기면 어디까지 되돌릴 수 있나요?”

## 4. 2단계 — 코드가 정상적으로 검사·빌드되게 만들기

### 목표

새 기능 개발 전에 현재 프로젝트가 기본적인 기술 검사를 통과하도록 만든다.

### 현재 확인된 문제

2026-07-30 기준:

- 프로덕션 빌드가 TypeScript 오류 4개로 실패한다.
- 린트에 오류 2개와 경고 13개가 있다.
- 테스트 파일은 있지만 `vitest`와 `jsdom` 개발 의존성이 없어 테스트가 실행되지 않는다.

주요 원인은 다음과 같다.

- 미디어 업로드 함수와 화면 호출부의 인자 수 불일치
- boolean 값인 `isSupabaseConfigured`를 함수처럼 호출
- 일정의 선택적 종료일 처리 누락
- 여행 상세 화면에서 React Hook을 조건부 호출

### 해야 할 일

1. 현재 TypeScript 오류를 모두 수정한다.
2. React Hook 관련 린트 오류를 수정한다.
3. `vitest`와 `jsdom`을 개발 의존성으로 추가한다.
4. 테스트 설정이 실제로 작동하는지 확인한다.
5. 다음 명령을 모두 통과시킨다.

```bash
npm run lint
npm test
npm run build
```

Windows PowerShell에서 `npm` 실행 정책 오류가 나면 다음과 같이 실행할 수 있다.

```powershell
npm.cmd run lint
npm.cmd test
npm.cmd run build
```

### 완료 기준

- 빌드 오류 0개
- 린트 오류 0개
- 모든 자동 테스트 통과
- 개발 서버에서 주요 페이지가 빈 화면 없이 열린다.

### 이 단계에서 하지 않을 일

- UI 전면 재디자인
- 알림, 채팅, 결제 같은 신규 대형 기능 추가
- 운영 DB에 검증되지 않은 마이그레이션 적용

## 5. 3단계 — 핵심 기록 흐름을 먼저 완성하기

### 목표

곰신로그의 가장 중요한 한 가지 흐름을 완성한다.

> 로그인 → 커플 연결 → 기록 작성 → 상대가 확인 → 원문 이동

### 세부 작업

#### 3-1. 로그인과 온보딩

- Google 로그인
- 이메일 매직링크
- Apple 로그인은 실제 설정이 준비된 경우에만 제공
- 역할과 닉네임 저장
- 초대 코드 생성과 참여
- 커플당 활성 구성원 최대 2명 확인
- 초대 코드를 만든 본인이 자기 코드를 다시 사용하는 행위 차단
- 초대 코드 24시간 만료 확인

#### 3-2. 텍스트 기록

- 공유 기록 작성
- 나에게만 남기는 비공개 기록 작성
- 수정과 삭제
- 저장 실패 시 성공 메시지를 띄우지 않도록 처리
- 실패한 낙관적 업데이트는 되돌리거나 재시도 안내

#### 3-3. 상대 기록 확인

- 상대에게는 공유 기록만 표시
- 비공개 기록은 내용뿐 아니라 날짜의 점, 개수, 요약에서도 존재가 드러나지 않아야 함
- 군화 홈의 요약은 실제 공유 기록만 사용
- 요약을 누르면 근거 원문으로 이동하고 강조

#### 3-4. 감정 흐름

- 외부 AI API를 추가하지 않음
- 규칙 엔진은 최대 3개 후보만 제안
- 사용자가 직접 확정한 감정만 저장
- 비공개 기록의 감정은 상대 요약에서 제외

### 완료 기준

두 개의 테스트 계정으로 다음 흐름이 모두 성공한다.

1. A가 커플 공간 생성
2. B가 초대 코드로 참여
3. A가 공유 텍스트 작성
4. B가 기록과 요약 확인
5. B가 요약을 눌러 원문으로 이동
6. A가 비공개 텍스트 작성
7. B 화면 어디에도 비공개 기록의 존재가 나타나지 않음

## 6. 4단계 — Supabase 보안과 프라이버시 확정하기

### 목표

프론트 화면을 조작하거나 직접 API를 호출하더라도 권한 없는 데이터는 DB가 반환하지 않게 한다.

### 테스트 계정

- A: 기록 작성자
- B: A와 연결된 상대
- C: 전혀 다른 제3자

### 반드시 보장할 권한

| 데이터 | A | B | C |
|---|---|---|---|
| A의 공유 기록 | 읽기·수정·삭제 | 읽기 | 접근 불가 |
| A의 비공개 기록 | 읽기·수정·삭제 | 존재 여부도 접근 불가 | 접근 불가 |
| 같은 커플의 공유 일정 | 정책에 따라 편집 또는 읽기 | 정책에 따라 편집 또는 읽기 | 접근 불가 |
| 개인 일정 | 본인만 접근 | 접근 불가 | 접근 불가 |
| 생리주기 | 본인만 접근 | 접근 불가 | 접근 불가 |
| 다른 커플의 멤버 정보 | 접근 불가 | 접근 불가 | 접근 불가 |

### 적용 전 결정할 사항

플랜 v2에 있는 선택지 중 다음은 먼저 확정해야 한다.

1. 공유 일정은 상대도 수정·삭제할 수 있게 할지
2. 연결 해제 후 각자의 과거 기록은 보존할지
3. 운영 서비스에서도 데모 둘러보기를 제공할지
4. 오늘의 식단 위젯을 제거할지

권장 기본값:

- 공유 일정은 둘 다 편집 가능하되 삭제 확인창 제공
- 연결 해제 후 데이터는 삭제하지 않고 상대 접근만 즉시 차단
- 운영에서는 데모를 별도 플래그로만 노출
- 오늘의 식단 위젯은 제거

### 현재 코드와 DB 사이의 중요한 불일치

`005_secure_rls_policies.sql`은 `events.visibility` 컬럼을 삭제하지만 현재 프론트엔드 코드는 해당 컬럼을 계속 읽고 저장한다. 이 상태로 마이그레이션만 먼저 적용하면 일정 저장이 실패할 수 있다.

따라서 다음 중 하나로 코드와 DB의 기준을 통일해야 한다.

- 권장: `is_private`를 유일한 기준으로 사용하고 프론트 코드에서 `visibility` 제거
- 또는 새 마이그레이션에서 `visibility`를 유지하도록 정책 재설계

### 완료 기준

- A/B/C 권한 테스트 표의 모든 항목 통과
- C가 다른 커플의 기록·일정·멤버 정보를 조회하면 항상 0행 또는 권한 오류
- 커플 연결 해제 직후 상대 기록 접근 차단
- RLS 테스트 결과를 문서로 보관

## 7. 5단계 — 사진·음성 파일 업로드 완성하기

### 목표

텍스트 기록이 안정된 뒤 사진과 음성 첨부를 안전하게 연결한다.

### 현재 해결해야 할 구조 문제

새 Storage 정책은 파일 경로를 다음처럼 요구한다.

```text
{coupleId}/{recordId}/{attachmentId}.{확장자}
```

또한 업로드할 때 해당 `recordId`의 DB 기록이 이미 존재하는지 검사한다. 하지만 현재 화면은 파일을 먼저 업로드한 뒤 기록을 만드는 흐름이다.

### 권장 업로드 순서

1. 사용자가 기록 작성 버튼을 누름
2. DB에 첨부 없는 기록을 먼저 생성
3. 생성된 `recordId`를 사용하여 파일 업로드
4. 업로드 성공 후 기록의 첨부 목록 업데이트
5. 실패하면 기록을 유지하고 재시도하거나, 사용자의 확인 후 빈 기록 삭제

### 추가 작업

- 지원 MIME 타입과 최대 파일 크기 결정
- 사진 압축 여부 결정
- 영상 기능은 용량과 비용을 고려해 베타 이후로 미루는 것을 권장
- Signed URL 만료 시간을 짧게 유지
- `create-media-signed-url` Edge Function 구현 및 배포
- 파일 삭제 시 Storage 객체도 함께 삭제
- 연결 해제된 사용자의 새 Signed URL 발급 차단

### 완료 기준

- 공유 사진은 A와 B만 열람
- 비공개 사진은 A만 열람
- C는 Signed URL 발급 불가
- 삭제된 기록의 파일이 Storage에 불필요하게 남지 않음
- 업로드 실패 시 사용자 기록이 조용히 사라지지 않음

## 8. 6단계 — 화면과 부가기능 정리하기

### 목표

사용자가 누를 수 있는 기능은 실제로 동작하고, 아직 구현되지 않은 기능은 명확히 “준비 중”으로 표시한다.

### 홈

- 곰신 홈 위젯 중 실제 데이터에 연결된 항목만 기본 노출
- 복무 진행률, 연락 가능 시간, 기념일은 실제 프로필·일정 데이터 사용
- 고정 45%, D-12 같은 목업 제거
- 알림 버튼은 기능 구현 전 숨기거나 준비 중으로 표시
- 군화 홈 에너지 백분율은 근거가 약하므로 정성 표현으로 시작하는 것을 권장

### 기록

- 달력 점, 개수, 미디어 수에 비공개 상대 기록이 포함되지 않는지 재검증
- 수정·삭제 실패 처리
- 긴 기록과 여러 첨부의 표시 확인

### 우리

- 기념일, 면회, 휴가, 여행을 구분
- 선택한 날짜의 상세 일정 표시
- 개인 일정은 상대에게 달력 점도 노출하지 않음
- 여행 플래너와 체크리스트 연결

### 마이

- 곰신의 생리주기는 마이 화면에서만 사용
- 군화는 복무 정보 표시
- 설정 기능은 `/settings`로 통합

### 설정

- 프로필 수정
- 로그아웃
- 커플 연결 해제
- 내 기록 삭제
- 개인정보 안내
- 아직 없는 생체인증, 백업, 푸시 알림은 준비 중 표시

### 레거시 정리

현재 사용되지 않거나 중복된 다음 파일은 참조가 완전히 사라진 것을 확인한 뒤 삭제한다.

- `src/features/home/GomshinHome.tsx`
- `src/features/home/SoldierHome.tsx`
- `src/pages/SchedulePage.tsx`
- `src/pages/ServicePage.tsx`

### 완료 기준

- 동작하지 않으면서 동작하는 것처럼 보이는 버튼이 없음
- 실제 데이터 대신 고정 예시값을 보여주는 핵심 위젯이 없음
- 4탭과 설정·여행 경로가 일관됨

## 9. 7단계 — 오류·오프라인·복구 처리하기

### 목표

인터넷이 끊기거나 Supabase 요청이 실패해도 데이터 손실이나 잘못된 성공 안내가 발생하지 않게 한다.

### 해야 할 일

- 저장 중 로딩 상태 표시
- 요청 실패 시 명확한 오류 메시지
- 자동 재시도 또는 사용자가 누르는 재시도 버튼
- 서버 저장 성공 전 “전해졌어요” 메시지 표시 금지
- Realtime 연결이 끊겼을 때 새로고침 또는 다시 동기화
- 오프라인에서는 마지막으로 안전하게 캐시된 데이터만 표시
- 비공개 기록 본문은 LocalStorage에 평문 저장하지 않음
- 로그아웃과 연결 해제 시 캐시 삭제
- Service Worker 캐시 버전 관리

### 완료 기준

비행기 모드, 느린 네트워크, Supabase 일시 장애 상황에서 다음이 보장된다.

- 사용자가 저장 성공 여부를 알 수 있음
- 실패한 기록이 성공한 것처럼 표시되지 않음
- 재접속 후 서버와 화면 데이터가 일치함
- 로그아웃한 사용자 데이터가 다음 사용자에게 보이지 않음

## 10. 8단계 — Android 앱으로 패키징하고 내부 테스트하기

### 목표

사용자에게는 Google Play 앱으로 제공하되, 현재 PWA를 Trusted Web
Activity(TWA) 방식의 Android App Bundle로 패키징한다.

TWA는 앱 내부에서 검증된 HTTPS PWA를 전체 화면으로 실행하는 방식이다.
따라서 “웹사이트를 먼저 공개 홍보”할 필요는 없지만, 앱이 불러올 HTTPS
주소 자체는 반드시 먼저 준비돼야 한다.

### 권장 구성

- 테스트용 Supabase 프로젝트
- 외부에 홍보하지 않는 HTTPS 앱 주소
- 테스트용 Google OAuth 설정
- 테스트 전용 이메일 계정
- 실제 개인정보를 사용하지 않는 가짜 데이터
- Bubblewrap 기반 TWA Android 프로젝트
- 앱 서명 키와 Digital Asset Links 설정

### 배포 전 준비

- `.env.example` 최신화
- 운영 secret이 Git에 들어가지 않았는지 확인
- Supabase OAuth Redirect URL 등록
- SPA 새로고침 시 `/record`, `/settings` 등이 404가 되지 않도록 rewrite 설정
- HTTPS 확인
- PWA manifest와 Service Worker 확인
- 모바일 Safari와 Android Chrome 테스트
- PWA manifest의 앱 이름·아이콘·테마 색상 확정
- Android 패키지명 확정
- `.well-known/assetlinks.json`으로 앱과 도메인 소유권 연결
- Android App Bundle(`.aab`) 생성 및 서명

### 스테이징 배포 체크리스트

- 신규 가입
- 로그인과 로그아웃
- 초대 코드 생성과 참여
- 공유/비공개 텍스트 기록
- 공유/비공개 사진
- 기록 수정과 삭제
- 커플 연결 해제
- 일정과 여행
- 생리주기 비공개
- 홈 화면 설치
- 새로고침 및 오프라인 진입
- Play Console 내부 테스트에서 설치·업데이트·Google 로그인

### 완료 기준

- Play 내부 테스트 앱에서 주요 기능이 동작
- 테스트 계정 외 데이터가 없음
- 보안 테스트와 회귀 테스트 통과

## 11. 9단계 — Google Play 비공개 테스트 진행하기

### 목표

처음부터 공개 서비스로 출시하지 않고 Google Play 비공개 테스트에서
기능과 사용성을 검증받는다.

### 권장 규모

- 실제 사용성 확인은 3~5커플부터 시작
- 신규 개인 개발자 계정의 정식 출시 조건을 위해 최소 12명의 테스터 확보
- 최소 14일 동안 테스터 12명 이상이 연속으로 비공개 테스트에 참여
- 실제 민감한 기록 대신 테스트용 기록 사용을 먼저 안내

### 확인할 핵심 질문

- 곰신이 하루 기록을 부담 없이 남길 수 있는가?
- 군화가 짧은 시간 안에 상대의 하루를 이해할 수 있는가?
- 공유와 비공개 설정을 혼동하지 않는가?
- 기록이 저장됐는지 사용자가 확신할 수 있는가?
- 초대와 연결 해제 과정이 이해하기 쉬운가?
- 홈 위젯이 실제로 도움이 되는가?

### 수집할 지표

- 가입 완료율
- 커플 연결 성공률
- 첫 기록 작성 성공률
- 기록 저장 실패율
- 요약에서 원문으로 이동한 횟수
- 앱 재방문율
- 사용자가 보고한 데이터 노출 또는 손실 문제

민감한 기록 본문을 분석용 로그에 수집하면 안 된다. 이벤트 이름과 성공·실패 여부 정도만 수집한다.

### 중단 조건

다음 문제가 하나라도 발생하면 신규 사용자 초대를 중단하고 먼저 수정한다.

- 비공개 기록 노출
- 다른 커플 데이터 노출
- 기록 또는 사진의 반복적인 손실
- 연결 해제 후에도 상대가 데이터에 접근
- 로그인 계정이 뒤섞이는 현상

## 15. 비전공자인 담당자가 직접 결정해야 할 제품 정책

기술자가 대신 정하면 서비스 방향이 달라질 수 있는 항목들이다.

### 공개 범위

- 기록 기본값을 “우리에게 공유”로 유지할지
- 개인 일정 기능을 제공할지
- 공유 일정은 상대도 수정할 수 있는지

### 연결 해제

- 연결 해제 후 각자의 기록을 보존할지
- 재연결을 허용할지

### 군화 홈

- 상대 상태를 백분율로 표현할지
- 오해를 줄이기 위해 “편안함/보통/지침” 같은 문구로만 표현할지

권장안은 정성 문구다. 기록 개수만으로 감정 에너지 백분율을 계산하면 실제 마음 상태처럼 오해될 수 있다.

### 운영 범위

- 데모 둘러보기를 운영에서도 보여줄지
- 사진까지만 지원하고 영상은 나중에 추가할지
- 푸시 알림을 베타 전에 만들지

권장안은 사진까지만 먼저 안정화하고, 영상과 푸시 알림은 베타 이후에 추가하는 것이다.

## 16. 현재 프로젝트의 현실적인 첫 번째 마일스톤

첫 번째 목표를 “앱 완성”으로 잡으면 범위가 너무 크다. 다음 상태를 첫 마일스톤으로 권장한다.

### 마일스톤 1: 안전한 텍스트 기록 베타

- 두 사용자가 로그인할 수 있음
- 초대 코드로 1:1 연결
- 공유 텍스트 기록 작성·수정·삭제
- 본인 전용 비공개 텍스트 기록
- 상대는 공유 기록만 열람
- 군화 홈 요약에서 원문 이동
- 연결 해제 시 상대 접근 즉시 차단
- 빌드·린트·테스트 통과
- A/B/C RLS 테스트 통과
- 스테이징 배포 완료

사진·음성·여행·위젯을 모두 완성하기 전에 이 마일스톤부터 성공시키는 것이 안전하다.

### 마일스톤 2: 미디어와 커플 일정

- 공유/비공개 사진 업로드
- 안전한 Signed URL
- 일정·기념일·여행
- 오프라인과 재시도 처리

### 마일스톤 3: 클로즈드 베타

- 3~5커플 초대
