## 1. 최종 사업 정의

### 제품 정의

> **함께하지 못한 하루를 안전하고 간편하게 이어주고, 그렇게 이어온 시간을 다시 정리할
> 필요 없이 둘만의 기억으로 만들어주는 서비스**

곰신로그는 `AI 커플앱`, `군인 커플앱`, `채팅앱`, `일기앱`, `포토북 앱`, `클라우드 저장앱`
중 하나로 축소하지 않는다. 초기시장은 군 복무 커플이지만 장기적으로 해결하는 문제는
반복되는 **생활시간 비대칭**이다.

사업의 전체 흐름은 다음과 같다.

```text
놓친 하루의 맥락 단절
→ 기록 → 상대방의 오늘 → 정확한 원본 → 이따 이야기하기 → 이야기거리
→ 실제 통화·기존 메신저·만남 → 이야기했어요
→ 시간이 지나 자연스럽게 기록 축적
→ 사용자가 고른 기억을 디지털·실물 Memory Product로 제작
```

### 사업모델 한 문장

> **연결과 보존은 무료, 함께 쌓아온 시간을 더 의미 있는 기억으로 만드는 경험에 과금한다.**

## 2. Primary Customer와 커플 단위 획득

### Primary Customer

1차 고객은 군 복무 중인 연인을 둔 민간인 파트너, 즉 **곰신**이다.

군 복무 중인 연인은 결제자라고 단정하지 않으며, 가치 생성에 함께 참여하는
**파트너 사용자**로 정의한다.

### 고객획득 퍼널

```text
곰신 유입
→ 가입
→ 군 복무 중인 연인 초대
→ 파트너 연결
→ 커플 단위 서비스 시작
```

따라서 획득의 최종 단위는 다운로드 1건이 아니라 **파트너 연결이 완료된 커플 1쌍**이다.
다운로드·노출은 보조적인 유입 지표일 뿐 고객가치 또는 시장수요 증거가 아니다.

## 3. Problem — 생활 맥락 단절

### 핵심 문제

곰신로그가 해결하는 것은 “군대 때문에 연락을 못 한다” 또는 이별 자체가 아니다.
핵심은 연락하지 못했던 시간 동안 서로 보지 못한 하루의 맥락이 누적되어, 나중에 다시
탐색·질문·설명해야 하는 **생활 맥락 단절과 재설명 부담**이다.

```text
물리적 분리
→ 시간적 분리
→ 공유되지 못한 하루 누적
→ 상대방의 맥락 부족
→ 메시지·사진 탐색
→ 질문·재설명
→ 오해·서운함 발생 가능성
```

서비스가 이별률을 낮춘다고 주장하지 않는다. 검증하는 것은 하루 맥락을 복구하는 데
드는 부담, 연결 행동, 실제 대화 전환이다.

### `일말상초` 사용 원칙

`일말상초`(일병 말~상병 초)는 군 복무 커플 사이에서 문제현상을 보여주는 **정성적 Hook**
으로만 사용한다. 공신력 있는 근거가 없는 이별률·갈등률·사용 효과 숫자를 만들지 않는다.
문제강도·갈등시기·맥락단절 비율은 협약기간 자체조사로 검증한다.

### 문제 설명의 고정 순서

1. 현상: 군 복무 커플의 관계 유지 어려움과 `일말상초`
2. 원인 가설: 생활시간 비대칭
3. 고객문제: 공유되지 못한 하루의 맥락
4. 현재 행동: 메시지·사진 탐색, 질문, 하루 재설명
5. 결과: 탐색·기억·설명 부담 및 오해·서운함 가능성
6. 미충족 수요: 연락량이 아니라 연락하지 못한 하루를 이후 빠르게 이해하는 경험

Problem에서 기술·AI를 먼저 설명하지 않는다.

## 4. 장기 문제 — 기록에서 기억으로 가는 중복 작업

평소 기록은 메신저·사진첩·SNS·캘린더·향후 음성·영상에 분산된다. 기념일·휴가·전역에
기억물을 만들려면 다시 다음을 수행해야 한다.

```text
탐색 → 날짜 확인 → 선별 → 문장 작성 → 배치 → 제작
```

곰신로그의 장기 문제정의는 저장공간 부족이 아니다. 이미 존재하는 기록을 기억으로
만들기 위해 다시 모으고 정리하는 **중복 작업과 제작 부담**을 줄이는 것이다.

## 5. 시장분석 방법과 가설 표기

시장규모는 현역병 숫자 하나로 확정하지 않는다. 다음 순서로 추정하고 각 단계의 가정을
명시한다.

```text
병무청 현역병 입영현황
→ 연령별 현역병 입영분포
→ 해당 연령대의 현재 연애 중 비율
→ 잠재 군 복무 커플 추정
→ 민간인 파트너 = 잠재 곰신
```

- 일반 20대 연애율을 현역병에게 적용하면 **시장확정치가 아니라 초기 가설**이다.
- 협약기간에는 입영 당시 연애관계 유지 비율을 자체조사해 보정한다.
- 학력 자료는 시장규모를 `현역병 × 연애율 × 대학생 비율`로 축소하는 데 사용하지 않는다.
- 학력은 대학생·취업준비·초기 직장생활 같은 Persona와 초기 고객획득 채널을 설계하는
  보조근거로만 사용한다.
- 곰신 수, 커플 수, 이별률, 시장점유율 등 근거 없는 수치는 만들지 않는다.

공식 통계, 공개 자료, 자체조사, 제품행동 데이터는 서로 다른 근거로 표시한다.

## 7. Daily Core와 AI 역할

### Daily Core

```text
간편 기록
→ 상대방의 오늘
→ 정확한 원본
→ 이따 이야기하기
→ 이야기거리
→ 실제 통화·기존 메신저·만남
→ 이야기했어요
```

실제 대화는 곰신로그 내부 채팅만을 뜻하지 않는다. 전화·기존 메신저 등 커플 사이의
대화로 자연스럽게 이어지는 것도 포함한다. 핵심 성공지표는 앱 체류시간이 아니라
**실제 대화 연결**이다.

### AI는 보조기술

AI는 제품 정체성이 아니라 놓친 하루의 이해와 기억제작 노동을 줄이는 보조기술이다.

허용:

- 사실 중심 요약
- 시간순 정리
- 사용자가 선택한 기록의 문장 편집
- 레이아웃·구성 보조
- 사용자가 고른 기억상품 제작의 반복작업 감소

금지:

- 관계점수·애정도·이별예측
- 숨은 감정 추론·관계진단
- 중요한 추억의 자동 선정
- 건강·관계 상태를 판단하는 프로파일링

### 온디바이스와 미지원기기

지원 가능한 기기에서는 온디바이스 AI를 검증한다. 목적은 민감 기록의 외부 전송 최소화,
빠른 하루 정리, 서버 AI 변동비 완화 **가능성** 검증이다. 서버 AI 비용이 0원이 된다고
확정하지 않는다.

미지원 기기는 규칙 기반 기본기능 유지 또는 검증된 대체방식을 사용한다. 기기 지원범위가
확정되기 전에는 모든 사용자에게 동일한 AI 성능을 약속하지 않는다.

## 8. Privacy와 기록 보존

Privacy는 Premium이 아니라 기본조건이다.

- E2EE를 유료화하지 않는다.
- 개인정보 보호기능을 Plus로 전환하지 않는다.
- 보안기능을 저장상품처럼 판매하지 않는다.
- 핵심 기록·관계 연결·데이터 권리를 저장용량 인질로 만들지 않는다.
- `완벽한 보안`, `해킹 불가능`이라고 표현하지 않는다.

협약기간에는 텍스트 기록 E2EE, 사진 E2EE, 키관리, 권한, 복구, 독립 보안검토를 단계적으로
고도화한다. 세부 암호 프로토콜은 [`E2EE_PHASE_1A_ARCHITECTURE_V2_1.md`](E2EE_PHASE_1A_ARCHITECTURE_V2_1.md),
개인정보·법적 경계는 [`DATA_LEGAL_E2EE_ARCHITECTURE_DECISION_2026-08-11.md`](DATA_LEGAL_E2EE_ARCHITECTURE_DECISION_2026-08-11.md)가 소유한다.

### 기억 아카이브의 정의

기억 아카이브는 클라우드 저장공간이 아니다. 평소 축적된 관계기록을 두 사람의 시간축에
따라 다시 찾고 회고하며, 사용자가 선택한 기억을 Memory Product로 활용하도록 만드는
**관계 기억관리 구조**다.

협약기간은 텍스트·사진 중심으로 검증하고, 음성·음성편지·영상·고화질 미디어는 후속
확장으로 둔다.

### 개인 클라우드 전략

개인 클라우드 연계 저장구조는 **검증할 기술방향**이다. iOS에서는 iCloud/CloudKit을
후보로 삼을 수 있지만 도입 완료·구현 완료로 쓰지 않는다.

```text
사용자 기기
→ 메타데이터·프라이버시 전처리
→ 곰신로그 E2EE
→ 사용자 개인 클라우드 후보 저장
→ 승인된 공유 구조 검증
```

계정·커플 연결·권한·메타데이터·운영정보는 별도 백엔드가 필요하다. 개인 클라우드가
서버비 0원, 무제한 영상, 회사가 제공하는 100GB를 보장한다는 식으로 표현하지 않는다.

## 9. Revenue Model — Free Core + Memory Product + Optional Plus

### 9.1 Free Core

제품 정책상 다음은 무료영역이다. 현재 구현 여부는 FACT STATES와 `CURRENT_STATE.md`로
별도 표시한다.

- 일상 기록
- 기본 관계기록과 기술적으로 지원되는 범위의 정상적인 사진·미디어 보존
- `상대방의 오늘`
- 정확한 원본 확인
- `이따 이야기하기`
- Conversation Bridge(이야기거리 보관함과 실제 대화 연결)
- E2EE·보안·프라이버시 제어
- 기본 일정·D-Day
- 기본 기억 타임라인
- 기본 데이터 내보내기·삭제 등 데이터 권리

사용자의 기록·원본 화질·정상적인 보존·내보내기를 일부러 막아 결제하게 만들지 않는다.

### 9.2 1차 수익 — Memory Product

협약기간 가장 먼저 검증할 수익모델은 **1회성 Memory Product**다.

```text
무료 사용
→ 관계기록 축적
→ 관계 마일스톤
→ 기억물 제작 제안
→ 미리보기
→ 사용자가 기억 선택
→ AI 편집보조
→ 제작 완성
→ 1회 결제
```

초기 대표 MVP는 **「우리의 한 달」**이다. 여러 상품을 동시에 약속하지 않고 이 상품의
수요와 제작 economics를 먼저 검증한다. 후보 마일스톤은 100일·첫 휴가·1주년·전역이다.

판매하는 것은 저장공간이 아니라, 이미 쌓인 시간을 다시 모으고 정리하지 않고 하나의
기억으로 완성하는 경험이다.

#### 구매자와 권한 경계

Primary Customer(곰신)는 반드시 유일한 결제자를 뜻하지 않고, 파트너 사용자와도 구분된다.
가치의 수혜자는 커플 두 사람이다. 「우리의 한 달」 MVP에서는 커플 중 한 명이 제작을
시작하고 결제할 수 있다.

다음 세 가지는 결제 구현 전에 확정해야 하며, 지금 추측하지 않는다.

- 정확한 구매자 정의
- 제작 중 미리보기의 상대방 노출 범위
- 연결 해제 이후 주문·완성물 접근 처리

이는 Memory Product 구현 전 선행 product/engineering gate다
([`ENGINEERING_ROADMAP.md`](ENGINEERING_ROADMAP.md)의 `P-MP` 단계).

### 9.3 가격은 가설

- 디지털 기억상품: **3,900~7,900원** 초기 가설
- 실물 기억책: **2~5만원대** 초기 가설

협약기간 가격민감도·실제 구매전환·POD 제작원가·배송·결제·CS·재제작 비용을 검증한
뒤 결정한다. 확정가격, 매출, 목표전환율을 미리 쓰지 않는다.

### 9.4 실물상품과 POD

초기 실물 기억상품은 대량생산하지 않고 POD 주문생산을 우선 검증한다.

```text
주문 → 제작 → 배송
```

#### 검증 순서 — 디지털 먼저, POD 다음

M7 안에서도 순서를 지킨다. 디지털 기억상품으로 지불의향·제작완료·실제결제를 먼저
검증한 뒤에 POD 실물 제작을 검증한다.

```text
디지털 Memory Product
→ 지불의향
→ 제작완료
→ 실제결제 확인
→ 그 다음 POD 실물 제작 검증
```

이유는 디지털 상품이 배송·수령인 개인정보·외부 제작 벤더 없이 수요를 확인할 수 있기
때문이다. 디지털에서 실제결제가 확인되기 전에 POD 업체 계약·최소 제작수량·선투자를
진행하지 않는다. 실물 제작·배송 개시에는 별도로 개인정보·법률·처리자 검토(§13)가
선행되어야 한다.

기여이익은 다음으로 판단한다.

```text
판매가격
− 제작비
− 배송비
− 결제수수료
− 플랫폼·판매채널 수수료(해당되는 경우)
− 포장·CS·재제작 비용
= 건당 기여이익
```

판매채널 수수료는 실제 판매·결제 경로가 확정된 뒤에 실측한다. 앱 내 디지털 상품은
앱스토어 수수료가 적용될 수 있고, 외부 웹 결제는 다른 조건이 적용될 수 있다. 확정 전에는
특정 수수료율을 사실로 쓰지 않고 **검증 대상 항목**으로 남긴다. 디지털 기억상품은 단가가
낮아 이 항목이 기여이익 판단을 바꿀 수 있으므로 M7 검증에 반드시 포함한다.

초기 대량재고·보관비·미판매 폐기를 전제로 하지 않는다.

### 9.5 Optional Plus

Plus는 핵심 BM이 아니며, Memory Product에서 실제 지불가치가 확인된 뒤에만 검증한다.
후보는 고급 회고·검색·타임라인·정리·커플 테마·홈 위젯·기념일 디자인·추가 템플릿·
기억상품 혜택이다.

Plus에 넣지 않는 것:

- E2EE·기본 보안·프라이버시
- 기본 기록·Conversation Bridge·기본 일상 연결
- 저장용량 자체·기본 데이터 권리

반복 가치가 확인되지 않으면 Plus를 도입하지 않는다. 구독 도입 자체가 목표가 아니다.

## 11. 협약기간 M1–M8 로드맵

`M1`–`M8`은 **8개의 순차 실행구간**이며 각 구간은 앞 구간의 산출물을 입력으로 받는다.
저장소에는 확정된 협약기간 길이·시작월이 없으므로 특정 달력 날짜를 전제하지 않는다.
사업계획 제출 시 실제 협약기간이 확정되면 그때 해당 월에 매핑한다. 그때까지 `M3 = 3개월차`
같은 달력 해석을 하지 않는다.

| 시기 | 핵심 과제 | 주요 실행 | 산출물·판단 |
|---|---|---|---|
| M1 | 개인정보 보호 | 텍스트 E2EE·보안구조 고도화 | 보안 기반 |
| M2 | 대화 연결 | Conversation Bridge·핵심 흐름 완성 | 실증 후보 |
| M3 | 고객 문제검증 | 곰신 고객문제·초기 사용실증 | 문제강도·연결행동 |
| M4 | UX 개선 | 실증 이탈구간 개선 | 핵심 UX V2 |
| M5 | 장기 기록 | 사진 E2EE·기본 기억 아카이브·개인 클라우드 연계 PoC | 기록축적 구조 |
| M6 | AI 실증 | 온디바이스 요약 기기별 실증 | 기기별 적용판단 |
| M7 | BM 검증 | `우리의 한 달` MVP·POD·가격시험 | 수익모델 근거 |
| M8 | 사업화 판단 | 반복사용·원가·구매 데이터 종합 | 시장진입 GO/HOLD |

음성·영상 전체 구현을 협약기간에 무리하게 약속하지 않는다. M-stage는 사업 실행·검증
순서이고, 기술 의존성은 [`ENGINEERING_ROADMAP.md`](ENGINEERING_ROADMAP.md)의 P-stage를
따른다.

M3의 통제된 외부 검증은 `ENGINEERING_ROADMAP.md`의 `LV — Limited Validation Gate`,
M7의 판매 가능한 기억상품 구현은 같은 문서의 `P-MP — Memory Product MVP`가 소유한다.
LV는 Public Beta·Production 승인이 아니고, P-MP는 온디바이스 AI 성공에 의존하지 않는다.

M1·M2가 고객 접촉을 금지하는 것은 아니다. 인터뷰·문제탐색 같은 저비용 고객조사는 M3
이전에 병행할 수 있다. M3는 **제품 사용 기반의 공식 검증 단계**이며, 팀이 고객과 처음
대화할 수 있는 시점이 아니다.

## 12. 생존·운영 구조

지원사업 종료 후의 생존전략은 **핵심개발 내부화 + 개인 클라우드 연계 + 온디바이스 AI +
POD**다.

- 내부 개발: 핵심 제품을 지속 개선할 역량 보유
- 개인 클라우드 연계: 고용량 미디어 저장비 증가를 완화할 가능성 검증
- 온디바이스 AI: 서버 AI 변동비 증가를 완화할 가능성 검증
- POD: 재고·선투자 부담 최소화

목표는 사용자 증가와 함께 저장·AI·재고 비용이 같은 속도로 급증하는 구조를 완화하는
것이지 비용을 0원으로 만드는 것이 아니다.

## 16. 검증 데이터 금지와 M8 GO/HOLD

다음 숫자를 현재 성과처럼 임의 생성하지 않는다.

- 곰신 수·군 복무 커플 수·시장점유율
- 군 복무 커플 이별률·`일말상초` 이별률
- 고객 인터뷰·베타 사용자 수
- 반복사용률·구매전환율·매출·기억상품 구매율

데이터가 없으면 **협약기간 검증 예정**으로 표시한다.

### M8 판단

M8은 다음 자료를 종합해 GO/HOLD를 판단한다.

- 문제강도와 자체조사 보정 결과
- 커플 연결·상대방 확인·실제 대화 행동
- 4주 반복사용
- Memory Product 실제 결제전환
- POD 기여이익
- 저장·AI·제작·CS 운영비와 지원 부담

사전에 숫자 임계값을 발명하지 않는다. 근거가 충분하지 않으면 HOLD 또는 추가 검증으로
남길 수 있다.

## 17. 전략 가드와 문서 유지

다음은 현재 전략이 아니다. 과거 문서나 작업 요청에서 재등장하면 **DIRECTION CONFLICT**로
표시하고 사용자 승인 없이는 사업전략·무료 경계·저장구조를 바꾸지 않는다.

- 저장공간을 주요 유료상품으로 판매
- 고화질 사진·긴 영상·용량별 구독을 유료 게이트로 사용
- E2EE·기본 보안을 유료화
- 구독을 초기 핵심 BM으로 설정
- 서버에 모든 미디어를 저장하는 구조만 전제
- AI가 중요한 추억을 자동 선정하거나 관계·감정을 점수화
- 체류시간 또는 다운로드를 최종 North Star/KPI로 사용
- 군인 전체를 고객으로 정의
- 기억책을 단순 포토북·저장공간 사업으로 설명
- 음성·영상·CloudKit을 현재 완료로 표현

이 문서의 사업전략을 바꿀 때는 제품·엔지니어링·현재상태 문서와의 충돌을 먼저 기록한다.
가격·상품·POD 원가가 바뀌면 초기 가설 표기를 유지하고 이 문서만 authoritative business
home으로 갱신한다. 과거 `WORK_LOG`와 원문 문서는 역사를 위해 남기되 현재 전략의 근거로
사용하지 않는다.
