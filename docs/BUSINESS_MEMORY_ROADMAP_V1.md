1. **보안은 절대 유료화하지 않는다.** E2EE, 코어 채팅, 코어 기록, 상대방의

3. **유료 가치는 "더 많이, 더 좋게, 더 오래 간직하기"이지 "코어 기능을
   잠그기"가 아니다.** Free 티어에서 관계 루프가 완전히 동작해야 한다.
4. **서버 비용을 회수할 수 있는 요금제만 설계한다.** 처음부터 "무제한"을

5. **관리형 인프라를 우선한다.** 지금 단계에서 자체 서버를 사지 않는다 (§5).
6. **AI는 편집자이지 심판이 아니다.** 관계·감정을 점수화하거나 판단하지
   않는다. 이 원칙은 `PRODUCT_V3.md` §13(기계 추론 감정 규칙)의 연장이다.

## 2. 포지셔닝의 장기 진화

```text
지금:     "함께하지 못한 시간까지, 서로의 하루가 이어지도록" (커플 앱)

장기:     "둘이 함께하지 못했던 시간까지 안전하게 보관하고,
           나중에는 손에 잡히는 기억으로 만들어주는 사적인 기억 보관소"
```

### 제품 플라이휠

```text
1. "오늘 서로 무엇을 놓쳤는가?"          — 코어 루프 (지금)
        ↓
2. "그 시간을 어떻게 함께 남겼는가?"      — 사진/미디어, 채팅 아카이브
        ↓
3. "우리가 함께 남긴 시간을 다시 볼 수 있는가?" — 아카이브 탐색, Book Studio
        ↓
4. "그 기억을 손에 들 수 있는가?"        — 실물 메모리북
```

제품 진화 축: **일상 연속성 → 사적 기억 아카이브 → 고화질 암호화 미디어 →
기억 큐레이션 → Book Studio → 실물 책.** 이것이 north-star 방향이다.

## 5. 미디어 아키텍처 방향

### 저장소

- **애플리케이션/Auth/DB:** Supabase — Auth, Postgres, RLS, 커플 관계,
  조율 메타데이터. 유지.
- **미디어 저장:** Cloudflare R2 또는 동급 저-이그레스 오브젝트 스토리지를
  선호. **암호화된 미디어 blob만 저장한다.** Supabase Storage에 사진/음성/
  영상을 대역폭 비용이 감당 안 될 규모까지 영구히 의존하지 않는다.
- **미디어 접근:** Cloudflare Worker(또는 동급) 얇은 인가 게이트웨이가
  인증된 사용자·활성 커플 접근·오브젝트 스코프를 검증한 뒤에만 암호화
  오브젝트 전송을 허용한다. **절대 평문 미디어 처리기가 되지 않는다.**
- **클라이언트:** 사진 처리, 실용적 범위의 영상 압축/트랜스코딩, 암호화,
  복호화, 가능한 범위의 썸네일/프리뷰를 기기에서 수행한다. E2EE 친화적
  클라이언트 처리를 우선한다.

이 방향은 `E2EE_PHASE_1A_ARCHITECTURE_V2_1.md`의 원칙과 일치해야 한다 —
서버가 콘텐츠 평문을 보지 않는다는 목표를 미디어 인프라 선택이 어겨서는
안 된다.

### 자체 서버 vs 관리형/임대 인프라

**지금 프로덕션 서버 컴퓨터를 사지 않는다.** 집/사무실 기기에서 사용자
사진/영상 프로덕션 저장소를 운영하지 않는다.

**현재 권장: 관리형 클라우드 / 오브젝트 스토리지.**

이유: 이중화, 하드웨어 장애 대응, 백업, 전원/네트워크 안정성, DDoS/네트워크
운영, 스케일링, 보안 운영, 창업자의 유지보수 부담 감소.

개인 소유 NAS/서버는 나중에 **암호화 백업/아카이브 실험** 용도로는
유용할 수 있으나, **프로덕션 원본 저장소로는 쓰지 않는다.**

측정된 클라우드 비용 데이터가 실제로 자체 서버/코로케이션을 정당화할
만큼 규모가 커지기 전까지는, 투기적 마이그레이션을 하지 않는다.

### 서버 비용 회수 원칙

유료 미디어 플랜은 그것이 소비하는 저장소 비용을 스스로 감당해야 한다.

- 초반에 "무제한" 플랜을 두지 않는다. 명시적 저장 용량 상한을 쓴다.
- 제품 경제성 평가 지표: **활성 유료 커플당 매출 − (앱스토어/결제 수수료 +
  저장소 + 오브젝트 연산 + 대역폭/게이트웨이 비용 + DB/Auth 비용 + 백업 +
  지원 + 실물 상품 원가)**
- 헤비 미디어 사용자가 플랜을 적자로 만들지 않을 만큼 충분히 높은 총마진을
  목표로 한다.
- 정확한 마진 가정을 측정된 베타 사용량 없이 고정하지 않는다.
- 베타에서 추적할 지표: 유료 커플당 중앙값 저장량, p90/p95 저장량, 업로드
  볼륨, 영상 사용량, 오브젝트 요청 수, 리텐션. 가격 개정은 이 데이터를
  본 뒤에 한다.

## 9. 가장 중요한 메모리 제품 결정 — 사용자가 매일 밤 긴 일기를 쓰게 하지 않는다

그 부담은 너무 크다. 대신 가벼운 메커니즘을 둔다:

> **"오늘의 책갈피"** (또는 "책에 남기기")

사용자가 선택:

- 기록 하나
- 사진 하나
- 채팅의 한 순간

선택적으로 **한 문장**만 쓴다: *"왜 이 장면을 기억하고 싶은가?"*

예:

- "첫 휴가 전날이라 둘 다 설렜던 날."
- "오늘 전화에서 했던 이 말은 꼭 기억하고 싶다."

이것이 **인간의 의도**를 포착한다. 빨라야 한다 — 대략 탭 한 번 + 선택적
한 문장.

### 왜 인간의 의도가 중요한가

AI가 나중에 혼자서 "이 날들이 중요했다"고 판단하게 두지 않는다. 두
사용자가 직접 **"이건 중요했다"**를 표시할 수 있어야 한다.

가장 좋은 책 소재는 **기록 + 사진 + 대화 + 사람이 만든 책갈피**에서
나와야 한다 — AI의 관계 점수화가 아니라. 심리적 판단을 하지 않는다.

## 10. Book Studio 로드맵 — 단계적 접근

### Stage 1 — AI 없음

먼저 수요를 증명한다.

다음으로부터 결정론적 책 초안을 생성한다: 날짜, 선택된 기록, 선택된 사진,
책갈피, 기념일/마일스톤.

사용자가 편집/재정렬/삭제할 수 있게 한다.

인쇄 준비 미리보기를 만든다.

**사용자가 실제로 책을 주문하지 않으면 AI에 크게 투자하지 않는다.**

### Stage 2 — AI Book Editor

**실물 책 수요가 확인된 뒤에만.**

AI의 역할은 **편집자/인터뷰어**이지 관계 심판이 아니다.

AI가 물을 수 있는 것:

- "입대 첫 주를 별도 챕터로 만들까요?"
- "이 사진과 이 기록이 같은 날이에요. 같이 넣을까요?"
- "이 시기에 가장 기억하고 싶은 일은 뭐였나요?"
- "이 문장을 책에 남기고 싶나요?"

**사용자가 결정한다.**

## 11. 프라이버시 경계 — AI Book Studio와 인쇄

이 절은 코어 E2EE 원칙과 정면으로 만나는 지점이므로 특히 중요하다.

### AI Book Studio 프라이버시

일반 곰신로그 콘텐츠는 **서버에서 자동으로 복호화되어 외부 모델로
전송되지 않는다.** Book AI 흐름은 **명시적 opt-in**이어야 한다.

선호하는 개념적 흐름:

```text
사용자가 기록/사진/책갈피를 선택
  → 기기가 "이 내용이 일반 E2EE 보호 밖으로 나간다"는 것을 명확히 설명
  → 선택된 콘텐츠만 Book Studio AI에 제공
  → AI가 편집/질문
  → 사용자가 최종 초안을 승인
```

**관계 아카이브 전체를 조용히 외부 모델에 업로드하지 않는다.**

AI를 다음 용도로 쓰지 않는다:

- 관계 품질 판단
- 궁합 점수화
- 우울감 추론
- 파트너 평가
- 숨겨진 심리 프로파일링 기반 "베스트 모먼트" 선정

### 인쇄 프라이버시 경계

물리적 프린터는 필연적으로 **인쇄용 평문 출력**을 필요로 한다. 이것은
E2EE 경계로부터의 **명시적 export**다.

UX가 명확히 설명해야 한다:

> "책 제작을 위해 사용자가 선택한 내용만 인쇄용 파일에 포함됩니다."

선택된 책 콘텐츠만 인쇄 워크플로에 들어가고, 나머지 곰신로그 데이터는
제외된다.

**향후 요구사항 (지금 구현하지 않음):** 임시 인쇄 파일에 대한 보존/삭제
정책을 정의해야 한다.

## 12. 코어를 유료화가 오염하지 않도록

**절대 유료화하지 않는다:**

- E2EE

- 코어 기록
- 상대방의 오늘
- 정확한 원본
- 기본 반응
- 이따 이야기하기
- 기본 일정/주기 안전 기능
- 보안/프라이버시 제어

- 더 많은 저장소
- 원본 화질
- 음성/영상
- 더 풍부한 아카이브
- 커스터마이징
- 기억 보존
- Book Studio
- 실물 상품

## 14. 단계적 롤아웃 순서

이 문서의 방향이 `ENGINEERING_ROADMAP.md`의 순서를 바꾸지 않는다. 관계:

1. 지금 진행 중: P0–P5 (핵심 루프, Phase 0 보안 기반, 채팅 계약, daily_records E2EE)

6. 실물 메모리북 상품 정식화 — 실제 POD 벤더 견적 확보 후

않고, 결정론적 Book Studio 이전에 AI Book Studio를 구현하지 않는다.
