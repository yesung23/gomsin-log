### 이 스캔에서 나온 결정적 사실 하나

**연결이 해제된 커플은 되살아날 수 없다.** 초대 코드를 발행하는 세 경로가 전부
**active 멤버십**을 요구하기 때문이다:

- `regenerate_invitation` (013:277) — `WHERE user_id = v_uid AND status = 'active'`,
  아니면 `No active couple to invite to`
- `create_invitation` (030) — `AND status = 'active'`, 아니면
  `Active member access required`
- `create_couple_and_invitation` (015) — active 커플이 있으면 거부하고,
  `INSERT INTO public.couples DEFAULT VALUES`로 **항상 새 couple_id를 만든다**

그리고 멤버십을 `active`로 되돌리는 경로는 전부 초대 **소비** 안에 있다
(001:357, 002:18, 006:111, 015:219). `disconnect_couple`이 양쪽을 모두
`disconnected`로 바꾸므로, 그 커플은 코드를 만들 수 없고 → 아무도 소비할 수 없고 →
**어떤 멤버십도 다시 active가 될 수 없다.**

이것이 §10의 재연결 의미를 결정한다. 정책으로 정한 것이 아니라 코드가 이미 강제하고
있는 사실이다.

## 1. 목적과 비목표

채팅의 가치는 "메신저가 하나 더 생기는 것"이 아니라 **맥락의 연속성**이다.

```text
가볍게 기록 → 상대방의 오늘 → 정확한 원본 기록 → 반응 / 이따 이야기하기
           → 채팅 → 실제 대화 → 추억 축적
```

카카오톡을 대체하려는 것이 아니다. 카카오톡에 없는 것 — **"이 기록에 대해"**라는
연결이 붙은 대화 — 가 목적이다.

**비목표:** 그룹 채팅 · 커뮤니티/공개 채팅 · 채널 · 업무용 메시징 · 음성/영상 메시지 ·
통화 · 스레드 · 전달(forward) · 타이핑 표시 · presence · 읽음 표시 · 사라지는 메시지 ·
예약 전송 · 서버 측 전문 검색 · AI 요약 · 봇 · 무거운 메시지 리액션.

근거는 §17.

## 3. 키·스코프 결정

### 후보

- **A. 커플 User-Content CSK 스코프 하나를 공유** — 기록·채팅·미디어가 같은 CSK
- **B. 커플 아래 채팅 전용 스코프** — 채팅만의 epoch·envelope·rotation

### 결정: **A**

| 기준 | A (공유 CSK) | B (전용 스코프) |
|---|---|---|
| 키 rotation | 기기 침해 시 한 번 | 도메인마다 한 번. 침해된 기기는 어차피 **모든** 도메인을 들고 있었으므로 분리 rotation은 존재하지 않는 시나리오다 |
| 삭제 의미 | 커플 소유 하나만 추적 | scope별 삭제·보존 규칙이 두 벌 |
| 새 기기 프로비저닝 | GLK2 envelope 한 세트 | 기기마다 envelope 세트가 하나 더. 실패 지점 증가 |
| 복잡도 | 추가 0 | epoch 상태 기계·envelope·rotation 전부 복제 |
| P5 (daily_records) | 같은 CSK를 그대로 씀 | 두 스코프가 공존, 라우팅 결정이 코드마다 생김 |
| P6 (사진) | 같은 CSK | 사진이 어느 스코프인지 또 결정해야 함 |
| Blast radius | CSK 유출 시 커플 공유 전체 | **동일하다.** 두 스코프 모두 같은 기기에 provisioning되므로 실질 차이가 없다 |
| 프로토콜 중복 | 없음 | 있음 |

**B를 거부한 이유 한 줄:** 신뢰 경계가 완전히 같다. 커플 기록을 읽을 수 있는 기기는
커플 채팅도 읽어야 하는 바로 그 기기이므로, 스코프를 나눠서 얻는 보안이 **0**인데
프로토콜만 두 벌이 된다. Blast radius조차 줄지 않는다.

### 절대 규칙

**HRK는 어떤 경우에도 채팅의 키가 되지 않는다.** 건강 도메인은 분리 상태를 유지하며,
채팅 payload에 건강 정보를 넣지 않는다. `scopeKeys.ts`의 도메인 일치 검사가
HRK→CSK 재포장을 막는 유일한 방벽이고 P3에서 회귀 테스트를 붙였다.

## 4. E2EE 모델

### 봉투: GLE1을 그대로. 새 포맷 없음

GLE1 AAD는 이미 `protocol, suite, format, domain, epoch, owner, scope,
object type, object id, field id, content_revision`을 묶는다. **`object type`이
있다는 것이 핵심이다** — 채팅 메시지는 새 봉투 형식이 아니라 새 object type 하나다.

"P5/P6이 와도 재설계가 필요 없다"의 실제 근거가 이것이다. 미래를 잘 예측해서가 아니라
**봉투가 원래 object-type-agnostic이기 때문**이다.

| GLE1 필드 | 채팅에서의 값 |
|---|---|
| `domain` | `couple` (3) |
| `key_epoch` | 쓰기 시점의 ACTIVE CSK epoch |
| `object type` | 채팅 메시지를 뜻하는 새 상수 (게이트 C2) |
| `object id` | 메시지 id (§7) |
| `field id` | 본문 |

`nonce`·`suite`·`format`(암호 버전)은 **전부 GLE1 헤더 안에** 있다. 별도 서버 컬럼으로
꺼내지 않는다 — 클라이언트가 어차피 헤더를 파싱하고, 서버는 이 값들로 질의할 일이 없다.

### Epoch

- 새 메시지는 **ACTIVE epoch로만** 암호화한다(`epochAcceptsWrites`). ACTIVE가 아닌
  epoch로 쓰려는 시도는 거부한다.
- 과거 메시지는 자기 epoch를 헤더에 들고 있고, RETIRED는 영원히 복호화 가능하다
  (`epochAllowsDecrypt`). **따라서 rotation은 히스토리를 깨지 않는다.**
- 대화가 두 epoch에 걸쳐도 읽기에는 차이가 없다.

### 발신 기기 정체성

콘텐츠 암호화는 **scope key**로 한다. GLE1 AAD는 owner/scope를 묶지 **device를 묶지
않는다.** 따라서 채팅에 기기 식별자가 필요 없고, 서버 행에도 넣지 않는다(§5).

### write floor: 평문 강등 방어는 불필요, ACTIVE epoch 강제는 **필수**

이전 판은 "채팅에 write floor가 필요 없다"고 적었다. **그 문장은 틀렸다.** 032의 write
floor는 두 가지 책임을 지는데, 하나만 보고 판단한 결과였다.

| 032의 책임 | 채팅에 필요한가 |
|---|---|
| **평문 강등 방어** (암호문 행이 평문 컬럼으로 되돌아가는 것을 막음) | **불필요.** 채팅 테이블에는 평문 본문 컬럼이 애초에 없어 내려갈 곳이 없다 |
| **R5 EPOCH — 살아있는 ACTIVE epoch를 지목하도록 강제** (032:163-182) | **필수.** 태어날 때부터 암호화된 것과 무관한, 완전히 별개의 책임이다 |

032:163-182의 주석이 그 이유를 직접 말한다: *"stale writer holding a retired epoch fails
loudly instead of writing content nobody routes correctly."* 회전에서 배제된 기기 —
폐기됐거나, 오프라인이었거나, 악의적인 — 가 옛 키로 새 메시지를 계속 만들어내면 안 된다.
채팅도 정확히 같은 노출을 갖는다.

### ACTIVE epoch 강제 — 헤더 직접 검증 (Option A)

**서버는 GLE1 헤더를 직접 읽어 검증한다. `key_epoch`를 별도 컬럼으로 복제하지 않는다.**

가능한 이유는 헤더가 평문이고 오프셋이 고정이기 때문이다 (`src/crypto/gle1.ts:49-64`):

| 오프셋 | 길이 | 필드 | 서버가 요구하는 값 |
|---|---|---|---|
| 0 | 4 | magic | `"GLE1"` |
| 4 | 1 | format_version | 알고 있는 버전. 모르는 값이면 **거부** |
| 7 | 1 | domain | `3` (couple) |
| 12 | 8 | key_epoch (u64be) | `couple_id`의 **ACTIVE** epoch |

INSERT 시 서버는 위 네 가지를 확인하고, epoch는 032와 **동일한 조회**로 판정한다 —
`scope_keys`에 `state = 'ACTIVE' AND domain = 'couple' AND owner_couple_id = NEW.couple_id
AND key_epoch = <헤더에서 읽은 값>`인 행이 존재해야 한다. 없으면 거부한다.
`bytea`에서 값을 꺼내는 것은 `get_byte()`와 `substring()`으로 충분하다(정확한 SQL은
구현 마이그레이션의 몫 — 게이트 C10).

**왜 헤더 검증이 신뢰할 수 있는가.** `domain`과 `key_epoch`는 GLE1 AAD에 묶여 있고
(`gle1.ts:143-144`), 복호화 경로는 헤더와 AAD의 불일치를 먼저 거부한다
(`gle1.ts:276-277`, `E_DOMAIN_MISMATCH` / `E_EPOCH_MISMATCH`). 따라서 클라이언트가
헤더에 ACTIVE epoch를 적어놓고 실제로는 RETIRED 키로 봉인하면, 수신자는 헤더가 지목한
epoch의 키로 AAD를 재구성하므로 **GCM 태그 검증에서 실패한다.** 그 메시지는 아무도
열 수 없는 쓰레기다.

> **성립하는 불변식:** *수락되었고 복호화된다* ⟹ *ACTIVE epoch 키로 봉인되었다.*
> stale epoch는 **유효한** 새 메시지를 만들 수 없다.

**정직하게 남는 한계.** 서버는 암호문이 실제로 열리는지 확인할 수 없다. 커플 구성원은
복호화 불가능한 쓰레기 행을 밀어넣을 수 있다. 이것은 기밀성·인가 우회가 아니라 **신뢰
경계 안에서의 자해성 DoS**이고(커플이 신뢰 경계다, §18), RLS가 이미 외부인을 막고 있다.
해법은 암호가 아니라 rate limit이다.

**Option B(`key_epoch` 컬럼 복제)를 기각한 이유.** 복제된 컬럼은 헤더와 어긋날 수 있고,
어긋나지 않음을 증명하는 유일한 방법은 **결국 헤더를 읽는 것**이다. 즉 Option B는
"Option A + 중복 컬럼 + 정합성 검사"라서 엄격히 더 나쁘다. `daily_records`가 컬럼을 쓰는
것은 필드별로 암호문이 여러 개고 평문 행과 공존해야 하는 사정 때문이며, 채팅에는 그
사정이 없다.

**대가는 명시한다.** 이 방식은 DB를 GLE1 와이어 포맷에 결합시킨다. format_version이
올라가면 마이그레이션이 필요하다. 이는 수용된 비용이며, 모르는 버전을 **거부**하는
것은 fail-closed라 오히려 바람직하다.

## 5. 전송(서버 행) 봉투 · 메타데이터 예산

서버가 보는 것 전부. **여섯 개 — ACTIVE epoch 강제를 넣고도 늘지 않았다** (§4).

| 필드 | 가시성 | 서버가 왜 필요한가 | 암호문으로 옮길 수 있나 | 보존 |
|---|---|---|---|---|
| `message_id` | 평문 | PK. 멱등 재시도의 근거이고 GLE1 AAD에 묶인다 | ❌ 불가 — PK이자 중복 판정 키 | 메시지와 함께 |
| `couple_id` | 평문 | **RLS의 유일한 근거.** 없으면 인가가 불가능 | ❌ 불가 — 인가는 복호화 전에 일어난다 | 커플 삭제 시 CASCADE |
| `sender_user_id` | 평문 | INSERT 시 "본인으로만 쓸 수 있다"와 "본인 메시지만 tombstone" (§9)을 RLS가 강제 | ❌ 불가 — 같은 이유. 2인 커플이라 수신자가 복호화하면 어차피 아는 사실이라 추가 누출 없음 | **`ON DELETE SET NULL`** — 계정 삭제가 공유 히스토리를 지우지 않는다 (§9.4) |
| `ciphertext` | 불투명 | 메시지 본체 (GLE1 blob). 서버는 헤더 네 바이트 구간만 읽고 본문은 열지 않는다 (§4) | — | 메시지와 함께. **`NULL` = tombstone** (§9.2) |
| `ordinal` | 평문 | 표시 순서. 서버가 부여한다 (§7) | ❌ 불가 — 서버가 정하는 값 |  메시지와 함께 |
| `created_at` | 평문 | 행이 도착한 시각. DB가 어차피 아는 값 | ❌ 무의미 — 숨겨도 서버가 안다 | 메시지와 함께 |

### 두 개의 `NULL`, 각각 의미가 하나뿐

이 표에는 `NULL`이 될 수 있는 칸이 둘 있다. 둘 다 **서버 측 전이로만** 생기고, 클라이언트가
INSERT로 만들 수 없으며, 의미가 정확히 하나다. 겹치지도 않는다.

| 칸 | `NULL`의 유일한 의미 | 어떻게 생기는가 |
|---|---|---|
| `ciphertext` | tombstone — 삭제됨 | 발신자의 단방향 delete-for-both UPDATE (§9.2) |
| `sender_user_id` | 작성자가 계정을 삭제함 | FK `ON DELETE SET NULL` (§9.4) |

두 값은 독립이다. 네 조합 모두 뜻이 분명하다 — 예를 들어 둘 다 `NULL`이면 "떠난 사람이
남기고 간, 이후 삭제된 메시지"다.

### 넣지 않은 것과 그 이유

| 넣지 않음 | 이유 |
|---|---|
| `message_type` | "텍스트냐 사진이냐 기록 참조냐"는 **암호문 안**에서 결정. 서버가 알면 대화의 성격이 새는데, 알 필요가 없다 |
| `sender_device_id` | 콘텐츠 암호화가 scope key 기반이라 불필요(§4). 순수한 추가 누출 |
| `key_epoch` / `key_domain` | 전부 GLE1 헤더 안. 서버는 **헤더에서 직접 읽어** ACTIVE 여부를 강제하므로(§4) 컬럼으로 복제할 이유가 없다. 복제하면 행과 헤더가 어긋날 여지만 생긴다 |
| `nonce` / `crypto_version` / `cipher_format` | 전부 GLE1 헤더 안. 서버가 이 값으로 질의하지 않는다 |
| `content_revision` | V1 메시지는 전송 후 불변이고 유일한 예외인 tombstone은 암호문을 **지우지** 새 리비전을 만들지 않는다 (§9.3). 리비전 CAS가 필요한 UPDATE 자체가 없다 |
| `deleted_at` | tombstone은 `ciphertext IS NULL`로 완결된다 (§9.2). 삭제 시각은 서버가 알 필요가 없는 새 메타데이터다 |
| `reply_to` | 암호문 안 (§6) |
| `record_id` / `context` | 암호문 안 (§12). 서버가 알면 "이 기록에 대해 이야기 중"이 샌다 |
| `delivered` / `read` | V1에 읽음 표시가 없다. "전달됨"은 행의 존재가 곧 증거다 |
| 첨부 객체 참조 | 암호문 안. Storage 인가는 경로의 couple 범위로 한다 (§13) |

> `PRODUCT_V3.md` §20이 허용한 "불투명 id, 시각, 순서, 전달 상태" 중 전달 상태는
> **행의 존재 자체**로 충족한다. 나중에 명시적 상태가 필요해지면 반드시 열거형이어야
> 하고 자유 텍스트여서는 안 된다.

### 서버 DB가 통째로 유출되면 무엇이 새는가

암호문은 안전하다. 새는 것: **누가 누구와, 언제, 얼마나 자주, 각 메시지가 대략 몇
바이트인지.** 길이는 `ciphertext = plaintext + 108`이므로 근사 노출된다. V1은 패딩하지
않는다 — 2인 대화에서 길이 분포가 밝히는 것이 제한적이고 비용 대비 이득이 불명확하다.
**수용된 누출**이며, 필요해지면 고정 길이 버킷 패딩이 해법이다.

## 6. 암호화 payload 계약

```text
payload v1
├─ v: 1                     페이로드 스키마 버전
├─ text: string             본문
├─ sent_at: ISO8601         클라이언트가 실제로 쓴 시각
├─ reply_to?: message_id    답장 대상 (불투명 id)
├─ context?:                맥락 참조 (§12)
│    ├─ kind: 'daily_record' | 'talk_about'
│    └─ id: uuid
├─ media?: [media_ref]      P6 예약. V1은 항상 비어 있다 (§13)
└─ ext?: { }                미래 확장 컨테이너 — 모르는 키는 보존하고 무시한다
```

원칙:

1. **`v`를 먼저 둔다.** payload가 진화해도 봉투(GLE1)는 그대로다. 즉 페이로드 변경이
   암호 포맷 변경을 유발하지 않는다.
2. **서버가 몰라도 되는 것은 전부 여기.** 맥락 종류(`kind`)조차 평문이 아니다.
3. **참조는 불투명 id만.** 참조된 기록의 본문을 payload에 **복사하지 않는다.** 사용자가
   직접 인용문을 쓴 경우에만 그 인용문이 `text`의 일부로 존재한다 — 그것은 사용자가
   작성한 내용이지 시스템이 복제한 원문이 아니다.
4. **`ext`로 forward-compat.** 모르는 키를 만난 구버전 클라이언트는 **보존한 채 무시**
   한다. 재전송 시 잃지 않기 위해서다.

### `sent_at`을 왜 암호문 안에 두는가

서버는 어차피 `created_at`(수신 시각)을 안다. 그러나 오프라인으로 새벽 2시에 쓰고 아침
9시에 전송된 메시지의 **작성 시각**은 별개의 정보다 — "새벽 2시에 깨어 있었다"는 생활
패턴이다. 서버가 알 이유가 없으므로 암호문 안에 둔다.

## 7. 메시지 id · 순서 · 멱등성

### id는 클라이언트가 만든다 — 랜덤 UUIDv4

요구사항: 전역 고유, 추측 불가, 생성에 서버 왕복이 없을 것.

- **멱등 재시도.** PK가 클라이언트 id이므로 재시도는 `ON CONFLICT DO NOTHING`이고,
  세 번 눌러도 행은 하나다.
- **낙관적 렌더링에 안정적인 정체성.** "임시 id → 서버 id" 교체가 없다.
- **AAD에 묶인다.** 암호문을 다른 메시지로 옮겨 붙일 수 없다.

UUIDv7이 아니라 v4를 쓴다. v7은 클라이언트 시계를 id에 새기는데, 순서는 어차피 서버가
정하므로 이득 없이 시계 정보만 더 샌다.

### 순서 규칙 (명시)

```text
정렬 = (ordinal ASC)
```

`ordinal`은 커플 단위 단조 증가 정수이고 **서버가 INSERT 시 부여한다.** 유일하므로
tie-breaker가 필요 없다. **클라이언트 시계는 순서에 절대 쓰지 않는다** — 시계 왜곡,
오프라인 지연, 악의적 클라이언트 어느 쪽으로도 순서가 흔들리면 안 된다.

동기화는 `ordinal > 마지막으로 본 ordinal` 한 줄이다.

### UI 정합 규칙

아직 `ordinal`이 없는 로컬 대기 메시지는 **항상 목록 맨 아래**에, 확정된 메시지 뒤에
붙인다. 서버 응답이 오면 그 메시지는 자기 `ordinal` 자리로 이동한다. 결과적으로 내가
보낸 메시지가 잠깐 아래에 있다가 제자리를 찾는데, 이것이 시계를 믿고 잘못된 위치에
확정해 두는 것보다 정직하다. 발신자 시계가 30분 틀려도 표시 순서는 영향받지 않는다.

### 정직한 한계 — Phase 1A는 순서를 인증하지 않는다

`E2EE_PHASE_1A_ARCHITECTURE_V2_1.md` §11: 재설치·복구 이후 서버는 리비전 N−1을 들키지
않고 제공할 수 있고, **누락은 부재와 구별되지 않으며, 독립 객체는 재정렬될 수 있다.**
인증된 히스토리 루트가 없다.

따라서 **다음을 주장하지 않는다**: 악의적 서버의 보류·재정렬을 탐지할 수 있다.
할 수 없다. per-scope 서명 manifest가 Phase 2의 해법이고 여기서 앞당겨 발명하지 않는다.
"E2EE니까 순서도 안전하다"로 읽히면 실제 사용자 기대를 배신하므로 명시한다.

## 8. 생명주기 · 오프라인 · 재시도

**로컬 UI 상태와 서버 지속 메타데이터는 완전히 별개다.** 아래 상태는 전부 클라이언트
안에만 존재하며 서버 행에 컬럼으로 나타나지 않는다.

```text
  local_pending ──encrypt──▶ sending ──ack──▶ sent
        ▲                       │
        └───── retryable ◀──────┘   네트워크/일시 오류
                                └──▶ failed   인가 실패 등 재시도 무의미
```

| 상태 | 뜻 | 서버에 존재? |
|---|---|---|
| `local_pending` | 암호화되어 outbox에 있음, 아직 업로드 안 함 | ❌ |
| `sending` | 업로드 진행 중 | ❌ |
| `sent` | 서버 행 존재 확인됨 | ✅ (행 자체) |
| `retryable` | 일시 오류. 같은 id로 재시도 | ❌ |
| `failed` | 재시도 무의미(비활성 커플 등). 사유를 말한다 | ❌ |

`retryable`과 `failed`의 구분은 기존 `serverErrors.ts` 분류 규칙을 그대로 따른다.

### 오프라인 전송

1. 사용자가 전송 → **id를 즉시 확정**하고 payload를 **로컬에서 암호화**
2. **암호문**을 outbox에 저장 — 기존 기록 outbox는 IndexedDB에 평문을 넣는데
   (DATA_LEGAL §B가 지적), 채팅은 전송 전에 이미 암호화할 수 있으므로 그 문제를
   복제하지 않는다. 큐가 새어도 본문이 새지 않는다
3. UI는 `local_pending`
4. 네트워크 복구 → **같은 id로** 업로드 → 중복은 멱등하게 흡수
5. 서버가 `ordinal`을 부여하면 UI가 제자리로 정렬

### 재시도 한도

지수 백오프(예: 1s → 2s → 4s → … 상한 5분)로 **무기한** 자동 재시도하되, 연속 실패가
임계치를 넘으면 자동 재시도를 멈추고 **수동 재시도 UI**로 전환한다. 메시지를 버리지
않는 것이 핵심이다 — 실시간 유실이 메시지 영구 손실이 되어서는 안 되고, 정상 동기화가
언제든 복구할 수 있어야 한다(§14).

## 9. 수정 / 삭제

### 9.1 수정 — V1 연기. 메시지는 전송 후 불변이다

2인 대화에서 수정의 제품 가치는 낮다(삭제 후 재전송으로 충분). 반면 비용은 실재한다:
암호문 교체는 리비전 단조성이 필요하고, 멀티 기기에서 충돌 해소가 필요하며, 파트너의
히스토리가 조용히 바뀌는 혼란이 생긴다.

> **미래 구현자에게:** 이 계약을 개정하지 않고 ciphertext에 UPDATE를 추가하지 말 것.
> GLE1 AAD가 이미 서버 검증 단조 `content_revision`을 묶고 있으므로 **구조적으로는
> 가능하지만**, 그것은 제품 결정이지 조용히 추가할 구현 디테일이 아니다.

**"불변"의 정확한 범위 (모순처럼 보이는 지점).** 메시지는 전송 후 불변이되, 서버가
허용하는 mutation이 **정확히 하나** 있다: §9.3의 단방향 tombstone 전이다. 그 외에는
어떤 컬럼도 UPDATE되지 않는다. 이것은 예외이지 불변성의 폐기가 아니며, 이 문서가
"불변"이라고 쓸 때는 항상 이 하나의 예외를 포함한 뜻이다.

### 9.2 삭제 — 세 가지를 절대 섞지 않는다

| 동작 | 실제로 일어나는 일 | UI가 말해야 하는 것 |
|---|---|---|
| **내 기기에서 숨기기** | 서버 호출 없음. 로컬 상태만 | "이 기기에서만 안 보이게 했어요" |
| **둘 다에게서 삭제** | **tombstone.** 암호문을 `NULL`로 지우고 행은 남긴다. **원작성자만** 할 수 있고 되돌릴 수 없다 | "서버와 앞으로의 동기화에서 지웠어요. **상대가 이미 본 내용은 되돌릴 수 없어요**" |
| **계정 삭제 / 연결 해제** | 별개 계약. 공유 채팅은 **지워지지 않는다** — §9.4, §10, `PRODUCT_V3.md` §14.4 | 그 문서를 따른다 |

**tombstone을 쓰는 이유 (하드 삭제를 거부한 이유).** 처음에는 "tombstone은 '여기
메시지가 있었다'를 서버에 영구히 남기는 메타데이터"라고 보아 하드 삭제를 택했으나,
두 가지가 그 판단을 뒤집었다:

1. **하드 삭제는 전파되지 않는다.** 이미 동기화해 간 상대는 삭제를 알 신호가 없어
   메시지를 영원히 들고 있게 된다. 순번의 구멍은 *아직 동기화하지 않은* 쪽에만 보인다.
   삭제가 상대 화면에 반영되지 않는 삭제는 삭제라고 부를 수 없다.
2. **published 테이블의 DELETE payload에는 RLS가 적용되지 않는다.** 015가
   `public.events`를 publication에서 제거한 이유가 정확히 이것이다
   (`privacy-access-matrix.md` §F). 하드 삭제는 그 함정에 다시 걸어 들어간다.

그리고 privacy 비용은 처음 생각보다 작다 — **서버는 그 메시지 행의 존재를 이미 알고
있었다.** tombstone이 새로 알려주는 것은 "지워졌다"뿐이다. 암호문은 실제로 사라진다.

#### tombstone의 표현: `ciphertext IS NULL`. 그것뿐이다

이전 판은 tombstone을 도입하면서 **그 상태가 어디에 사는지를 정의하지 않았다.** 확정한다.

- `ciphertext IS NULL` **이 곧, 그리고 오직, tombstone이다.**
- 평문 의미 컬럼을 새로 만들지 않는다. `is_deleted`도, `deleted_at`도, 상태 열거형도 없다.
- **메타데이터 예산은 여섯 개 그대로다** (§5). tombstone은 필드를 추가하지 않는다.

`NULL`이 "malformed" 또는 "pending"을 뜻할 여지는 없다. INSERT 경로가 그 둘을 미리
배제하기 때문이다 — 삽입되는 암호문은 NULL이 아니어야 하고, 길이가 최소
`92 + 16`이어야 하며, magic·format_version·domain·ACTIVE epoch 검사를 통과해야 한다
(§4). 즉 **행이 존재하는데 `ciphertext`가 `NULL`인 유일한 경로는 §9.3의 삭제 전이뿐이다.**

tombstone이 보존하는 것과 잃는 것:

| 남는다 | 사라진다 |
|---|---|
| `message_id` — 클라이언트가 로컬 사본을 지목해 제거하는 열쇠 | **본문 암호문 전체** |
| `couple_id` — RLS가 계속 작동해야 한다 | GLE1 헤더(암호문의 일부다) |
| `sender_user_id` — §9.4의 계정 삭제 규칙을 따른다 | `reply_to`·`context`·첨부 참조 (전부 암호문 안이었다, §6) |
| `ordinal` — 순번에 구멍을 내지 않아 동기화 커서가 깨지지 않는다 | |
| `created_at` — 이미 서버가 알던 값 | |

삭제 시각을 남기지 않는 이유는 명확하다. 클라이언트는 동기화 시점에 tombstone을 보고
바로 처리하므로 시각이 필요 없고, `deleted_at`은 서버가 몰라도 되는 정보를 새로 만드는
순수 추가 메타데이터다. 필요해질 때 계약을 고쳐 추가하는 편이 낫다.

#### 누가 delete-for-both를 할 수 있는가 — **원작성자만**

| 주체 | 내 기기에서 숨기기 | delete-for-both (tombstone) |
|---|---|---|
| 메시지를 보낸 사람 | ✅ | ✅ |
| 받은 사람 | ✅ | ❌ |

수신자가 발신자의 메시지를 원격으로 지울 수 있게 하면, 한쪽이 상대가 **작성한** 관계
히스토리를 일방적으로 파괴할 수 있게 된다. 수신자의 실제 요구("이거 내 화면에서 안
보이면 좋겠다")는 로컬 숨기기로 이미 완전히 충족되며, 그쪽이 훨씬 약한 권한이다.
`PRODUCT_V3.md` §14.4가 공유 객체를 남은 파트너에게 **유지**시키는 방향인 것과도 같은
결의다 — 공유 히스토리는 한쪽이 마음대로 없앨 수 있는 것이 아니다.

데이터 계약으로 옮기면 UPDATE 정책의 `USING`에 `sender_user_id = auth.uid()`가 들어간다.
게이트 C11이 이것을 실제 액터로 증명한다.

#### tombstone은 단방향이다

되살아날 수 없어야 한다. 계약상 전이는 하나뿐이다:

```text
ciphertext = <GLE1 blob>   ──(발신자의 delete-for-both)──▶   ciphertext = NULL
                                                                    │
                          ✗ 역방향 없음 · ✗ 다른 암호문으로 교체 없음 ◀┘
```

RLS만으로 구조적으로 강제된다 — UPDATE 정책의 `USING`이 `ciphertext IS NOT NULL`을
요구하면, **한 번 tombstone이 된 행은 어떤 UPDATE 정책과도 매칭되지 않아 영구히 얼어붙는다.**
`WITH CHECK`은 `ciphertext IS NULL`을 요구해, 허용된 UPDATE가 도달할 수 있는 상태를
tombstone 하나로 고정한다.

나머지 컬럼은 전부 동결이다. `message_id`·`couple_id`·`sender_user_id`·`ordinal`·
`created_at` 중 어느 하나라도 바뀌면 거부한다(트리거 또는 동등한 수단, 게이트 C11).
순번을 다시 쓰거나 작성자를 갈아끼우는 것으로 히스토리를 조작할 수 없어야 한다.

DELETE는 부여하지 않는다. 하드 삭제를 거부한 위 두 이유가 그대로 적용되고, 권한이
없으면 realtime DELETE payload 문제도 아예 발생하지 않는다.

#### tombstone은 어떻게 전파되는가

새로운 실시간 메커니즘이 필요 없다. 기존 content-free invalidation 채널
(`collaboration_invalidations`, §14)이 "이 커플의 채팅에 뭔가 바뀜"만 알리고,
클라이언트가 평소의 재동기화를 돈다. 재동기화 결과에서 해당 `message_id`의
`ciphertext`가 `NULL`인 것을 보고 로컬 표시를 제거하거나 "삭제된 메시지"로 대체한다.
`ordinal`이 남아 있으므로 동기화 커서도 그대로다.

**DELETE realtime payload가 필요 없다** — 이것이 하드 삭제 대비 두 번째 이득이다.
tombstone은 UPDATE이고, UPDATE에는 구독자의 SELECT 정책이 적용된다.

오프라인 상대는 재접속 전까지 로컬 사본을 그대로 갖고 있고, 동기화 후 tombstone을 받아
화면에서 제거한다. **이미 보거나 복사한 내용은 암호학적으로 회수되지 않는다.**

**절대 쓰지 않을 문구:** "상대방 기기에서도 완전히 삭제되었습니다." 강제할 수 없고,
상대가 이미 복호화·캐시·스크린샷했다면 거짓이다 (`AGENTS.md` §10).

상대가 오프라인이면 그동안은 그대로 갖고 있다 — 이것도 숨기지 않는다.

### 9.3 이 절의 전이 요약

| 전이 | 허용 | 누가 | 되돌릴 수 있나 |
|---|---|---|---|
| INSERT (새 메시지) | ✅ | 발신자 본인 | — |
| `ciphertext` → `NULL` | ✅ **유일한 UPDATE** | 원작성자만 | ❌ 영구 |
| `NULL` → 암호문 | ❌ | — | — |
| 암호문 → 다른 암호문 (수정) | ❌ V1 연기 (§9.1) | — | — |
| 그 외 컬럼 UPDATE | ❌ | — | — |
| 행 DELETE | ❌ 권한 없음 | — | — |

### 9.4 계정 삭제 — 공유 채팅은 남은 파트너에게 **유지된다**

이전 판의 §5는 `sender_user_id`의 보존 정책을 "계정 삭제 시 CASCADE"라고 적었다.
**`PRODUCT_V3.md` §14.4와 정면으로 충돌한다:**

> | 커플 소유 / 공유 객체 | 남은 파트너가 있으면 유지된다 |
>
> 키 자료를 유지하는 유일한 이유는 **한 사용자의 탈퇴가 남은 파트너가 정당하게 소유한
> 공유 콘텐츠를 암호학적으로 파괴하지 않게 하기 위해서**다.

채팅 메시지는 전달된 순간부터 **커플이 공동으로 보유한 관계 히스토리**다. CASCADE는
한 사람의 탈퇴로 남은 파트너의 대화 절반을 소멸시킨다. 게다가 `PRODUCT_V3.md` §14.4가 커플 키 자료를
보존하는 이유가 "남은 파트너가 공유 콘텐츠를 열 수 있게 하려고"인데, 열 대상이 이미
지워졌다면 그 보존은 무의미해진다. **정정한다.**

**`sender_user_id UUID REFERENCES auth.users(id) ON DELETE SET NULL`** (nullable).

저장소에 선례가 있다 — `018:10` `assignee_id`, `031:356` `approver_device_id`가 같은
패턴이다. `NULL`은 INSERT로 만들 수 없다(RLS INSERT가 `sender_user_id = auth.uid()`를
요구하므로). 오직 FK 동작으로만 생기고, 의미는 하나다: **작성자가 계정을 삭제했다.**

발신자 표기는 2인 대화라 남은 클라이언트가 로컬에서 해결할 수 있다 — `NULL`이 아니면
"나", `NULL`이면 떠난 사람. 살아있는 계정 접근을 유지할 필요가 없다. 표시 문구는 UI
결정으로 남기되(예: "이전 파트너"), `PRODUCT_V3.md` §14.4가 요구하는 **삭제 확인 화면의 명시** 의무는
그대로다: 어떤 객체가 남는지 사용자에게 알려야 한다.

**하지 않는 것:**

| 금지 | 이유 |
|---|---|
| 작성자를 남은 파트너로 이전 | 히스토리 위조다. 상대가 하지 않은 말을 상대가 한 것으로 만든다 |
| 옛 발신자를 생존자로 덮어쓰기 | 위와 같음 |
| 작성자가 탈퇴했다는 이유로 공유 메시지 삭제 | `PRODUCT_V3.md` §14.4 위반. 남은 파트너의 정당한 콘텐츠다 |
| 계정 삭제를 "내가 보낸 것 전부 delete-for-both"로 처리 | 아래 참조 |

#### 계정 삭제 ≠ delete-for-both

절대 섞지 않는다.

| | A. 개별 메시지 delete-for-both | B. 계정 삭제 |
|---|---|---|
| 범위 | 사용자가 고른 메시지 하나 | 계정 전체 |
| 공유 채팅에 미치는 영향 | 그 한 건이 tombstone (§9.2) | **없다.** 공유 히스토리는 유지된다 |
| 발신자 표기 | 변하지 않음 | `NULL`로 전이 |
| 근거 | 이 문서 §9.2 | `PRODUCT_V3.md` §14.4 |

계정 삭제는 **삭제하는 사용자의 전용 콘텐츠**를 지운다. 공유 채팅은 전용 콘텐츠가
아니다. 계정 삭제가 조용히 "내가 보낸 메시지 전부 삭제"로 동작하려면 제품 계약을
**먼저** 고쳐야 하며, 이 문서는 그것을 승인하지 않는다.

**양쪽 다 탈퇴하면** 남은 파트너가 없으므로 `PRODUCT_V3.md` §14.4의 유지 조건이 성립하지 않는다. 커플
행이 사라지고 `couple_id` CASCADE로 메시지도 함께 사라진다. 정당한 보유자가 아무도 없는
공유 콘텐츠를 남길 이유가 없다.

## 10. 연결 해제 / 재연결

### 해제

- `get_my_active_couple_id()`가 NULL → RLS가 읽기·쓰기·동기화를 전부 닫는다. 커플
  스코프 테이블 전체와 같은 메커니즘이고 채팅만의 예외를 만들지 않는다
- 새 전송 불가, 새 조회 불가, 실시간 접근 중단, active-couple 경로를 통한 새 키 취득 불가
- Phase 1A대로 CSK를 미래 epoch로 rotate
- 클라이언트 동기화 상태에서 채팅을 비운다 — `purgeSharedAccess`가 records/events/
  trips/talkAboutMarks를 비우는 것과 같은 처리. **제품 수준 정리이지 암호학적 보증이
  아니다**
- 이미 상대가 받아 복호화한 것은 회수할 수 없고, 이미 쥔 키는 마법처럼 폐기되지 않는다

### 재연결 — 코드가 이미 답을 정해 두었다

§0에서 확인한 대로 **연결이 해제된 커플은 되살아날 수 없다.** 초대 코드 발행 세 경로가
모두 active 멤버십을 요구하고, 멤버십을 active로 되돌리는 유일한 방법이 초대 소비이기
때문이다.

따라서:

| 경우 | 실제 동작 |
|---|---|
| "같은 관계로 재연결" | **도달 불가능한 상태다.** 그 couple_id로는 코드를 만들 수 없다 |
| 새 페어링 | 항상 **새 couple_id → 새 CSK 스코프**. 옛 채팅은 영원히 넘어오지 않는다 |

즉 **채팅 데이터가 관계 경계를 넘는 경로가 구조적으로 존재하지 않는다.** 이것이 가장
안전한 동작이고, 내가 정책으로 고른 것이 아니라 기존 코드가 강제하고 있다.

> 남은 정리 항목: `disconnect_couple`이 `crypto_pairings`를 `UNLINKED`로 전이시키지
> 않는다 (`CURRENT_STATE.md` #17). 위 분석에 따르면 이것은 **데이터 누출 위험이 아니라
> 상태 일관성 문제**다 — 어차피 되살아날 수 없는 커플의 pairing 행이 실제와 다른
> 상태로 남아 있을 뿐이다. 게이트 C6에서 정리한다.

## 12. 맥락 연결

채팅이 카카오톡과 다른 지점. 세 진입점 모두 **암호문 안 불투명 id**만 쓴다.

| 진입점 | 동작 |
|---|---|
| **기록 상세 → "이 기록에 대해 이야기하기"** | 작성기가 `context: {kind:'daily_record', id}`를 들고 열린다. 수신자는 (아직 권한이 있으면) 정확한 원본으로 이동 |
| **상대방의 오늘 → 대화** | 요약이 아니라 **source record id**를 참조한다. 요약은 파생물이라 진실의 원천이 될 수 없다 |
| **이따 이야기하기 → 대화** | `talk_about_marks`의 `record_id`를 그대로 맥락으로 쓴다. 마크 자체에 평문이 없으므로 복사할 것도 없다 |

이동은 P2에서 만든 내구성 있는 `?record=<id>` 경로를 쓴다 — 새로고침·딥링크에서도
정확한 원본에 도달한다.

### 참조가 사라졌을 때

서버가 참조 무결성을 강제할 수 없다(참조가 암호문 안이므로). 강제할 필요도 없다.
참조는 복호화할 수 있는 클라이언트에게만 의미가 있고, 그 클라이언트는 이미 RLS로
범위가 정해진 기록 접근권을 갖는다.

- **메시지는 그대로 남는다.** 히스토리는 구조적으로 온전하다
- **맥락 카드만 조용히 사라진다.** 자리표시자도, 개수도, "볼 수 없는 항목" 표시도
  만들지 않는다
- 삭제된 경우와 권한이 없어진 경우가 **구별되지 않는다.** 구별되면 "무언가 있다"가
  새고, 그것이 `PRODUCT_V3.md` §6.4가 금지한 존재 누출이다
- 수신 당시 사용자가 정당하게 알게 된 것(예: 메시지 본문에 스스로 쓴 인용) 이상은
  새지 않는다

P3의 `buildTalkAboutTopics`가 이미 이 규칙으로 동작하고 테스트되어 있다.

## 13. 암호화 사진 호환성 (P6)

지금 만들지 않는다. 나중에 재설계가 없도록 인터페이스만 고정한다.

```text
채팅 메시지 → 암호문 payload → media[] → 불투명 media object id
                                          │
                                          ▼
                              Storage: {couple_id}/chat/{object_id}
```

**Storage 인가는 경로의 couple 범위로 한다. 메시지 링크로 하지 않는다.** 링크가 암호문
안이라 서버는 "이 미디어가 당신 커플의 메시지에 붙어 있는가"를 판정할 수 없다. 경로에
`couple_id`를 넣으면 커플 멤버십만으로 인가되고 **서버는 그 미디어가 어느 메시지
것인지 끝내 모른다.** 기존 `couple-media`의 `{couple_id}/{record_id}/{filename}`와
같은 모양이다.

미디어 콘텐츠 키는 canonical 계층을 따른다 — 객체마다 DEK, DEK는 CSK로 wrap. 채팅용
별도 키 계층을 만들지 않는다.

**P6이 만족해야 할 것:** ① 미디어 객체 id가 불투명하고 payload에서 참조 가능할 것
② 경로가 `{couple_id}/…`로 시작해 couple 범위 인가가 가능할 것 ③ 메시지 삭제 시 고아
미디어를 정리할 주체가 정해질 것(링크를 아는 것은 클라이언트뿐 — 게이트 C5).

오디오·영상은 `PRODUCT_V3.md` §12.3대로 **수요 검증 후 Premium Candidate**이며 여기서
구조를 만들지 않는다.

## 14. 실시간 경계

실시간은 **전송 최적화이지 진실의 원천이 아니다.**

**content-free 신호만** 나른다. 기존 `collaboration_invalidations` 패턴(014)을 쓴다 —
"이 커플의 채팅에 뭔가 바뀌었다"만 알리고 클라이언트가 RLS 아래에서 다시 읽는다.
채팅 테이블 자체를 publication에 넣지 않는다.

| 요구 | 왜 만족되는가 |
|---|---|
| RLS 우회 금지 | 데이터를 나르지 않으므로 우회할 것이 없다 |
| 평문 금지 | 암호문조차 나르지 않는다 |
| 유일한 사본이 되지 않을 것 | 원본은 DB 행. 신호는 "다시 읽어라"일 뿐 |
| E2EE 인가 의미 불변 | 재조회가 정상 RLS 경로를 지난다 |
| 지연·중복·유실 내성 | 재조회가 멱등. 이벤트가 메시지를 만들지 않는다. 실시간이 아예 없으면 느려질 뿐 정확성은 그대로 |

직접 publication을 택하지 않은 결정적 이유: **DELETE payload에는 RLS가 적용되지
않는다.** 015가 `public.events`를 publication에서 제거한 이유이고
(`privacy-access-matrix.md` §F), 같은 함정을 반복하지 않는다.

P4에서 실시간을 구현하지 않는다.

## 15. 알림

기본값은 **generic**: `새 메시지가 도착했어요`. 본문·발신자명·기록 발췌·사진 캡션·
감정·관계 맥락을 넣지 않는다 (`PRODUCT_V3.md` §14.3).

푸시 제공자가 침해되어도 얻는 것은 "특정 기기에 특정 시각 알림이 갔다"뿐이다. 다만
**타이밍과 빈도는 제공자에게 실제로 새는 메타데이터**이며, 푸시를 쓰는 한 구조적으로
피할 수 없다. 수용하고 기록한다.

향후 기기 내 복호화로 알림을 풍부하게 만드는 것은 **클라이언트 동작**으로만 가능하며,
서버 평문이 되어서는 안 된다. 이 작업에서 알림 인프라를 만들지 않는다(현재 저장소에
알림 인프라 자체가 전무하다 — §0).

## 19. P5 / P6가 보존해야 할 것

### P4는 채팅을 daily_records E2EE보다 먼저 구현하라는 뜻이 **아니다**

P5는 여전히 **daily_records E2EE 수직 슬라이스**가 우선이다. P4의 목적은 순서를 바꾸는
것이 아니라, 나중에 서로 맞지 않는 scope/epoch/맥락참조/미디어/메시지 의미를 만들지
않게 하는 것이다.

### P5(daily_records E2EE)가 보존해야 할 결정

| # | 결정 | 왜 |
|---|---|---|
| 1 | **CSK 하나를 공유한다** — 기록 전용 스코프를 새로 만들지 않는다 | §3. 새 스코프는 채팅과 라우팅 충돌을 만든다 |
| 2 | **GLE1 `object type`으로 구분한다** | §4. 봉투를 나누면 두 벌이 된다 |
| 3 | **epoch 규칙 동일** — ACTIVE로만 쓰고 RETIRED는 계속 읽는다. `daily_records`는 032의 `key_epoch` 컬럼으로, 채팅은 GLE1 헤더 직접 검증으로 강제한다 — **수단은 다르되 규칙은 같다** | §4 |
| 4 | **맥락 참조는 불투명 id, 해결 실패 시 조용히 사라진다** | §12. 기록↔채팅이 서로를 참조하므로 규칙이 같아야 한다 |
| 5 | **오프라인 큐는 암호문** | §8. 기록 outbox의 평문 문제를 그대로 두면 채팅과 불일치 |

### P6(암호화 미디어)가 보존해야 할 결정

§13의 세 가지: 불투명 media object id · `{couple_id}/…` 경로 기반 couple 범위 인가 ·
고아 미디어 정리 주체 지정. 그리고 미디어 DEK는 CSK로 wrap한다 — 미디어 전용 키 계층을
만들지 않는다.

### C10 — ACTIVE epoch (§4)

실제 DB의 정책·트리거·RPC 동작에 대고 증명한다. **지금 구현하지 않는다.**

1. ACTIVE epoch 헤더를 가진 메시지 INSERT가 **성공**한다
2. RETIRED epoch 헤더를 가진 메시지 INSERT가 **실패**한다
3. 폐기·stale 기기가 자신의 이전 epoch로 **수락되는 유효한 새 메시지를 만들지 못한다**
4. 위조·불일치 라우팅 정보로 epoch 검사를 **우회하지 못한다** — 헤더를 ACTIVE로 위조한
   행은 수락되더라도 **복호화에 실패**함을 함께 보인다 (위협 19)
5. **다른 커플의** ACTIVE epoch를 자기 `couple_id`에 사용하지 못한다

> mutation 검증 필수. 이 저장소는 두 계층이 같은 것을 막아 **바깥 계층이 한 번도
> 실행되지 않은** 공허한 보안 단언을 이미 두 번 출하했다(028 private media, 038 멤버십
> 게이트). epoch 검사도 RLS가 먼저 막아 공허해질 수 있으므로, 검사를 제거했을 때
> 반드시 실패하는지 확인한다.

### C11 — tombstone (§9.2, §9.3)

1. 발신자가 **자기** 메시지를 tombstone 할 수 있다 (`ciphertext IS NULL`이 된다)
2. 수신자가 **발신자의** 메시지를 tombstone **하지 못한다**
3. tombstone을 **되돌리지 못한다** — `NULL` → 암호문 UPDATE가 거부된다
4. `message_id`·`couple_id`·`sender_user_id`·`ordinal`·`created_at`을 **재작성하지 못한다**
5. INSERT 시 `ciphertext = NULL`이 **거부**된다 — `NULL`의 유일한 출처가 삭제 전이임을 고정

### C12 — 계정 삭제 (§9.4)

1. 한쪽이 탈퇴해도 **남은 파트너가 공유 채팅을 계속 읽는다** (행 존재 + 복호화 가능)
2. 탈퇴한 사용자의 **전용** 계정 데이터는 부적절하게 남지 않는다
3. 발신자 표기가 **살아있는 삭제된 계정을 유지하지 않고도** 성립한다 (`NULL` 전이로 충분)
