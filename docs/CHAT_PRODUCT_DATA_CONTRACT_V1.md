## 1. 목적과 비목표

채팅의 가치는 "메신저가 하나 더 생기는 것"이 아니라 **맥락의 연속성**이다.

```text
기록 → 상대방의 오늘 → 정확한 원본 → 반응 / 이따 이야기하기
     → 채팅 → 실제 대화 → 추억으로 축적
```

카카오톡을 대체하려는 것이 아니다. 카카오톡에는 없는 것, 즉 **"이 기록에 대해"**라는
연결이 붙은 대화가 목적이다.

### 비목표 (V1에서 만들지 않음)

그룹 채팅 · 커뮤니티/공개 채팅 · 채널 · 업무용 메시징 · 음성/영상 메시지 · 통화 ·
스레드 · 메시지 전달(forward) · 타이핑 표시 · 접속 상태(presence) · 읽음 표시 ·
사라지는 메시지 · 예약 전송 · 서버 측 검색 · AI 요약 · 봇.

각 항목의 근거는 §15.

## 3. E2EE — 어떤 키가 채팅을 보호하는가

### 결론: 기존 **CSK(couple 도메인)**를 그대로 쓴다. 새 scope를 만들지 않는다.

`PRODUCT_V3.md` §20의 데이터 분류표가 이미 채팅을 CSK로 지정했고, 이 계약은 그것을
확인한다. 근거:

- 채팅은 본질적으로 커플 공유다. 메시지마다 수신자를 고르는 결정이 없으므로 `is_private`
  같은 축이 존재하지 않는다. 기록과 달리 **개인 채팅이라는 것이 없다.**
- 전용 chat scope를 만들면 epoch 상태 기계, 기기별 GLK2 envelope, 기기 폐기 시 rotation을
  전부 한 벌 더 만들어야 한다. 그런데 신뢰 경계가 완전히 같다 — 커플 기록을 읽을 수 있는
  기기는 커플 채팅도 읽을 수 있어야 하는 그 기기다. **분리해서 얻는 보안이 0이다.**
- rotation은 기기 침해가 유발한다. 침해된 기기는 그 기기가 들고 있던 **모든** 도메인을
  들고 있었으므로, "채팅만 rotate" 같은 시나리오는 존재하지 않는다.

### 봉투: GLE1을 그대로 쓴다. 새 포맷 없음.

Phase 1A의 GLE1 AAD는 이미 `protocol, suite, format, domain, epoch, owner, scope,
object type, object id, field id, content_revision`을 묶는다. **`object type`이 있다는
것이 핵심이다** — 채팅 메시지는 새 봉투 형식이 아니라 새 object type 하나다.

이것이 §6이 요구한 "P5/P6이 와도 재설계가 필요 없을 것"의 답이다. 재설계가 필요 없는
이유는 미래를 잘 예측해서가 아니라, **봉투가 이미 object-type-agnostic이기 때문**이다.
P5의 daily_records와 P4의 chat은 같은 GLE1 안의 서로 다른 object type이다.

| GLE1 필드 | 채팅에서의 값 |
|---|---|
| `domain` | `couple` (3) |
| `key_epoch` | 쓰기 시점의 ACTIVE CSK epoch |
| `object type` | 채팅 메시지를 뜻하는 새 상수 |
| `object id` | 메시지 id (§7) |
| `field id` | 본문 |

### Epoch 상호작용

- 새 메시지는 **ACTIVE epoch로만** 암호화한다 (`epochAcceptsWrites`). ACTIVE가 아닌
  epoch로 쓰려는 시도는 거부한다.
- 과거 메시지는 자기 epoch를 봉투 헤더에 들고 있고, RETIRED epoch는 영원히 복호화
  가능하다 (`epochAllowsDecrypt`). **따라서 rotation은 히스토리를 깨지 않는다.**
- rotation 도중 보낸 메시지는 그 순간의 ACTIVE를 참조한다. 대화가 두 epoch에 걸쳐도
  읽기에는 아무 차이가 없다.

### write floor가 필요 없다

`daily_records`는 032의 write floor가 필요했다. 평문 컬럼이 이미 있었고, 암호문으로
올라간 행이 다시 평문으로 내려가는 것을 막아야 했기 때문이다.

**채팅 테이블에는 평문 본문 컬럼이 애초에 없다.** 내려갈 곳이 없으므로 floor도 필요
없다. 태어날 때부터 암호화된 테이블의 이점이다.

## 4. 전송(서버 행) 봉투

서버가 보는 행. **이것이 전부다.**

| 필드 | 평문? | 왜 서버가 알아야 하는가 |
|---|---|---|
| `id` | 예 | PK. 멱등 재시도의 근거이고 GLE1 AAD에 묶인다 |
| `couple_id` | 예 | **RLS의 유일한 근거.** 이것 없이는 인가가 불가능하다 |
| `sender_user_id` | 예 | INSERT 시 "본인으로만 쓸 수 있다"를 RLS가 강제하려면 필요. 2인 커플이므로 수신자가 복호화하면 어차피 아는 사실이라 추가 누출이 없다 |
| `ciphertext` | 불투명 | GLE1 blob |
| `ordinal` | 예 | 표시 순서. 서버가 부여한다 (§7) |
| `created_at` | 예 | 행이 도착한 시각. DB가 어차피 아는 값이다 |

여섯 개. 아래는 **의도적으로 넣지 않은 것들**이고, 각각 왜 필요 없는지가 근거다.

| 넣지 않은 것 | 이유 |
|---|---|
| `key_epoch` 컬럼 | 이미 GLE1 헤더 안에 있다. 클라이언트가 어차피 헤더를 파싱한다. 서버는 epoch로 질의할 일이 없다 |
| `key_domain` 컬럼 | 채팅은 항상 couple이다. 상수를 저장하지 않는다 |
| `sender_device_id` | 콘텐츠 암호화는 scope key로 한다. GLE1 AAD는 owner/scope를 묶지 device를 묶지 않는다. 기기 식별자는 순수한 추가 누출이다 |
| `message_type` | "텍스트냐 사진이냐"는 **암호문 안**에서 결정한다. 서버가 알면 대화의 성격이 새고, 알 필요는 없다 |
| `reply_to` | 암호문 안 (§5) |
| `record_id` / `context` | 암호문 안 (§10). 서버가 알면 "이 기록에 대해 이야기 중"이 샌다 |
| `delivered` / `read` 상태 | V1은 읽음 표시가 없다. "전달됨"은 행의 존재가 곧 증거다 |
| `deleted_at` tombstone | 하드 삭제한다 (§8). tombstone은 "여기 메시지가 있었다"를 영구히 남기는 메타데이터다 |

> `PRODUCT_V3.md` §20은 채팅 서버 메타데이터로 "불투명 id, 시각, 순서, 전달 상태"를
> 허용한다. V1의 "전달 상태"는 **행의 존재 자체**로 충족한다. 나중에 명시적 상태가
> 필요해지면 반드시 열거형이어야 하며 자유 텍스트여서는 안 된다.

### 서버 DB가 통째로 유출되면 무엇이 새는가 (정직하게)

암호문은 안전하다. 새는 것은: **누가 누구와, 언제, 얼마나 자주, 각 메시지가 대략 몇
바이트인지**. 메시지 길이는 `ciphertext ≈ plaintext + 108`이므로 근사적으로 노출된다.
V1은 패딩하지 않는다 — 비용 대비 이득이 불명확하고, 2인 대화에서 길이 분포가 밝히는
것이 제한적이기 때문이다. 이것은 **수용된 누출**이며, 필요해지면 고정 길이 버킷 패딩이
해법이다.

## 5. 암호화 payload 계약

암호문 안에 들어가는 논리 구조. 버전을 붙인다.

```text
payload v1
├─ v: 1                     페이로드 스키마 버전
├─ text: string             본문
├─ sent_at: ISO8601         클라이언트가 실제로 쓴 시각 (§7)
├─ reply_to?: message_id    답장 대상 (불투명 id)
├─ context?:                맥락 참조 (§10)
│    ├─ kind: 'daily_record' | 'talk_about'
│    └─ id: uuid
└─ media?: [media_ref]      P6 예약. V1은 항상 비어 있다 (§11)
```

원칙 세 가지:

1. **`v`를 먼저 둔다.** payload 스키마가 바뀌어도 봉투(GLE1)는 그대로다. 즉 페이로드
   진화가 암호 포맷 변경을 유발하지 않는다.
2. **서버가 알 필요 없는 것은 전부 여기 들어온다.** 맥락 종류(`kind`)조차 평문이 아니다.
   "이 커플이 지금 기록 이야기 중"이라는 사실이 메타데이터로 새지 않는다.
3. **`media`를 지금 자리만 잡아둔다.** P6이 왔을 때 `v: 2`로 올릴 필요조차 없도록
   optional로 예약한다.

### `sent_at`을 왜 암호문 안에 두는가

서버는 어차피 `created_at`(수신 시각)을 안다. 그런데 오프라인으로 새벽 2시에 쓰고
아침 9시에 전송된 메시지의 **작성 시각**은 별개의 정보다 — "새벽 2시에 깨어 있었다"는
생활 패턴이다. 서버가 알 이유가 없으므로 암호문 안에 둔다.

V1 UI는 서버 순번과 서버 시각으로 표시한다. `sent_at`은 나중에 "실제로 쓴 시각" 표시를
붙일 때를 위해 지금부터 실어 둔다.

## 6. 상태 기계

```text
        composeOffline / composeOnline
                    │
                    ▼
              [ local pending ]   ← 암호문으로 큐에 저장
                    │
          upload ciphertext (id 고정)
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   [ delivered ]           [ retryable ]
   서버 행 존재            네트워크/일시 오류
        │                       │
        │                  재시도 (같은 id)
        │                       │
        │                       └──→ delivered (멱등)
        ▼
   [ deleted ]  (양쪽 삭제 시 서버 행 제거)
```

`retryable`과 `failed`를 구분한다. 인가 실패(비활성 커플 등)는 재시도해도 소용없으므로
`failed`로 두고 사유를 말한다 — 기존 `serverErrors.ts`의 분류 규칙을 그대로 따른다.

## 7. 순서·멱등성·오프라인

### 메시지 id는 클라이언트가 만든다

랜덤 UUID(v4). 이유:

- **멱등 재시도.** PK가 클라이언트 id이므로 재시도는 `ON CONFLICT DO NOTHING`이고,
  세 번 눌러도 행은 하나다.
- **낙관적 렌더링에 안정적인 정체성.** "임시 id → 서버 id" 교체가 없다.
- **AAD에 묶인다.** 암호문을 다른 메시지로 옮겨 붙일 수 없다.

시간 순서가 들어간 UUIDv7이 아니라 v4를 쓴다. v7은 클라이언트 시계를 id에 새기는데,
순서는 어차피 서버가 정하므로(아래) 이득 없이 시계 정보만 더 새기게 된다.

### 순서는 서버가 정한다

커플 단위 단조 증가 `ordinal`을 서버가 INSERT 시 부여한다. 표시 순서는 이것이다.

**클라이언트 시계는 순서에 절대 쓰지 않는다.** 시계 왜곡, 오프라인 지연, 악의적
클라이언트 어느 쪽으로도 순서가 흔들리면 안 된다.

동기화는 `ordinal > 마지막으로 본 ordinal` 질의다. 몇 시간 뒤 재접속해도 이 한 줄이다.

### 정직한 한계 — Phase 1A는 순서를 인증하지 않는다

`E2EE_PHASE_1A_ARCHITECTURE_V2_1.md` §11이 명시한다: 재설치·복구 이후 서버는 리비전
N−1을 들키지 않고 제공할 수 있고, **누락은 부재와 구별되지 않으며, 독립 객체는 재정렬될
수 있다.** Phase 1A에는 인증된 히스토리 루트가 없다.

따라서 채팅에 대해 **다음을 주장하지 않는다**: 악의적 서버가 메시지를 보류하거나
순서를 바꾸는 것을 탐지할 수 있다. 할 수 없다. per-scope 서명 manifest가 Phase 2의
해법이고, 여기서 앞당겨 발명하지 않는다.

이것을 숨기지 않고 적는 이유는, 나중에 "E2EE니까 순서도 안전하다"고 잘못 읽히는 것이
실제 사용자 기대를 배신하기 때문이다.

### 오프라인 큐는 암호문을 저장한다

기존 기록 outbox는 IndexedDB에 **평문**을 넣는다 (DATA_LEGAL §B가 지적한 문제). 채팅은
전송 전에 이미 암호화할 수 있으므로(CSK는 인가된 기기에 있다) **큐에 암호문을 넣는다.**
큐가 새어도 본문이 새지 않는다.

## 8. 수정 / 삭제

### 수정 — V1 연기

`daily_records`와 달리 채팅 메시지 수정은 제품 가치가 낮다(2인 대화에서는 삭제 후
재전송으로 충분하다). 반면 비용은 실재한다: 암호문 교체는 리비전 단조성이 필요하고,
불변 리비전 체인은 객체 수와 UI를 늘린다.

**구조적 막다른 길이 아니라는 점이 중요하다.** GLE1 AAD는 이미 서버 검증 단조
`content_revision`을 묶는다. 즉 나중에 수정을 붙이는 것은 제품 결정이지 재설계가
아니다.

### 삭제 — 세 가지를 절대 섞지 않는다

| 동작 | 실제로 일어나는 일 | UI가 말해야 하는 것 |
|---|---|---|
| **내 기기에서 숨기기** | 서버 호출 없음. 로컬만 | "이 기기에서만 안 보이게 했어요" |
| **둘 다에게서 삭제** | 서버 행(암호문) 제거. 이후 동기화에서 사라짐 | "서버와 앞으로의 동기화에서 지웠어요. **상대가 이미 본 내용은 되돌릴 수 없어요**" |
| **계정 삭제 / 연결 해제** | 별개 계약 — `PRODUCT_V3.md` §14.4 | 그 문서를 따른다 |

**절대 쓰지 않을 문구:** "상대방 기기에서도 완전히 삭제되었습니다." 강제할 수 없고,
상대가 이미 복호화·캐시·스크린샷했다면 거짓이다. `AGENTS.md` §10이 같은 규칙을 이미
명령한다.

tombstone을 남기지 않고 하드 삭제하는 이유: tombstone은 "여기 메시지가 있었다"를 서버에
영구히 남기는 메타데이터다. 순번에 생기는 구멍이 유일한 흔적이고, 그 정도는 수용한다.

삭제 전파는 §12의 content-free 무효화 신호로 알린다. **상대가 오프라인이면 그동안은
그대로 갖고 있다** — 이것도 숨기지 않고 적어야 할 사실이다.

## 9. 연결 해제 / 재연결

### 해제

- `get_my_active_couple_id()`가 NULL을 반환 → RLS가 읽기·쓰기·동기화를 전부 닫는다.
  기존 모든 커플 스코프 테이블과 동일한 메커니즘이고, 채팅만의 예외를 만들지 않는다.
- Phase 1A대로 CSK를 미래 epoch로 rotate한다.
- 클라이언트의 동기화 상태에서 채팅을 비운다 — `purgeSharedAccess`가 records/events/
  trips/talkAboutMarks를 비우는 것과 같은 처리다. 이것은 **제품 수준 정리이지 암호학적
  보증이 아니다.** 결심한 공격자가 자기 기기에서 복구하는 것을 막지 못한다.
- 이미 상대가 받아 복호화한 것은 회수할 수 없다. 마법은 없다.

### 재연결 — 여기에 미해결 의존성이 하나 있다

두 경로가 갈린다:

| 경우 | 기대 동작 |
|---|---|
| **같은 커플이 다시 활성화** | 보존된 epoch가 그대로 있으므로 히스토리가 돌아온다 |
| **새 커플로 페어링** | Phase 1A: 이전 couple key 재사용 금지, 완전히 새 scope. 옛 대화는 **영원히** 읽을 수 없다 |

그런데 `CURRENT_STATE.md` #17이 기록한 대로, 현재 `disconnect_couple`은
`crypto_pairings`를 `UNLINKED`로 전이시키지 않는다. **즉 "재연결"이 위 둘 중 어느
경로인지를 판정할 권위 있는 상태가 지금은 없다.**

→ **구현 게이트 G3 (§17).** 채팅 출시 전에 닫아야 한다. 이 계약이 그것을 대신 결정하지
않는다.

## 10. 기록 / `이따 이야기하기` 맥락 연결

목표 동작:

```text
기록 상세 → "이 기록에 대해 이야기하기"
         → 채팅 작성기가 맥락 참조를 들고 열린다
         → 수신자는 (아직 권한이 있다면) 정확한 원본으로 이동할 수 있다
```

### 참조는 암호문 안의 불투명 id다

`context: { kind, id }`는 payload 안에 있다(§5). 서버는 이 메시지가 어떤 기록과 관련
있는지 **모른다**.

"그러면 서버가 참조 무결성을 강제할 수 없지 않은가?" — 강제할 필요가 없다. 참조는
복호화할 수 있는 클라이언트에게만 의미가 있고, 그 클라이언트는 이미 RLS로 범위가 정해진
기록 접근권을 갖고 있다. 참조가 볼 수 없는 것을 가리키면 **맥락 카드만 조용히 사라진다.**

이것은 P3에서 이미 검증된 패턴이다. `buildTalkAboutTopics`는 해결할 수 없는 마크를
자리표시자나 개수로 렌더하지 않고 **소리 없이 버린다** — "볼 수 없는 무언가가 있다"는
표시 자체가 `PRODUCT_V3.md` §6.4가 금지한 존재 누출이기 때문이다. 채팅 맥락 카드도
같은 규칙을 따른다.

대가: 기록이 삭제돼도 서버가 CASCADE로 정리해 줄 수 없다. 죽은 참조를 든 메시지가
남는다. **메시지 자체는 멀쩡하고 맥락 카드만 안 뜬다** — 허용 가능한 실패 방식이다.

## 11. 암호화 사진 호환성 (P6 대비)

지금 구현하지 않는다. 나중에 재설계가 필요 없다는 것만 확보한다.

```text
채팅 메시지 → 암호문 payload → media[] → 불투명 media object id
                                          │
                                          ▼
                              Storage: {couple_id}/chat/{object_id}
```

**Storage 인가는 경로의 couple 범위로 한다. 메시지 링크로 하지 않는다.** 이유가 있다:
링크가 암호문 안에 있으므로 서버는 "이 미디어가 당신 커플의 메시지에 붙어 있는가"를
판정할 수 없다. 경로에 `couple_id`를 넣으면 커플 멤버십만으로 인가되고, **서버는 그
미디어가 어느 메시지 것인지 끝내 모른다.** 기존 `couple-media`의
`{couple_id}/{record_id}/{filename}` 관례와 같은 모양이다.

결과로 생기는 숙제: 메시지가 삭제된 뒤 남는 고아 미디어를 서버가 스스로 못 찾는다.
링크를 아는 것은 클라이언트뿐이므로 삭제 시 클라이언트가 함께 지워야 한다.
→ **구현 게이트 G5 (§17).**

오디오·영상: `PRODUCT_V3.md` §12.3대로 **수요 검증 후 Premium Candidate**. 채팅에서도
V1 범위 밖이고, 여기서 구조를 만들지 않는다.

## 12. 실시간 — 전송 수단이지 보안 진실이 아니다

실시간은 **content-free 신호**만 나른다. 기존 `collaboration_invalidations` 패턴을
그대로 쓴다(014). "이 커플의 채팅에 뭔가 바뀌었다"만 알리고, 클라이언트가 RLS 아래에서
다시 읽는다.

이 한 가지 선택이 아래 네 요구를 전부 만족시킨다:

| 요구 | 왜 만족되는가 |
|---|---|
| RLS를 우회하지 않는다 | 데이터를 나르지 않으므로 우회할 것이 없다 |
| 평문을 나르지 않는다 | 암호문조차 나르지 않는다 |
| 메시지의 유일한 사본이 되지 않는다 | 메시지는 DB 행이 원본이다. 신호는 "다시 읽어라"일 뿐 |
| E2EE 인가 의미를 바꾸지 않는다 | 다시 읽기가 정상 RLS 경로를 지난다 |

실시간 이벤트가 **중복되어도 무해하다.** 재조회는 멱등이고, 이벤트가 메시지를 만들지
않는다. 실시간이 아예 없으면 동기화가 느려질 뿐 정확성은 그대로다.

## 13. 알림

기본값은 **generic**이다: `새 메시지가 도착했어요`. 본문·발신자명·맥락을 넣지 않는다
(`PRODUCT_V3.md` §14.3).

푸시 제공자가 침해되어도 얻는 것은 "특정 기기에 특정 시각 알림이 갔다"뿐이다. 다만
**타이밍과 빈도는 제공자에게 실제로 새는 메타데이터**이며, 이것은 푸시를 쓰는 한
구조적으로 피할 수 없다. 수용하고 기록한다.

이 작업에서 알림 인프라를 만들지 않는다.

## 14. 분석 / AI

채팅 내용은 외부 분석으로 **절대** 나가지 않는다.

허용되는 이벤트는 내용도 의미 분류도 없는 것뿐이다: `chat_open`,
`message_send_success`, `message_send_failed`(오류 코드만).

금지: 본문 · 발췌 · 길이 분포 · 추출된 주제 · 감정 · 관계 해석 · AI 점수 · 대화 빈도를
관계 지표로 집계하는 것.

AI 채팅 분석은 설계하지 않는다 (`PRODUCT_V3.md` §15).

## 16. 자체 검증 — 12가지 경우

계약이 결정적인 답을 갖는지 확인한다.

| # | 상황 | 계약상 동작 |
|---|---|---|
| 1 | 같은 메시지를 3번 재시도 | 클라이언트 id + PK + ON CONFLICT DO NOTHING → 행 하나 |
| 2 | 로컬 전송 후 오프라인 | 암호문이 큐에 남고, 복구 시 같은 id로 재전송 → 멱등 |
| 3 | 수신자가 몇 시간 뒤 재접속 | `ordinal > 마지막 본 값` 질의 하나 |
| 4 | 발신자가 커플 연결 해제 | RLS가 닫힘, CSK rotate, 새 메시지 불가 |
| 5 | 옛 기기에 복호화된 히스토리가 남음 | 회수 불가. 정직하게 그렇게 말한다 (§9) |
| 6 | 새 기기가 나중에 합류 | Phase 1A 기기 프로비저닝으로 CSK epoch envelope를 받고, 보존된 모든 epoch를 복호화 → **히스토리 전체를 받는다** (portable scope key의 의미이자 사용자 기대) |
| 7 | 참조된 기록이 삭제됨 | 맥락 카드만 사라지고 메시지는 멀쩡 |
| 8 | 참조된 기록이 접근 불가 | 7과 **구별 불가능한** 동일 경로. 존재가 새지 않는다 |
| 9 | 미디어는 있는데 맥락이 없음 | 커플 범위 Storage 인가는 유효하지만 렌더할 것이 없다 → 고아 미디어. G5 |
| 10 | 서버 DB 침해 | 암호문은 안전. 누가·언제·얼마나 자주·대략 몇 바이트가 샌다 (§4) |
| 11 | 푸시 제공자 침해 | 내용 없음. 타이밍·빈도는 샌다 (§13) |
| 12 | 실시간 이벤트 중복 | 재조회가 멱등. 이벤트는 메시지를 만들지 않는다 |

추가로: **악의적인 파트너**는 해결 대상이 아니다. 커플이 신뢰 경계이고, 읽을 수 있는
것은 스크린샷할 수 있다. 이것을 기술로 막는다고 주장하지 않는다.
