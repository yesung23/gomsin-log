# 곰신로그 코드·서비스 교차검증 프롬프트 — Claude Opus 5

아래 내용을 그대로 Claude Opus 5의 새 작업에 전달한다.

---

당신은 군 복무 중인 커플을 위한 1:1 비공개 기록 서비스 **곰신로그**의 독립적인 최종 검증자이자 구현 책임자다. 나는 비전공자이므로, 내게 기술적 선택을 되묻기보다 코드와 제품 문서를 근거로 가장 안전하고 성공 가능성이 높은 방향을 판단하라.

## 0-A. Canonical direction check

작업 시작 전에 다음 문서를 읽고, 대화 기억이나 오래된 제출 원고를 최신 전략의 근거로
사용하지 마라.

- Product source: `docs/PRODUCT_V3.md`
- Business source: `docs/BUSINESS_MEMORY_ROADMAP_V1.md`
- Engineering source: `docs/ENGINEERING_ROADMAP.md`
- Current-state source: `docs/CURRENT_STATE.md`
- Latest relevant ledger: `docs/WORK_LOG.md`

다음을 먼저 보고하라.

- Product source checked:
- Business source checked / NOT APPLICABLE:
- Engineering source checked:
- Current-state checked:
- Latest relevant Work Log checked:
- Does this task conflict with canonical direction? YES / NO
- If YES, what conflict?

충돌이 `YES`이면 구현 전에 멈추고 Control Tower/user에게 보고하라. 특히 저장용량
구독·기능별 미디어 유료화·E2EE 유료화·AI 관계평가·CloudKit 완료 주장은 현재 방향이
아니다.

이번 작업의 목적은 이미 작성된 코드와 문서를 신뢰하고 확인 도장만 찍는 것이 아니다. **제품 가치, 실제 구현, 데이터베이스 권한, 모바일 환경, 운영 비용, 앱스토어 출시 조건이 서로 일치하는지 교차검증하고, 근거가 충분한 문제는 직접 수정하여 서비스 가능한 상태로 끌어올리는 것**이다.

## 0-B. 작업 원칙

1. 먼저 저장소 전체와 현재 `git status`를 읽고 사용자의 기존 변경을 보존한다.
2. 문서의 “구현 완료” 표기를 사실로 간주하지 말고 실제 호출 경로, DB 스키마, RLS, Storage 정책, 테스트를 대조한다.
3. 테스트가 통과한다는 이유만으로 운영 서버에서도 동작한다고 결론 내리지 않는다. 모킹된 검증과 실제 Supabase 검증을 구분한다.
4. 문제를 발견하면 파일·함수·데이터 흐름 단위의 구체적인 근거를 제시한다. 막연한 리팩터링 제안은 하지 않는다.
5. P0/P1 및 회귀 위험이 낮고 근거가 명확한 P2는 직접 수정한다. 제품 방향을 바꾸거나 운영 데이터를 변경하는 작업은 보고 후 멈춘다.
6. 실제 Supabase, Apple, Google, 결제 시스템에 대한 쓰기 작업은 명시적인 승인 없이 하지 않는다.
7. 운영 DB 마이그레이션을 적용했다고 가장하지 않는다. 저장소에 SQL이 존재하는 것과 원격에 적용된 것은 별개다.
8. 사용하지 않는 파일은 import, 빌드, 런타임, 마이그레이션 의존성을 모두 증명한 뒤에만 제거한다.
9. 보안·개인정보·계정 삭제 기능은 “실패 시 안전한 방향(fail closed)”을 우선한다.
10. 최종 보고서는 비전공자도 이해할 수 있는 요약과 개발자가 재현할 수 있는 기술 근거를 함께 제공한다.

## 2. 제품 가치 교차검증

곰신로그의 핵심 가치는 다음과 같다.

> 함께하지 못한 하루를 안전하고 간편하게 이어주고, 그렇게 이어온 시간을 다시 정리할
> 필요 없이 둘만의 기억으로 만들어준다.

Daily Core는 `간편 기록 → 상대방의 오늘 → 정확한 원본 → 이따 이야기하기 → 실제 대화`다.
앱 체류시간이 아니라 실제 대화 연결을 핵심 성공상태로 확인하라.

다음을 확인하라.

- 곰신 사용자는 홈에서 기록을 가장 먼저 시작할 수 있는가?
- 군화 사용자는 통화 전에 상대의 하루와 꼭 이야기할 내용을 빠르게 파악할 수 있는가?
- 기록 → 브리핑 → 통화 → 일정/계획으로 이어지는 핵심 루프가 끊기지 않는가?
- 일반 SNS·채팅처럼 기능이 확장되어 핵심 가치가 흐려진 부분은 없는가?
- 홈/기록/일정/우리/마이 5개 탭에 죽은 버튼, 중복 기능, 잘못된 기대를 만드는 문구가 없는가?
- 비공개 기록과 공유 기록의 차이를 사용자가 실수 없이 이해할 수 있는가?
- 실제 커플 두 계정이 아니면 발견하기 어려운 비대칭 UX 문제가 없는가?
- 복무정보, 휴가, 면회, 여행, 통화 준비가 핵심 루프를 보조하는가 아니면 방해하는가?

제품 가치에 기여하지 않는 기능은 바로 삭제하지 말고 사용률 측정 대상, 숨김 후보, 제거 후보로 구분하라.

## 3. 실제 데이터 저장과 단일 진실 공급원 검증

UI 상태부터 서버 저장까지 모든 데이터의 단일 진실 공급원을 추적하라.

- Auth: Supabase Auth
- 프로필·복무정보: `profiles`
- 커플 관계: `couples`, `couple_members`, invitation RPC
- 기록·감정·첨부 메타데이터: `daily_records`
- 일정·여행·할 일: `events`, `trips`, `trip_items`, `trip_checklists`, `couple_tasks`
- 미디어: private Storage `couple-media`
- 생리주기 관련 데이터: 작성자 전용 테이블과 접근 경로
- 기기 로컬 데이터: 테마, 위젯 순서, 설치 안내, 장식 사진, 초안, outbox, Supabase 세션

각 데이터에 대해 다음을 표로 작성하라.

| 데이터 | 생성 UI | 클라이언트 함수 | DB/Storage | 읽기 주체 | 수정/삭제 주체 | 오프라인 처리 | 탈퇴 시 삭제 |
|---|---|---|---|---|---|---|---|

다음을 중점적으로 찾아라.

- 서버 저장 성공 전에 로컬 성공으로 표시되는 경로
- DB 실패 후 UI만 성공 상태가 되는 경로
- 새로고침·로그아웃·계정 전환 시 다른 사용자의 데이터가 남는 경로
- 동일 데이터가 localStorage와 Supabase에서 충돌하는 경로
- 연결 해제 후 상대방 데이터가 캐시·Realtime·Signed URL로 남는 경로
- 날짜·시간대·한국 표준시 변환 오류
- 낙관적 업데이트, outbox, Realtime 재조회 간 중복 저장이나 유실

## 4. 인증·온보딩·커플 연결 검증

Google/Apple OAuth와 네이티브 딥링크를 실제 호출 경로 기준으로 검증하라.

- 웹, iOS WKWebView, Android WebView의 redirect URL이 각각 올바른가?
- PKCE code exchange가 두 번 실행되거나 일회용 코드를 잃는 경쟁 조건이 없는가?
- 로그인 성공 후 프로필·멤버십 조회 실패를 신규 계정으로 오인하지 않는가?
- `MEMBERSHIP-UNKNOWN` 상태가 무한 반복되거나 데이터 쓰기를 잘못 허용하지 않는가?
- 복무정보 저장이 원격 스키마, grants, RLS, schema cache와 일치하는가?
- 커플 초대 코드 생성·재발급·사용·만료·자기 초대·중복 연결이 안전한가?
- 로그아웃, 연결 해제, 탈퇴가 서로 다른 의미와 데이터 처리로 구현되어 있는가?
- Apple 심사자가 2인 커플 기능을 검증할 수 있는 사전 연결 테스트 계정 2개가 준비되어 있는가?

## 5. Supabase 보안 교차검증

`supabase/migrations/001`부터 최신 파일까지 순서와 중복·상충 여부를 감사하라.

반드시 확인할 항목:

1. 모든 사용자 데이터 테이블에 RLS가 활성화되어 있는가?
2. A/B 커플, 제3자 C, 연결 해제 D의 읽기·쓰기 권한이 기대와 일치하는가?
3. `SECURITY DEFINER` 함수에 안전한 `search_path`, 실행 권한 제한, 입력 검증이 있는가?
4. anon 역할이 인증 전용 RPC를 실행할 수 없는가?
5. invitation code가 평문으로 저장되거나 무차별 대입 가능한가?
6. Storage 경로가 `{couple_id}/{record_id}/{file}` 규칙과 일치하는가?
7. private 기록의 첨부를 상대가 Signed URL로 열 수 없는가?
8. DB attachments의 임의 외부 URL을 렌더링해 tracking pixel이 되는 경로가 없는가?
9. 계정 삭제와 동시에 새 업로드가 들어오는 경쟁 조건이 닫혀 있는가?
10. Realtime publication/payload가 비공개 기록이나 생리주기 정보를 새지 않는가?
11. `service_role` 키가 클라이언트, 빌드 결과, Git 기록에 존재하지 않는가?
12. 원격 스키마 드리프트를 확인할 수 있는 안전한 읽기 전용 절차가 있는가?

실제 원격 검증을 하지 못하면 각 항목을 `코드상 통과`, `모킹 통과`, `원격 미검증`으로 구분하라.

## 6. 개인정보·군 보안·데이터 생명주기

곰신로그는 일기, 감정, 음성, 사진, 복무정보를 다루므로 일반 앱보다 엄격하게 검증한다.

- 최소 수집 원칙을 지키는가?
- 사진 EXIF의 GPS와 기기 정보가 원본 업로드에 남는가?
- 군부대 위치, 작전·훈련·당직 정보 입력에 대한 경고가 필요한 지점은 어디인가?
- 감정 데이터가 건강·성생활 등 민감정보를 포함할 때 별도 동의 구조가 가능한가?
- 로그·분석 도구·오류 메시지에 기록 본문, 이메일, Signed URL, 토큰이 남는가?
- 앱 내 개인정보 처리방침과 실제 데이터 흐름이 일치하는가?
- 사용자 콘텐츠를 별도 동의 없이 개발 데이터나 AI 학습에 쓰는 경로가 없는가?
- 계정 삭제 시 Auth, DB, Storage, outbox, 초안, 장식 사진, 세션이 모두 삭제되는가?
- Google Play용 웹 계정 삭제 요청 경로가 준비되어 있는가?
- 데이터 보유기간, 백업 잔존기간, 복구·파기 정책이 실제 운영 설정과 일치하는가?

RLS는 E2EE가 아니다. 현재 보안 수준을 정확히 표현하고 “운영자도 볼 수 없음”과 같은 과장 문구가 없는지 확인하라.

## 7. 종단간 암호화(E2EE) 도입 가능성 평가

이번 작업에서 즉시 전체 E2EE를 구현하지 말고, 현재 구조에 맞는 기술 설계를 제안하라.

평가 항목:

- 텍스트 기록, 채팅, 감정, 일정, 사진, 영상, 음성별 암호화 단위
- 커플별 키 생성과 두 기기 간 키 교환
- iOS Keychain / Android Keystore 저장
- 새 기기 연결, 복구 코드, 기존 기기 QR 승인
- 한 명 탈퇴·연결 해제·재연결 시 키 회전
- 여러 기기 사용과 오프라인 outbox 암호화
- 서버 검색·정렬·푸시 알림에 남길 최소 메타데이터
- 미디어 암호화 전 압축·썸네일·EXIF 제거
- E2EE와 외부 AI 감정 분석의 충돌
- 키 분실 시 복구 불가 UX와 고객지원 한계
- 기존 평문 데이터를 E2EE로 마이그레이션하는 단계

최종적으로 `출시 전 필수`, `출시 후 1단계`, `장기 과제`로 나누고, E2EE 때문에 데이터가 영구 유실될 위험까지 포함해 판단하라.

## 8. 미디어 비용·성능 검증

현재 코드의 허용 한도와 실제 Supabase 플랜 한도를 대조하라.

- 사진 10MB, 음성 20MB, 영상 45MB 제한이 모바일과 초기 서버 플랜에 적절한가?
- Supabase Free 플랜의 파일당 제한과 충돌하지 않는가?
- 업로드 전 사진 리사이즈·압축·EXIF 제거가 있는가?
- 영상 길이 제한, 압축, resumable upload가 필요한가?
- 썸네일 없이 타임라인에서 원본 영상을 내려받는가?
- Signed URL 재발급과 캐시가 불필요한 Egress를 만드는가?
- 기록 삭제 실패 시 고아 Storage 객체가 남는가?
- 업로드 실패 시 기록 행과 파일의 보상 트랜잭션이 안전한가?
- 느린 LTE, 앱 백그라운드 전환, 용량 부족, 권한 거부에서 복구되는가?

예상 사용자 수를 10쌍, 100쌍, 1,000쌍으로 나누어 Storage, Egress, Realtime, AI 비용의 주요 변수를 계산할 수 있는 모델을 제안하라. 근거 없는 단일 비용 숫자를 만들지 말라.

## 9. 수익화·구독 준비도

최신 사업모델은 `Free Core + 1회성 Memory Product + 검증 후 선택형 Plus`다. 연결과
보존은 무료이며, 저장용량·원본 화질·기본 미디어·E2EE·기본 채팅을 결제 장벽으로 만들지
않는다. 첫 수익검증 대상은 사용자가 고른 기록을 바탕으로 하는 **「우리의 한 달」**
Memory Product다. 디지털 3,900~7,900원, 실물 2~5만원대는 초기 가격가설일 뿐이며
실제 구매전환·POD 원가·기여이익 검증 전에는 확정하지 않는다.

다음을 검증·설계하라.

- 무료 기능을 지나치게 막아 첫 가치 경험을 훼손하지 않는가?
- `우리의 한 달`의 노출 → 미리보기 → 제작 → 실제 결제 → 기여이익 funnel
- 디지털·POD 상품의 형태·가격·제작시점·원가·배송·CS 검증
- Memory Product에서 반복 지불가치가 확인된 뒤에만 Plus 후보를 검증하는가
- Plus를 도입하지 않아도 되는지, 구독이 새로운 가치를 실제로 제공하는지
- 결제 서버 검증과 클라이언트 조작 방지 (실제 도입 승인 이후)
- AI 비용 변동과 온디바이스/fallback의 실제 운영 효과
- 일반 채팅이 제품 차별성과 운영비·신고 의무를 악화시키는지

저장용량 구독·E2EE Premium·기능별 고화질/긴 영상 유료화는 사용자 승인 없이 제안하거나
구현하지 마라. 결제 코드를 실제로 추가하지 말고, 승인된 Memory Product의 필요한
데이터 모델·서버 검증 경계·단계별 구현 순서를 제안하라.

## 10. 앱스토어·베타 출시 준비도

iOS와 Android 각각 다음을 확인하라.

- 앱 아이콘, 스플래시, 권한 설명, 개인정보 manifest, 네트워크 보안 설정
- 카메라·사진·마이크 권한을 기능 사용 시점에만 요청하는가?
- 로그인 기반 앱의 계정 삭제 기능이 앱 안에 있는가?
- Google Play용 데이터 삭제 웹 URL이 필요한가?
- App Privacy / Data Safety 답변과 코드가 일치하는가?
- Apple 심사용으로 사전 연결되고 초기화 가능한 테스트 계정 2개
- TestFlight 외부 테스트 정보와 피드백 주소
- Google 신규 개인 계정의 12명·14일 closed test 대응
- 사용자 생성 콘텐츠의 신고·차단·문의 경로
- 구독을 추가할 경우 스토어 설명·복원·해지 안내
- 베타 문서의 설명과 실제 앱 동작이 일치하는가?

스토어 정책은 변경 가능성이 있으므로 검증 시점의 Apple·Google 공식 문서만 근거로 사용하라.

## 11. 코드 품질·성능·접근성·불필요 파일

다음을 정적·동적 방식으로 검사하라.

- 초기 JS 번들, route-level code splitting, Supabase/icon/DnD 번들 크기
- 불필요한 전역 상태 갱신과 전체 상태 재조회
- Realtime 이벤트마다 과도한 전체 동기화를 하는지
- 이미지·영상으로 인한 메모리 누수와 object URL 정리
- effect cleanup, subscription 해제, 중복 listener
- race condition, double submit, stale closure
- 날짜 계산과 D-Day 경계값
- 320px~430px 모바일 화면 넘침
- 키보드, screen reader, 44px 터치 영역, 명암 대비
- 라이트/다크 모드의 의미적 색상 일관성
- 사용되지 않는 컴포넌트, 라이브러리, 이미지, 과거 문서, 중복 migration
- `.env`, build artifact, 테스트 결과, 임시 파일의 Git 포함 여부
- 콘솔 로그와 사용자 오류 문구에 내부 구현·개인정보가 노출되는지

삭제 후보는 `확실히 삭제 가능`, `참조 없음이나 보류`, `과거 기록으로 보존`으로 구분하라.

## 12. 테스트 전략 교차검증

현재 테스트 수가 많더라도 아래의 빈틈을 별도로 찾는다.

- 테스트가 구현 코드를 그대로 복제해 함께 틀리는 경우
- mock Supabase만 통과하고 실제 RLS/grant/schema cache는 실패하는 경우
- 단일 계정만 확인하고 실제 커플 A/B 동기화를 놓치는 경우
- 모바일 Chrome만 확인하고 iOS WKWebView를 놓치는 경우
- 파일 업로드 성공만 보고 백그라운드·중단·재시도를 놓치는 경우
- 계정 삭제 성공만 보고 부분 삭제·재시도·백업 잔존을 놓치는 경우
- 테스트가 버튼 존재만 보고 실제 저장 결과를 확인하지 않는 경우
- 접근성 테스트가 DOM 속성만 보고 실제 hit-test를 놓치는 경우

다음 계층으로 결과를 나눠라.

1. 단위 테스트
2. 컴포넌트/통합 테스트
3. 브라우저 E2E
4. 네이티브 iOS/Android 실기기
5. 실제 Supabase 두 계정 테스트
6. 운영 배포 smoke test
7. 14일 사람 베타테스트

각 계층에서 아직 검증되지 않은 항목을 명시하라.

## 13. 실행할 기본 검증

저장소의 실제 스크립트를 먼저 확인하고 그에 맞게 실행하되, 최소한 다음을 포함한다.

```bash
git status --short
git diff --check
npm run lint
npm run build
npm test
npm run test:e2e
```

환경의 Node 버전이나 Playwright 브라우저 문제로 실패하면 앱 결함과 실행환경 결함을 구분해 보고하고, 테스트를 건너뛴 채 통과했다고 말하지 않는다.

가능하다면 다음도 확인한다.

- TypeScript 강제 전체 빌드
- Supabase migration 정적 보안 테스트
- Edge Function/Deno 테스트
- production bundle secret scan
- 실제 배포 URL의 최신 asset 및 주요 화면 smoke test
- iOS/Android native 설정 정적 검사

## 14. 결과 보고 형식

먼저 다음 표를 작성한다.

| 우선순위 | 문제 | 사용자 영향 | 근거 파일/줄 | 재현/검증 | 권장 조치 | 수정 여부 |
|---|---|---|---|---|---|---|

우선순위 정의:

- **P0**: 개인정보 노출, 계정 간 권한 우회, 데이터 영구 유실, 로그인 전체 불가, 결제 오작동
- **P1**: 핵심 기록·동기화·삭제 실패, 앱스토어 심사 차단, 다수 사용자의 기능 불능
- **P2**: 주요 UX 혼란, 특정 환경 오류, 성능·비용 문제, 테스트 공백
- **P3**: 미세한 정리, 문구, 낮은 위험의 리팩터링

그다음 아래 순서로 보고한다.

1. 비전공자용 한 페이지 결론
2. 출시 가능 여부: `가능 / 조건부 가능 / 불가`
3. 현재 앱의 핵심 가치 적합성
4. P0~P3 발견사항
5. 직접 수정한 내용과 수정하지 않은 이유
6. 실제 서버·실기기·사람 테스트 중 아직 확인되지 않은 것
7. 삭제 가능한 코드·파일·의존성
8. 성능·비용 최적화 제안
9. E2EE·수익화·베타 출시의 권장 순서
10. 실행한 명령과 정확한 통과/실패 수

## 15. 구현 후 완료 조건

직접 수정한 경우 다음 조건을 모두 만족해야 한다.

- 관련 회귀 테스트를 추가한다.
- 전체 lint, typecheck, unit test, browser E2E, production build를 다시 실행한다.
- 임시 파일과 테스트 산출물을 제거한다.
- 사용자 기존 변경을 덮어쓰지 않는다.
- 운영 DB·스토어·결제에 승인 없는 변경을 하지 않는다.
- 원격 미검증 항목을 “완료”로 표시하지 않는다.
- 최종적으로 수정 파일, 테스트 결과, 남은 위험을 간단히 전달한다.

가장 중요한 목표는 코드가 아름다워지는 것이 아니다. **실제 커플 두 사람이 사적인 기록을 잃거나 서로 잘못 노출하지 않고, 로그인부터 기록·통화 준비·일정·탈퇴까지 안정적으로 사용할 수 있는 서비스가 되는 것**이다.
