## 확정된 결정 (2026-08-07)

이 절이 이 문서의 다른 서술보다 우선한다.

1. **군화 기본 홈은 3개다.** 상단 `통화 전 60초`(고정, 제거·순서변경 불가) · 중단 `상대방의 오늘`(`partner_day`) · 보조 `전역 D-Day`(작은 형태).
2. **`partner_day`는 유지한다.** 브리핑의 요약이 무엇을 근거로 만들어졌는지 보여주는 화면이며, `README` §1.4와 `PartnerDayTimelineWidget.test.tsx`의 회귀 방지 의도를 지킨다. 브리핑과 대체 관계가 아니다.
3. **기본값에서 내리는 4개는 코드·기능을 삭제하지 않는다.** `partner_emotion_flow` `partner_emotion_summary` `care_hint` `today_word`. 위젯 추가/관리, 관련 상세 화면, 기록 탭에서 계속 도달 가능해야 한다.
4. **`upcoming_schedule`은 기본값에 넣지 않는다.** 긴급하거나 함께 결정할 일정은 `통화 전 60초`가 우선 노출하고, 전체 일정 위젯은 사용자가 선택해 추가한다.
5. **주기 기능에는 새 보안 설계를 만들지 않는다.** 이미 코드가 강제하는 규칙을 제품 문서에 옮겨 적는 것만 한다(§2.8).
6. **색상 토큰 전면 이관은 이 작업 범위가 아니다.** 별도 PR로 분리한다.
7. **구현하지 않는 것:** 통화 후 결정 캡처, 홈 컴포저 바텀시트화. 둘은 파일럿 검증 항목으로만 남긴다.

## 확정된 시각 개정 (2026-08-20) — Astryx 컴포넌트 기반 + 미디어 우선 — 최우선

이 절은 컴포넌트 기반과 미디어 표현에 관해 이 문서의 다른 모든 절보다 우선한다.
기능·권한·데이터 계약은 바꾸지 않는다.

### 컴포넌트 기반: Astryx

컴포넌트 기반은 **Meta의 Astryx**(`@astryxdesign/core`)다. 단, **토큰의 주인은 바뀌지
않는다.** Astryx가 이 앱의 토큰을 읽도록 매핑하며, 그 반대가 아니다.

- `src/styles/astryx-gomsin.css`가 Astryx의 `--color-*` / `--font-*` / `--radius-*` /
  `--spacing-*`를 이 앱의 OKLCH 토큰으로 가리킨다. 모든 값이 `var()`이므로 dark 블록이
  없고, 있을 수도 없다 — 색을 복사하는 순간 light에서는 맞고 dark에서는 틀리는 두 번째
  사본이 생긴다.
- `@astryxdesign/core/tailwind-theme.css`는 **가져오지 않는다.** 그 파일은
  `--color-card` `--color-muted` `--color-border` `--color-primary`를 선언하는데,
  이는 `index.css`가 이미 소유한 이름이다. import하면 앱 전체의 `bg-card`가 조용히
  Astryx 회색을 가리키게 되고, 아무 테스트도 실패하지 않는다.
- `@astryxdesign/core/reset.css`도 **가져오지 않는다.** Tailwind Preflight와 같은 일을
  전역으로 한 번 더 하는 파일이다.
- layer 순서는 `theme, base, astryx-base, astryx-theme, components, utilities`다.
  `base` 뒤라서 Astryx가 Preflight를 이기고, `utilities` 앞이라서 Tailwind 클래스가
  Astryx 컴포넌트를 이긴다.
- 위 네 가지는 `src/lib/astryxFoundation.test.ts`가 강제한다.

Astryx는 이 앱이 손으로 만들지 않은 것만 가져온다 — `Carousel` `Lightbox`
`AspectRatio` `SegmentedControl`. `Card` `Button` `List` `Badge`는 이 앱 것을 유지한다.

### 미디어가 주인공이다

기존 에디토리얼 타임라인은 미디어에 **68px(≥360px에서 76px) 고정 열**을 줬다. 그 열은
실제 버그의 수정이었지만(절대 배치된 미디어가 높이를 만들지 못해 아래 기록 위로 그려졌다),
사진을 행에서 가장 작은 것으로 만들어 §3.1의 content-first hierarchy를 뒤집었다.

`src/components/media/RecordMediaGallery.tsx`가 이를 대체한다.

| 규칙 | 내용 |
|---|---|
| 폭 | 본문 열 전체. 68px 열은 폐기한다 |
| 비율 | 4:5 세로. 390px에서 다음 기록의 존재가 보이는 가장 긴 크롭 |
| 여러 장 | Astryx `Carousel` + snap. 한 제스처에 한 장 |
| 전체 화면 | Astryx `Lightbox` + zoom. **사진만** |
| 영상 | 인라인 재생. lightbox 오버레이를 씌우지 않는다 — 재생 탭을 먹는다 |
| 음성 | carousel에 넣지 않는다. 사진을 넘기다 소리가 끊긴다 |

**깨면 안 되는 두 규칙.** `[data-testid="record-attachment"]`는 `<button>` 조상을 가질 수
없고(`<video controls>`가 button 안에 있으면 무효 HTML이며 카드 핸들러가 컨트롤 탭을
삼킨다), 확대 버튼은 미디어의 **형제**여야 한다.

### 사진 아카이브 (기록 탭)

기록 탭은 이제 두 개의 렌즈를 갖는다. `타임라인`은 하루를 순서대로 읽고, `사진`은
기간 전체를 훑는다(`MediaArchiveGrid`, 3열 정사각형, 최신 우선). 같은 기록에 대한 두
시점이며 한쪽이 다른 쪽을 숨기지 않는다. §16의 공개 소셜 프로필이 되지 않도록:
개수·랭킹·인기 없음, 정렬은 시간뿐, 본인의 비공개 사진은 표시하되 자물쇠로 표시한다.

### 상단 바

`src/components/ui/AppBar.tsx`. 열두 화면이 각자 손으로 쓴 헤더를 대체한다 —
같은 마크업이 화면마다 다른 padding과 다른 radius로 흩어져 있었다.

### Instagram에서 가져온 것과 가져오지 않은 것

시각 문법만 가져온다: 미디어 우선, 스와이프, 전체 화면 뷰어, 그리드 아카이브,
낮은 chrome, 반투명 상단 바.

**가져오지 않는다** — §16 비목표이며 개정 없이는 도입하지 않는다:
좋아요·조회수·팔로워·공개 피드·알고리즘 정렬·연속 기록·"읽음" 표시·무한 스크롤·광고.
이 앱의 링과 배지는 관계를 점수화하지 않으며, 사진이 커진 것은 사용자의 사진이
앱의 카피보다 중요하기 때문이지 체류 시간을 늘리기 위해서가 아니다(§제품원칙 11).

## 확정된 시각 개정 (2026-08-08)

이 절은 색상·타이포그래피·간격·표면·기록 표현에 관해 아래의 이전 절보다 우선한다. 기능 구조·권한·데이터 계약은 바꾸지 않고 **presentation layer와 interaction density**만 개정한다.

> 미디어 표현(68px 열)에 관한 이 절의 서술은 위 2026-08-20 절이 대체한다.

### 디자인 포지셔닝

**Intimate Editorial Utility — 친밀한 에디토리얼 도구**

곰신로그는 “카드가 많은 커플 대시보드”가 아니라 **상대의 실제 하루를 편집된 타임라인처럼 읽고, 필요한 결정을 즉시 실행하는 content-first relational utility**다.

- `Intimate`: 친밀함은 하트·이모지·캐릭터 반복이 아니라 사용자 사진·목소리·문장과 미세한 색조에서 나온다.
- `Editorial`: 시간·미디어·원문·메타데이터를 명확한 읽기 순서로 편집한다.
- `Utility`: 일정·여행·설정은 장식적 카드보다 스캔 가능한 리스트와 명확한 액션을 우선한다.

시각 레퍼런스는 `docs/design-references/clean-couple-ui-reference.jpg`다. 레퍼런스의 브랜드 자산·캐릭터·카피·화면을 복제하지 않고 **density, hierarchy, rhythm, timeline grammar, restrained color application**만 차용한다.

### 레퍼런스에서 무엇을 가져왔고 무엇을 버렸는가

파일: `docs/design-references/clean-couple-ui-reference.jpg` (5화면 시트: 곰신 홈 · 배려
선택 시트 · 군화 브리핑 홈 · 타임라인 기록 · 내 몸의 리듬). 이 이미지는 삭제하지 않는다.

가져온 것:

| 레퍼런스에서 관찰한 것 | 이 앱에 적용된 형태 |
| --- | --- |
| 기록을 시간 열 → 썸네일 → 문장 순서로 편집한 수직 리듬 | `TimelineRow`의 44px 시간 열 + 68/76px 미디어 열 + 나머지 본문 |
| 반복 항목을 카드가 아니라 divider로 나눈 줄로 표현 | `List.tsx`의 `RowGroup` / `ListRow` / `PressableRow` |
| 강조색을 화면당 한두 곳에만 쓰고 나머지는 잉크와 회색 | 화면당 강조색 2개·주요 CTA 1개 예산, `bg-coral-strong`만 글자를 얹는 채움 |
| 컴팩트한 상단 진입 컨트롤 한 줄 | 곰신 홈의 36px 캡처 런처 (타일 4개를 대체) |
| 그림자 없이 여백과 정렬로만 만드는 구조 | `Card`의 그림자 제거, 16px 반경, 16px 패딩 |
| 얇은 하단 탭바 | 70px → 58px + safe-area, 아이콘 21px, 중복 인디케이터 제거 |

의도적으로 버린 것:

- **캐릭터 일러스트와 하트 장식.** 이 앱의 친밀함은 사용자의 사진·목소리·문장에서 나온다.
  레퍼런스의 커플 일러스트를 흉내내면 콘텐츠보다 장식이 위에 온다.
- **감정을 얼굴 아이콘 5단으로 고르는 방식.** 감정을 척도로 만들면 점수처럼 읽힌다. 이 앱은
  텍스트 칩 + 중성 배경만 쓰고 고정색·수치 축·꺾은선을 금지한다(§감정 표현의 비정량화).
- **`지친 에너지 60%` 같은 정량 게이지.** 상대의 상태를 퍼센트로 환산하는 것은 진단이다.
  본인이 확인한 감정만, 확인한 형태 그대로 보여준다.
- **레퍼런스의 카피와 화면 구성 자체.** 문구·화면 순서·정보 구조는 이 앱의
  `USER_FLOWS`와 `FEATURE_SPEC`을 따른다.

### 핵심 설계 원칙

1. **Content-first hierarchy** — 실제 사진·음성·사용자 원문이 앱 생성 카피·배지·분석보다 높은 시각 위계를 갖는다.
2. **Progressive disclosure** — 홈에는 기록 유형 선택과 핵심 맥락만 노출하고 감정·공개 범위·통화 표시는 선택 뒤 필요한 단계에서 공개한다.
3. **Surface economy** — 카드 수가 아니라 표면의 필요성을 검증한다. 기록·일정·장소처럼 반복되는 데이터는 리스트·타임라인으로 표현한다.
4. **Compact readability** — 글자를 작게 만드는 것이 아니라 과도한 display type, 패딩, 카드 높이를 줄여 정보 밀도를 회복한다.
5. **Visual footprint ≠ hit target** — 아이콘·칩의 보이는 크기와 실제 클릭 영역을 분리한다. 시각적 높이는 컴팩트하게, hit target은 최소 44×44px로 유지한다.
6. **Semantic chroma** — 색은 장식이 아니라 의미다. 코랄=관계·주요 행동, 블루=계획, 민트=완료, 옐로=확인 필요, 빨강=오류·파괴로 고정한다.
7. **Low-chrome interface** — 반복 테두리·그림자·그라데이션·중첩 카드·과도한 pill을 제거하고 여백·정렬·divider로 구조를 만든다.
8. **Authentic over synthetic** — AI가 생성한 것처럼 보이는 균일 카드, 자동 제목, 장황한 추천 카피, 무의미한 감정 배지를 금지한다.

### 디자인 용어와 판정 기준

| 용어 | 이 제품에서의 정의 | 잘못 적용한 상태 |
| --- | --- | --- |
| `Information hierarchy` | 사용자 원문·미디어·시간·다음 행동의 중요도가 크기·배치·대비로 구분되는 상태 | 모든 카드와 제목이 같은 무게로 경쟁함 |
| `Visual density` | 한 뷰포트에서 이해 가능한 정보량. 패딩과 장식을 줄이되 가독성은 유지 | 글자와 터치 영역까지 작게 줄여 빽빽하게 만듦 |
| `Scanability` | 본문을 정독하지 않아도 시간·작성자·상태·행동을 빠르게 찾을 수 있는 성질 | 긴 설명문, 불규칙 정렬, 반복 배지가 탐색을 방해함 |
| `Progressive disclosure` | 처음에는 기록 유형과 핵심 맥락만 보여주고 세부 옵션은 선택 뒤 공개 | 홈에 모든 입력 필드와 설정을 동시에 펼침 |
| `Low-chrome` | 콘텐츠 외의 테두리·그림자·컨테이너를 최소화한 인터페이스 | 모든 정보를 둥근 카드와 그림자로 감쌈 |
| `Semantic color` | 색마다 기능적 의미가 고정되고 텍스트·아이콘이 함께 제공됨 | 분위기를 위해 파스텔 색을 임의로 섞음 |
| `Editorial timeline` | 날짜·시간·미디어·원문을 한 수직 리듬으로 편집한 기록 목록 | 기록을 채팅 말풍선 또는 독립 카드 모음으로 표현함 |
| `Affordance` | 누를 수 있음·선택됨·이동 가능함을 모양과 상태 변화로 예측하게 함 | 장식과 버튼의 형태가 같거나 행 클릭 범위가 불분명함 |

전문 용어는 장식적인 설명이 아니라 **디자인 리뷰에서 합격·불합격을 같은 방식으로 판정하기 위한 공통 언어**로 사용한다.

| `radius-surface` | 16px | 의미가 묶인 카드·시트 |
| `divider` | 1px | 반복 목록 구분; 카드 반복을 대체 |

390px 기준 좌우 gutter는 16~20px, 320px은 14~16px이다. 큰 카드 사이의 빈 공간으로 위계를 만들지 않고 **8/12/16/24px rhythm**으로 일관되게 구성한다.

### 개정 타이포그래피

| 역할 | 크기/행간 | 굵기 | 제한 |
| --- | --- | --- | --- |
| `display` | 26/32 | 700 | D-Day·함께한 일수처럼 화면당 1개 이하 |
| `page-title` | 22/30 | 700 | 화면 제목 |
| `section-title` | 17/24 | 600 | 섹션 제목 |
| `body-emphasis` | 16/24 | 600 | 브리핑 핵심·중요 사용자 원문 |
| `body` | 15/22 | 400 | 기록 본문·설명·입력값 |
| `label` | 13/18 | 500 | 필터·담당자·상태·버튼 라벨 |
| `caption` | 12/16 | 400 | 시간·메타데이터·보조 설명 |

본문을 일괄 16px 이상으로 강제하지 않는다. 핵심 원문은 15~16px로 보호하고 시간·상태 같은 메타데이터는 12~13px을 허용한다. 사용자 글자 확대에서는 reflow로 대응하며 잘림을 허용하지 않는다.

### 손글씨 (2026-08-22 신설)

이 앱에는 두 개의 서체가 있다. **인쇄체(Pretendard)는 앱이 하는 말**이고, **손글씨는 사람이
쓴 글**이다. 종이 일기장이 그렇다 — 양식은 인쇄되어 있고 내용만 손으로 쓴다.

- 서체: **나눔손글씨 세화체** (`Nanum SeHwaCe`, NAVER 2019). Regular 단일 weight.
- 토큰: `--font-hand`. 광학 보정 배율 `--font-hand-scale` 하나를 곱한다.
  **7단계 타입 스케일에 새 단계를 만들지 않는다.**
- `font-weight` 합성 금지. weight가 하나뿐이며 faux bold는 손글씨 획을 뭉갠다.
  강조는 **크기와 여백**으로 만든다.

#### 손글씨를 쓰는 곳 (화이트리스트)

| 쓴다 | 쓰지 않는다 |
| --- | --- |
| 기록 본문 (포스트 캡션 · 스토리 카드 · 기록 상세) | 시간 · 날짜 · 개수 · D-Day 숫자 |
| 요약(편지 카드 · 스토리 속표지)의 문장 | 탭 라벨 · 버튼 · 메뉴 |
| 작성 시트의 입력 필드 | 설정 · 계정 · 프라이버시 화면 전체 |
| 커플 프로필의 한 줄 소개 · 마일스톤 라벨 | **법적 고지 · 동의 · 오류 · 보안 문구** |

**법적 고지 · 오류 · 보안 문구에 손글씨를 쓰는 것은 영구 금지다.** 읽기 어려운 글씨로 쓴
"복구할 수 없습니다"는 정직하지 않다.

#### 2026-08-09에 되돌린 두 이유를 어떻게 해결했나

`src/styles/index.css`의 주석이 그때의 발견을 보존하고 있고, "다시 볼 거면 이 발견에서
시작하라"고 명시한다. 각각에 답한다.

| 그때의 발견 | 이번의 대응 |
| --- | --- |
| **본문 가독성이 인쇄체보다 나빴다** | 그때는 **전면 적용**이었다. 이번에는 본문 화이트리스트에만 쓰고, 광학 보정 배율을 두고, **설정에서 끌 수 있다**(`손글씨 사용`, 기본 켬). 이것은 취향이 아니라 접근성 장치다 |
| **한글 서브셋이 588 kB였다** | **빈도순 unicode-range 분할**로 첫 화면 **81–105 kB**를 실측했다(60자 · 187 슬라이스). 단일 서브셋 파일은 여전히 탈락이다 — KS X 1001 2,350자는 532 kB다. 빌드 도구는 `scripts/fonts/`에 있다 |

#### 지켜야 하는 것

- **자체 호스팅만.** CSP가 `font-src 'self' data:`이며 `cspExternalResources.test.ts`가
  외부 origin을 잡는다.
- `font-display: swap` + Pretendard fallback. 폰트가 늦어도 글은 즉시 읽힌다.
- 슬라이스는 **빈도순**으로 자른다. 코드포인트 순서로 자르면 한 문장의 음절이
  `U+AC00–D7A3` 전역에 흩어져 오히려 더 무거워진다.
- 예산: **첫 화면에서 실제로 내려받는 손글씨 ≤ 150 kB.** 초과하면 적용 범위를 줄인다.

### 표면·컨트롤 규칙

- 화면의 **elevated surface는 최대 3개**, primary CTA는 최대 1개, 강조색은 최대 2개다.
- 카드가 필요한 경우만 `surface + 1px border + 16px radius`를 사용하고 기본 그림자는 쓰지 않는다.
- 반복 데이터 행에 개별 카드를 적용하지 않는다. `list row + divider` 또는 `editorial timeline`을 사용한다.
- primary CTA의 시각적 높이는 48px, 일반 버튼은 40~44px이다. 모든 조작은 hit target 44px 이상을 보장한다.
- pill은 필터·짧은 상태·단일 선택에만 사용한다. 일반 버튼과 모든 메타데이터를 pill로 만들지 않는다.
- 하단 탭은 **56~60px + safe-area**, 아이콘 20~22px, 라벨 11~12px을 목표로 한다. 기존 70px chrome은 시각 밀도 회귀 대상으로 재검토한다.

### 기록의 에디토리얼 타임라인 문법

기본 읽기 순서는 `날짜 → 시간 → 미디어 → 작성자·원문 → 공개/상태 → 보조 행동`이다.

| 영역 | 390px 권장 | 320px 권장 | 규칙 |
| --- | --- | --- | --- |
| 시간 열 | 44~48px | 38~42px | tabular number, caption |
| 미디어 | 72~80px | 60~68px | 사진·영상 썸네일 또는 음성 재생 표면 |
| 콘텐츠 | 나머지 | 나머지 | 작성자 + 사용자 원문 2~3줄 |

- 기록별 자동 생성 제목을 만들지 않는다.
- 감정·`꼭 얘기`·비공개는 작은 secondary metadata이며 사용자 원문보다 앞서지 않는다.
- 사진·음성 없는 텍스트 기록은 미디어 열을 제거하고 시간 다음에 본문을 넓게 쓴다.
- 상세 화면에서만 전체 본문·편집·삭제·파생 정보가 확장된다.

### 이 대조에서 실제로 고친 것

시각 검증은 유닛 테스트가 구조적으로 볼 수 없는 결함 3개를 잡아냈다. 세 개 모두 실제
브라우저에서만 드러났다.

1. **기록 본문 행간이 1.375였다.** `text-body`는 15/22(1.467)를 갖고 있는데 행에 붙은
   `leading-snug`가 그것을 덮어써서, 화면에서 가장 자주 읽히는 사용자 문장이 이 문서가
   정한 1.4 하한 밑으로 내려갔다. jsdom은 유틸리티 클래스의 `line-height`를 계산하지
   않으므로 유닛 스위트 1294개가 전부 통과하는 동안 아무도 볼 수 없었다.
2. **홈 헤더에서 로그인한 사람의 이름이 사라졌다.** 화면 재설계가 `안녕 {myName} ♡`를
   “앱 생성 감성 인사말”로 보고 지웠는데, 인사말과 함께 이름까지 지웠다. 이름은 생성된
   카피가 아니라 사용자 자신의 것이고, 홈에서 어느 계정으로 들어와 있는지 말하는 유일한
   요소였다. 인사말은 지운 채로 두고 이름만 `caption`으로 돌려놓았다.
3. **위젯 추가 버튼의 접근 이름이 바뀌어 있었다.** `새 항목 추가` → `위젯 추가`. 아이콘
   전용 버튼이라 보이는 변화는 없지만, 군화 홈이 편집 가능하다는 사실을 검증하는 유일한
   훅이 끊겼다.

함께 정리한 것: 간격 이탈 3건(40px → 24px)과, `semanticSurfaces`의 “측정 대상 3개 이상”
하한. 후자는 배지·틴트를 절반 가까이 줄인 것이 이 개정의 성과이므로, 하한을 지키려고
틴트를 다시 늘리는 대신 하한을 1로 내리고 그 근거를 테스트 주석에 남겼다.

재발 방지로 유닛 가드 2개를 추가했다. 간격 6단 리듬을 벗어난 padding·margin·gap을
금지하는 가드와, `text-body`/`text-emphasis`에 `leading-snug`류를 붙이는 것을 금지하는
가드다. 둘 다 스캔이 헛돌지 않는지 자기검증 케이스를 함께 갖는다.

## 1. 현재 문서와 화면 구조의 강점

문서 세트가 이례적으로 좋다. 디자인을 새로 하기 위해 지어낼 것이 거의 없었다.

1. **문제 정의가 행동 단위다.** “군 커플용 앱”이 아니라 “곰신이 하루를 다시 설명하는 시간”을 없앤다고 쓰여 있다. 이건 디자인 판정이 가능한 문제 정의다. 대부분의 제품 문서는 여기까지 못 온다.

2. **비대칭을 인정하고 첫 화면을 갈랐다.** 곰신=남기기, 군화=따라잡기. 커플 앱이 보통 “둘에게 같은 화면”을 주고 실패하는 지점을 처음부터 피했다.

3. **북극성 지표가 시간이다.** `브리핑 진입 → 확인 완료 60초 이하`. 체류 시간과 기록 개수를 지표에서 명시적으로 제외했다. 덕분에 “카드를 더 넣자”는 압력에 저항할 근거가 문서에 이미 있다.

4. **`통화 때 꼭 얘기`가 존재한다.** 앱의 추측보다 사용자의 명시 표시를 앞세운 결정(`PRODUCT_REVIEW` §2)은 이 제품에서 가장 좋은 판단이다. AI 없이 우선순위 문제를 푼다.

5. **근거 우선 원칙.** 요약이 원문을 대체하지 않고 원문으로 이동한다. 감정은 작성자가 확인한 것만 공유한다. 진단하지 않는다. 신뢰 설계가 UI 문법에 들어와 있다.

6. **하지 않을 것 목록이 구체적이다.** 채팅, 관계 점수, 연속 출석, 유료 지도 의존, 장문 AI 요약. 디자인이 흔들릴 때 돌아올 기준선이 있다.

7. **디자인 토큰이 이미 견고하다.** `[구현]` OKLCH 기반 시맨틱 토큰, `[data-theme='dark']` 완비, Pretendard 자체 호스팅(dynamic subset), `:focus-visible` 링, `prefers-reduced-motion` 처리. 특히 reduced-motion 처리가 진지하다 — 무한 `wiggle`을 끄고 진입 애니메이션은 1ms로 접고 `animate-spin`은 느리게 남긴 판단은 정확하다. **여기는 손대지 않는다.**

8. **상태 설계표가 있다.** 로딩·빈 화면·오프라인·저장 실패·권한 없음·동기화 지연을 화면별로 흩뜨리지 않고 표로 관리한다(`FEATURE_SPEC` §11).

## 2. 개선할 점

### 2.1 가장 심각: 군화 기본 홈이 60초 규칙을 스스로 깨고 있다

`PRODUCT_PRD` §7.3은 “군화의 핵심 화면에는 우선순위 3개를 넘기지 않는다”고 못박았다. 그런데 `FEATURE_SPEC` §3의 군화 기본 홈은 **위젯 7개**다.

```
통화 전 60초(고정) · 상대방의 오늘 타임라인 · 상대방 마음 흐름
오늘의 요약 · 다정한 한마디 · 오늘의 기록 · 전역 D-Day
```

구현도 그대로 존재한다 — `CallBriefingWidget` `PartnerDayTimelineWidget` `PartnerEmotionWidgets` `CareHintWidget` `TodayLogWidget` `DDayWidget` `UpcomingScheduleWidget`.

더 결정적인 것은 `PRODUCT_REVIEW` §2가 이미 이 문제를 진단하고 “조치: 통화 전 60초에 통합하고 홈 상단에 고정했다”고 적었다는 점이다. **통합은 브리핑 카드 안에서만 일어났고, 중복 위젯은 기본 홈에서 내려오지 않았다.** 진단과 기본값이 어긋나 있다.

군화가 앱을 열면 같은 맥락을 네 번(타임라인·마음 흐름·오늘의 요약·다정한 한마디) 다른 포장으로 읽는다. 60초를 아끼려고 만든 화면이 60초를 쓴다.

### 2.2 60초가 UI에 존재하지 않는다

북극성 지표가 60초인데 화면 어디에도 “이걸 다 보면 끝난다”는 신호가 없다. 남은 항목 수도, 완결 지점도 보이지 않는다. 스크롤이 필요하면 사용자는 “얼마나 더 있나”를 모른 채 읽는다. **완결감 없는 읽기는 실제 소요 시간보다 길게 느껴진다.**

### 2.3 곰신 홈의 인라인 컴포저가 너무 무겁다

`TodayLogWidget.tsx`가 **32.5KB**다. 페이지가 아니라 홈 위젯 하나가 글·사진·영상·음성·반응·감정 확인·공개 범위·통화 표시를 전부 인라인으로 들고 있다.

“긴 일기를 쓰라는 압박 없이”가 목표인데, 홈을 열면 채워야 할 필드가 펼쳐져 있다. 빈 입력창은 그 자체로 과제로 읽힌다. 한 손·짧은 시간·낮은 집중력 조건에서 첫 화면이 폼이면 안 된다.

### 2.4 색이 5색 규칙을 벗어나 있다

`PRODUCT_PRD` §7.2는 코랄=관계, 인디고=계획, 초록=완료, 앰버=확인 필요, 빨강=오류/삭제로 제한한다. 그런데 `index.css`의 다크 모드 블록이 실제 사용 색의 인구조사표다.

```
amber · indigo · blue · emerald · teal · pink · purple · yellow · red · gray
```

컴포넌트들이 시맨틱 토큰(`bg-card` `text-muted-foreground`)을 우회해 원시 Tailwind 팔레트(`bg-pink-50` `bg-teal-100`)를 직접 썼기 때문에, 다크 모드를 살리려고 **팔레트 변수 자체를 재매핑하는 우회로**가 생겼다. 주석이 그 이유를 정직하게 적어두었다.

이건 두 가지 비용을 만든다. 첫째, 화면마다 색 의미가 달라져 “색만으로 말하지 않기” 원칙이 흔들린다. 둘째, 새 컴포넌트를 만들 때마다 재매핑 표를 늘려야 한다.

### 2.5 320px은 문서의 약속일 뿐 검증되지 않는다

`FEATURE_SPEC` §11과 `PRODUCT_PRD` §9가 320px 이상을 보장한다. 실제 e2e 뷰포트는 다음 네 개뿐이다.

```js
{ 390x844 } { 412x915 } { 430x932 } { iphone-393x852 }
```

**320px은 한 번도 렌더링되지 않는다.** 가장 좁은 화면이 가장 깨지기 쉬운데 게이트가 없다.

### 2.6 핵심 루프의 마지막 고리가 끊겨 있다

`기록 → 따라잡기 → 통화 → 일정·여행 반영 → 추억`에서 **통화 → 일정** 구간만 손으로 옮겨야 한다. 통화가 끝난 직후가 결정을 기록할 유일한 순간인데, 그때 앱은 `여기까지 확인` 버튼 하나로 끝난다. `PRODUCT_PRD` §6은 이걸 후보 3번으로 미뤄뒀지만, 루프를 닫지 않으면 일정·여행 탭은 통화와 무관한 별도 생산성 도구로 남는다.

### 2.7 `통화 때 꼭 얘기`가 저장 시점에만 존재한다

이 표시는 이 제품의 우선순위 엔진이다. 그런데 작성 폼 안의 체크박스로만 걸 수 있다. 곰신이 나중에 “아, 이건 통화에서 얘기해야지”라고 생각했을 때 되돌아가 켤 경로가 약하다. `PRODUCT_REVIEW`가 다음 파일럿의 1순위 질문으로 “곰신이 실제로 이걸 쓰는가”를 꼽았는데, 켜는 비용이 높으면 사용률은 낮게 나올 것이고 그러면 잘못된 결론(“표시는 쓸모없다”)에 도달한다.

### 2.8 주기 기능은 보안이 아니라 **제품 문서 범위**의 공백이다

**정정.** 이 문서의 초판은 “권한·빈 상태·오류 설계 대상에서 빠져 있다”고 썼다. 권한 부분은 사실이 아니다. 주기 데이터의 접근 통제는 이 저장소에서 가장 엄격하게 설계된 영역이다. 새 보안 설계를 만들 필요가 없고, 만들어서도 안 된다.

**코드가 이미 강제하는 규칙** (마이그레이션 004 · 011 · 014, `privacy-access-matrix.md`, `AI_HANDOFF` §2-8)

- **원본 주기 기록은 작성자만 접근한다.** `cycle_entries` · `cycle_settings`는 `user_id = auth.uid()` owner-only RLS다. 파트너·제3자 모두 접근 불가.
- **원본 날짜·증상·메모·예측 결과는 상대에게 공유되지 않는다.**
- **공유는 `cycle_support_signals` 하나로만 이뤄진다.** 사용자가 직접 고른 당일 비의료 신호와 선택 메시지만 담고, **원본 주기 데이터와 FK가 없다.**
- **철회·만료 가능하다.** 최대 24시간, 즉시 철회.
- **Realtime publication에 넣지 않는다.** 이유가 문서화되어 있다 — Realtime은 DELETE payload에 RLS를 적용하지 않으므로, 구독만 허용해도 “언제 무엇을 지웠는지”가 새어 나간다(§F). 비공개 일정에서 실제로 발생했던 유출을 같은 방식으로 차단했다.
- **전역 store와 `localStorage`에 raw cycle을 넣지 않는다.**
- 데이터 모듈은 불리언이 아니라 이유를 담은 결과 유니온(`CycleEntryWriteResult`)을 돌려준다.

**실제 공백**은 7개 제품 문서(`SERVICE_OVERVIEW` `PRODUCT_PRD` `FEATURE_SPEC` `USER_FLOWS` `WIREFRAMES` `TRACEABILITY_MATRIX` `PRODUCT_REVIEW`)에 이 기능이 아예 없다는 것뿐이다. 보안·마이그레이션 문서에는 완비되어 있다.

**조치는 하나다.** 위 규칙을 `FEATURE_SPEC`과 IA에 그대로 옮겨 적는다. **새 공유 필드도, 우회 경로도, 새 원칙도 추가하지 않는다.** 디자인이 추가로 정할 것은 화면 문법뿐이다.

- `마이` 안의 **작성자 전용** 섹션. 상대에게는 섹션의 존재 자체를 렌더링하지 않는다 — “권한 없음” 안내조차 데이터의 존재를 암시하므로(`FEATURE_SPEC` §11 규칙과 동일).
- 공유 신호를 켤 때 **무엇이 상대에게 보이는지 그 문장 그대로** 미리 보여준다. “증상과 날짜는 공유되지 않아요”를 추측이 아니라 화면에 쓴다.
- 켜진 동안에는 만료까지 남은 시간과 `지금 철회` 를 항상 같은 자리에 둔다.
- 이 화면에 예측·통계·점수를 표시하지 않는다.

### 2.9 감정 흐름이 “점수화 금지”와 위험하게 가깝다

`EmotionFlowSummarySection` `EmotionFlowInsightCard` `PartnerEmotionWidgets`가 마음의 흐름을 시각화한다. 원칙은 “관계를 점수화하지 않는다”인데, 흐름 그래프는 사용자에게 쉽게 “이번 주 점수”로 읽힌다. 선을 어디에 그을지 시각 문법으로 정해야 한다.

`AI_HANDOFF` §2-3-1이 이미 강한 보호선을 쳐 두었다 — 분석은 확정 감정만 입력으로 받는 순수 파생값이고, 어디에도 저장되지 않으며, 요약문은 고정된 문장 표에서만 나오고 진단 어휘는 테스트로 금지된다(`NON_DIAGNOSTIC_BANNED_TERMS`). 남은 위험은 **시각 표현**뿐이다. 축과 눈금이 있는 꺾은선은 그 자체로 정량화를 암시하므로, 이 문서는 수치 축 없는 **칩 시퀀스**로 표현한다(§3.2).

### 2.10 이미 측정된 시각 결함 4건이 디자인 결정을 기다리고 있다

`AI_HANDOFF` §4.1은 실제 브라우저(390/412/430 × 라이트·다크 × 곰신·군화)에서 측정했지만 **“디자인 결정이 필요해서 의도적으로 고치지 않은”** 항목을 남겨 두었다. 이 문서가 그 결정을 내려야 한다.

## 3. 최종 디자인 콘셉트

### 3.1 키워드

**친밀한 에디토리얼 도구 (Intimate Editorial Utility)**

- **시간을 존중한다** — 화면은 사용자의 시간을 쓰는 비용이다. 카드 하나를 추가할 때 “이건 몇 초인가”를 묻는다.
- **근거가 먼저다** — 앱의 문장보다 상대의 문장이 크다. 요약은 안내판이고 원문이 목적지다.
- **완결감** — 모든 핵심 화면은 “여기서 끝”이 보인다. 무한 스크롤 없음.
- **차분한 따뜻함** — 따뜻함은 색의 채도가 아니라 문장과 여백에서 나온다. 핑크·하트·이모지 남용으로 만들지 않는다.
- **한 손, 아래쪽** — 주요 행동은 엄지 도달 범위(화면 하단 1/3)에 둔다.

한 줄로: **상대의 실제 하루를 에디토리얼 타임라인으로 읽고, 필요한 결정을 즉시 실행하는 조용한 관계 도구.**

### 3.2 색상 원칙

`[구현]` 토큰 세트는 그대로 쓴다. OKLCH·다크 완비·대비 확보가 이미 되어 있다. 바꾸는 것은 **사용 규율**이다.

| 역할 | 토큰 | 쓰는 곳 | 쓰지 않는 곳 |
| --- | --- | --- | --- |
| 관계·기록·주요 행동 | `coral` | 기록하기, 브리핑 강조, 선택 상태 | 계획, 완료 |
| 계획 | `info` / `info-surface` | 일정, 여행, 할 일 | 기록, 감정 |
| 완료·동기화 성공 | `success` / `success-surface` | 체크 완료, 저장됨 | 강조 일반 |
| 나만 보기·확인 필요·지연 | `warning` / `warning-surface` | 비공개 배지, 오프라인, OCR 미확인 | 감정 표현 |
| 오류·파괴 | `destructive` | 실패, 삭제 | 경고, 강조 |
| 본문·표면 | `foreground` `background` `card` `muted` `border` | 그 외 전부 | — |

`[변경]` 규칙 세 개를 추가한다.

1. **원시 팔레트 사용 금지.** `bg-pink-*` `bg-teal-*` `bg-purple-*` `bg-emerald-*` `bg-yellow-*` `bg-blue-*` `bg-indigo-*` `bg-amber-*`를 시맨틱 토큰으로 이관한다. 완료되면 `index.css`의 다크 모드 재매핑 블록을 삭제한다. 그 블록의 존재 자체가 규율 위반의 지표다.
2. **한 화면에 강조색 2개까지.** 코랄과 인디고가 같은 카드에서 동시에 경쟁하지 않는다.
3. **색은 항상 두 번째 신호.** 작성자·공개 범위·상태는 텍스트 또는 아이콘으로 먼저 말하고 색이 보조한다. (`lilac` `mint`는 배경 틴트 전용, 의미 전달 금지)

`[신규]` 감정 색: 감정에 고정 색을 배정하지 않는다. 좋음=분홍, 힘듦=파랑 같은 매핑은 감정을 정량화·서열화하는 인상을 준다. 감정은 **텍스트 칩 + 중성 배경**으로만 표현하고, 강조가 필요하면 굵기와 여백을 쓴다.

`[신규]` 감정 흐름은 **수치 축이 없는 칩 시퀀스**로 그린다. 꺾은선·막대·눈금·퍼센트를 쓰지 않는다.

```
아침 (걱정) → 점심 (그리움) → 저녁 (지침)
```

시간 순서와 전환은 보이지만 “높다·낮다·좋아졌다”는 축이 없다. `PRODUCT_REVIEW` §4의 감정 점수 금지를 시각 문법으로 옮긴 것이다.

#### `--coral-strong` — 명도비 결정 (§2.10 #1)

`[신규]` **토큰 1개를 추가한다.** 화면마다 색을 더하는 것이 아니라 토큰 파일 한 곳에서 정의한다.

현재 `--coral` 은 `oklch(0.78 0.12 22)` 로 밝다. 여기에 흰 글씨를 얹으면 실측 2.01~2.09:1로 AA(4.5:1)를 크게 못 채운다. 그런데 `--coral` 은 약 100곳에서 쓰이고 대부분은 **틴트·테두리·선택 표시**여서 명도비 기준이 적용되지 않는 용도다. 그래서 밝은 코랄을 없애는 대신 **글자를 얹는 용도만 분리**한다.

```
--coral         유지  틴트, 테두리, 선택 표시, 좌측 레일, 장식        (글자 없음)
--coral-strong  신규  글자를 얹는 채움 — primary 버튼, 배지 배경      (흰 글씨 AA 충족)
```

라이트/다크 각각의 실제 값은 구현 시 canvas 실측으로 확정한다(`AI_HANDOFF` §4.1이 지적한 대로 `oklch()` 문자열 파싱은 틀린 값을 낸다). 목표는 흰 글씨 기준 **라이트 ≥ 4.5:1, 다크 ≥ 4.5:1**.

대안으로 “코랄 배경 + 네이비 글씨”도 검토했다. 명도비는 통과하지만 두 브랜드 색이 한 버튼에서 경쟁해 위계가 흐려지고, 다크 모드에서 네이비 글씨가 배경과 붙는다. 채택하지 않는다.

이 토큰 추가는 §2.10 #1의 결정이며, **색상 토큰 전면 이관(별도 PR)과는 다른 작업**이다. 이관은 원시 팔레트를 시맨틱 토큰으로 옮기는 일이고, 이것은 접근성 결함 수정이다.

#### 하단 영역 스택 (§2.10 #3)

`[신규]` 겹침을 없애는 유일한 방법은 **순서와 오프셋을 한 곳에서 정하는 것**이다.

```
아래에서 위로
  탭바                     70   (safe-area inset 별도)
  오프라인/동기화 배너      44   탭바 바로 위, 겹치지 않음
  플로팅 CTA               52   배너 위 12px
```

배너가 있을 때 CTA가 위로 밀린다. 배너를 CTA 위에 띄우거나 같은 층에 두는 현재 구조가 18px 겹침의 원인이었고, 배너를 더 올리면 36px로 악화된다는 측정도 같은 원인을 가리킨다. **배너와 CTA는 같은 하단 스택의 형제**여야 하고, 서로를 밀어야 한다.

### 3.4 아이콘 원칙

### 3.6 카드

카드는 비싸다. 테두리 하나가 “읽을 것이 하나 더 있다”는 신호다.

- 화면당 elevated surface 3개 이하. 반복 기록·일정·장소 행은 카드 수에 포함하기 전에 카드 자체를 사용하지 않는 것을 기본으로 한다.
- 배경 `card`, 테두리 `border` 1px, radius 16px, 그림자 없음. 그림자는 시트·모달 등 띄운 층에만.
- 카드 안에 카드 금지. 내부 구분은 여백과 얇은 구분선.
- 모든 카드에는 제목이 있다. 제목 없는 카드는 카드가 아니라 문단이다.
- 반복 콘텐츠는 `list row + divider` 또는 `editorial timeline`으로 표현한다.

### 3.7 탭

`[구현]` 하단 5탭 유지: `홈 · 기록 · 일정 · 우리 · 마이`

- **시각 높이 56~60 + safe-area inset.** 아이콘 20~22 + 라벨 11~12px. 각 탭의 hit target은 44px 이상이며 **라벨은 항상 표시**한다.
- 선택 상태는 `coral` + 굵기 + 라벨 색. 색만으로 구분하지 않는다.
- 탭 전환은 상태를 보존한다. 기록 작성 초안은 탭을 넘어도 유지된다. `[구현]`
- 일정↔여행은 탭이 아니라 일정 화면 상단의 세그먼트. `[구현]` `PlanSectionNav`

### 3.8 바텀시트 vs 모달

`[신규]` 이 구분을 규칙으로 고정한다. 현재는 혼용 가능성이 열려 있다.

**바텀시트** — 생성·편집·선택. 한 손 도달이 목적.
- 스와이프로 닫힘, 배경 탭으로 닫힘
- 상단에 grabber, 제목, 우상단 닫기(44px)
- 최대 높이 90dvh, 내부 스크롤, 액션 바는 하단 고정
- `animate-slide-up` 사용 `[구현]`
- 예: 기록 컴포저, 위젯 추가, 일정 생성, 장소 추가, 감정 편집

**중앙 모달** — 파괴적 확인 **전용**.
- 스와이프로 닫히지 않음, 배경 탭으로 닫히지 않음
- 결과를 자연어로 먼저 설명 → 그다음 버튼 `[구현]`
- `[취소]`가 왼쪽·기본 포커스, `danger`가 오른쪽
- 예: 계정 삭제, 연결 해제, 기록 전체 삭제

**어느 쪽도 아닌 것**: 정보 전달만 하는 팝업은 만들지 않는다. 인라인 배너 또는 토스트로 처리한다. `[구현]` `OfflineBanner` `CoupleStatusBanner` `SharedSyncBanner`

시트/모달은 **2단 중첩 금지.** 시트 안에서 다음 시트를 열어야 하면 흐름이 잘못 설계된 것이다. 유일한 예외는 시트 안의 파괴적 확인 모달.

### 5.1 군화 홈 — 스크롤 없이 완결

`[변경]` **기본 위젯을 7개 표면에서 3개로 줄인다.** 확정된 결정 §1~4에 따른다.

**삭제가 아니다.** 코드·기능은 전부 유지하고 도달 경로를 남긴다.

| 위젯 | 기본값에서 내린 뒤 어디서 보나 |

### 5.2 브리핑과 타임라인이 같은 내용으로 보이지 않게 하는 방법

같은 기록을 두 카드가 다루기 때문에 시각 문법으로 역할을 분리해야 한다. 문구로 설명하지 않고 **형태로** 구분한다.

| | 통화 전 60초 | 상대방의 오늘 |
| --- | --- | --- |
| 역할 | 판단 — 무엇을 먼저 물을지 | 근거 — 실제로 무엇이 있었는지 |
| 정렬 | 우선순위 순 (시각 아님) | **시각 순** |
| 항목 수 | 최대 3, 고정 | 그날 전체 |
| 각 항목 | 이유 배지 + 발췌 2줄 | 시각 + 미디어 + 본문 |
| 미디어 | **표시하지 않음** (썸네일 없음) | 썸네일·재생 컨트롤 표시 |
| 좌측 | 이유 배지 `● 꼭 얘기` | **시각 레일** `09:20 │` |
| 배경 | `card` + 좌측 코랄 4px 레일 | `card`, 레일 없음 |
| 앱이 쓴 문장 | 있음 (먼저 살필 마음, 첫 질문) | **없음.** 상대의 문장만 |
| 액션 | `여기까지 확인` (완결) | `전체 보기 ›` (탐색) |

가장 강한 구분은 두 가지다. **미디어는 타임라인에만 나온다** — 브리핑은 텍스트 발췌만 다루므로 두 카드는 첫눈에 다른 물건으로 보인다. 그리고 **앱이 생성한 문장은 브리핑에만 있다** — 타임라인에는 상대가 쓴 것만 놓인다.

좌측 레일도 다르다. 브리핑은 이유 배지가, 타임라인은 시각이 왼쪽을 차지한다. 왼쪽 열만 훑어도 “우선순위 목록”과 “시간표”가 구분된다. 텍스트를 읽지 않아도 정보 우선순위를 이해할 수 있어야 한다는 원칙의 구현이다.

#### 설계 결정

**`● 배지`가 왜 항목마다 있나** — 이 항목이 왜 상위 3개에 뽑혔는지 알려준다. `꼭 얘기`(곰신의 명시 표시)와 `힘들었어`(반응값)와 `결정 필요`(일정/여행)는 신뢰 수준이 다르다. 군화는 “곰신이 직접 표시한 것”을 먼저 물어야 한다. 배지가 없으면 세 항목이 동등해 보이고, 우선순위 엔진의 판단이 UI에서 사라진다. `FEATURE_SPEC` §6의 7단계 우선순위가 화면에 드러나는 유일한 지점이다.

**발췌는 2줄 고정** — 3줄이면 3개 항목이 한 화면에 안 들어온다. 2줄이면 “더 있다”는 감각이 남아 `›`(원문 이동)의 동기가 된다. 요약이 원문을 대체하지 않는다는 원칙과 물리적으로 일치한다.

**`결정 필요`를 4번째 슬롯이 아니라 3개 안에서 경쟁시킨다** `[신규]` `[검증]` — `PRODUCT_PRD` §6 후보 5번. 슬롯을 늘리면 3개 규칙이 깨진다. 대신 일정·여행의 `통화 때 꼭 얘기` 항목을 기록과 **같은 우선순위 큐에 넣는다.** 오늘 정해야 할 결정이 어제의 좋은 소식보다 통화에서 급하다.

**`더 보기`는 접힌 상태가 기본** — 마음 흐름·오늘의 요약·다정한 한마디를 여기에 넣는다. 시간이 있는 군화는 펼치고, 3분 남은 군화는 무시한다. **정보를 없애지 않고 시간 예산만 사용자에게 넘긴다.**

**`여기까지 확인`이 스크롤 없이 눌린다** — 북극성 지표가 이 버튼의 도달 시간이다. 버튼이 스크롤 아래에 있으면 지표가 측정하는 것은 사용자의 이해 시간이 아니라 스크롤 시간이 된다. 우하단, 엄지 도달 범위.

**새 맥락이 없을 때** — 빈 카드를 보여주지 않는다.
```
통화 전 60초
새로운 맥락이 없어요
어제 21:40 이후로 공유된 기록이 없습니다.
바로 안부를 물어도 좋아요.
```
`FEATURE_SPEC` §11의 “실패처럼 보이지 않는 빈 상태 + 다음 행동 1개” 규칙. `USER_FLOWS` §4의 마지막 분기와 일치.

### 5.3 곰신 홈 — 1탭으로 시작

`[변경]` 인라인 폼을 **compact capture launcher**로 바꾼다. 런처는 대형 기능 타일이 아니라 한 줄 퀵 액션이며, 다음 영역에서 사용자가 실제로 남긴 기록을 즉시 보여 준다.

```text
┌──────────────────────────────────────┐
│ 곰신로그                        알림 │ 46
│ 좋은 저녁이에요, 민지님              │ 32
├──────────────────────────────────────┤
│ 오늘 어떤 순간이 있었나요?           │ 28
│ [글]  [사진·영상]  [음성]  [반응]    │ 44
│ 어제 이어 쓰던 글이 있어요  이어쓰기 ›│ 44  (초안 있을 때만)
├──────────────────────────────────────┤
│ 오늘의 기록                 전체 보기 │ 36
│ 14:20  ▣  카페에서 본 노을           │ 64
│        민지 · 사진 1장                │
│──────────────────────────────────────│
│ 18:10  ♪  오늘 훈련 끝! · 0:14       │ 64
│        현우 · 음성                    │
├──────────────────────────────────────┤
│ 전역 D-142 · 다음 면회 D-8           │ 52
├──────────────────────────────────────┤
│  홈    기록    일정    우리    마이   │ 56+safe
└──────────────────────────────────────┘
```

각 런처의 **visual footprint는 32~36px**, 행 전체 **hit target은 최소 44px**로 분리한다. 탭하면 해당 모드로 전체화면 바텀시트 컴포저가 열린다. 홈에서 만든 앱 문구나 요약이 실제 기록보다 앞서지 않는다.

#### 컴포저 시트

```text
┌──────────────────────────────────────┐
│ ═══                              ✕  │ 56
│ 오늘의 기록                          │
├──────────────────────────────────────┤
│                                      │
│ 무슨 일이 있었어?                    │
│ (입력 영역)                          │
│                                      │
│ [사진] [영상] [음성]  ← 여기서도 추가│
│                                      │
│ 마음                                 │
│ (좋았어) (이런 일이) (힘들었어)      │
│ (네 생각났어)              + 직접    │
│                                      │
├──────────────────────────────────────┤
│ 우리에게 공유 ▾      ☐ 통화 때 꼭 얘기│ 56
│ [            기록하기              ] │ 60
└──────────────────────────────────────┘
```

#### 설계 결정

**왜 폼을 홈에서 뺐나** — 빈 입력창은 과제다. 홈을 열 때마다 “써야 한다”는 압박을 만든다. 목표는 “긴 일기를 쓰라는 압박 없이”인데 현재 구조는 정확히 그 압박을 첫 화면에 놓는다. 타일은 **선택**이고, 선택은 부담이 낮다. `PRODUCT_PRD` §7.5 “입력보다 선택”을 홈에 적용한 것이다.

**왜 4개 타일인가** — 3개면 `반응`이 빠지는데, 반응(좋았어·힘들었어 등)은 **가장 낮은 비용의 기록**이고 브리핑 우선순위에 직접 들어간다. 시간이 30초뿐인 곰신에게 남길 방법이 있어야 한다. 5개는 320px에서 타일 폭이 56px 아래로 내려간다.

**공개 범위와 `통화 때 꼭 얘기`가 저장 버튼과 같은 시야에 있다** — 이 두 결정은 실수하면 되돌리기 어렵다(비공개로 쓸 걸 공유했다면 이미 상대가 봤다). 스크롤 위쪽에 두면 저장 순간에 확인할 수 없다. 하단 고정 바에 `기록하기`와 함께 둔다.

**공개 범위 기본값은 `우리에게 공유`, 표시는 항상 명시** — 기본값을 숨기면 사용자는 자기가 무엇을 선택했는지 모른다. `나만 보기`를 고르면 `warning` 배지로 저장 후에도 계속 보인다.

**이어쓰기 줄은 초안이 있을 때만** `[구현]` — 초안 보존은 이미 되어 있다. 보이지 않으면 사용자는 초안이 있는지 모르고 처음부터 다시 쓴다.

## 6. 핵심 화면 UI 명세

> 이미지 시안 대신 픽셀 예산과 토큰이 명시된 와이어프레임으로 제공한다. 기준 390×844, 다크 모드는 토큰 자동 대응. 실제 화면 구현이 필요하면 이 명세대로 React/Tailwind로 만들 수 있다.

### 6.1 로그인

```text
┌──────────────────────────────────────┐
│                                      │
│                                      │
│              곰신로그                │ display
│   답장이 늦어도, 오늘의 순간은       │ body
│         놓치지 않도록                │
│                                      │
│                                      │
│  [  Google로 계속하기            ]   │ 52  secondary
│  [  Apple로 계속하기             ]   │ 52  secondary
│                                      │
│  둘러보기                            │ ghost
│                                      │
│  계속하면 이용약관과 개인정보        │ caption
│  처리방침에 동의합니다               │
└──────────────────────────────────────┘
```

주요 행동을 화면 하단 1/3에 배치. 소셜 로그인은 `primary` 코랄을 쓰지 않는다 — 브랜드 색을 남의 인증 버튼에 얹으면 어느 것이 앱의 주요 행동인지 흐려진다.

### 6.2 온보딩 (한 화면 한 결정)

```text
┌──────────────────────────────────────┐
│ ‹                            2 / 4  │ 52
│                                      │
│ 어느 쪽이신가요?                     │ title
│                                      │
│ ┌──────────────┐ ┌──────────────┐   │
│ │     곰신     │ │     군화     │   │ 88
│ │ 기다리는 사람│ │ 복무 중인 사람│  │
│ └──────────────┘ └──────────────┘   │
│                                      │
├──────────────────────────────────────┤
│ [              다음               ]  │ 52
└──────────────────────────────────────┘
```

`WIREFRAMES` §4의 “한 화면에 하나의 결정”을 지킨다. 현재 와이어프레임은 역할과 복무 상태를 같은 화면에 둔다 — `[변경]` 분리한다. 역할 선택이 이후 질문의 내용을 바꾸기 때문이다(곰신에게 자기 군종을 묻지 않는다).

진행 표시는 `2 / 4` 텍스트. 점 인디케이터는 320px에서 좁고 스크린리더에 무의미하다.

### 6.3 커플 연결

```text
┌──────────────────────────────────────┐
│ ‹                            4 / 4  │
│ 둘만의 공간을 연결해요               │ title
│                                      │
│ [       새 공간 만들기            ]  │ 52 primary
│                                      │
│ ────────── 또는 ──────────          │
│                                      │
│ 초대 코드 6자리                      │ label
│ ┌───┬───┬───┬───┬───┬───┐          │ 56
│ │ 3 │ 8 │ 1 │ 2 │   │   │          │
│ └───┴───┴───┴───┴───┴───┘          │
│ ⚠ 만료된 코드예요. 상대에게          │ caption warning
│   재발급을 부탁해 주세요.            │
│                                      │
│ [           참가하기              ]  │ 52
└──────────────────────────────────────┘
```

오류는 입력 바로 아래, 입력값 유지. `USER_FLOWS` §2 규칙. 숫자 입력은 `inputmode="numeric"`, 자동 포커스 이동, 붙여넣기 시 6칸 분배.

### 6.4 기록 탭

기록은 메신저 말풍선이나 반복 카드가 아니라 **editorial timeline**으로 표현한다. 읽기 순서는 `시각 → 미디어 → 원문 → 작성자·공개 범위`이며, 앱이 생성한 제목이나 감정 문구가 사용자의 원문보다 먼저 나오지 않는다.

```text
┌──────────────────────────────────────┐
│ 기록                        2026. 8 │ 46
│ ‹   일  월  화  수  목  금  토    ›  │ 56
│      3   4   5  [6]  7   8   9      │
├──────────────────────────────────────┤
│ [전체]  사진  영상  음성  글          │ 40 필터
├──────────────────────────────────────┤
│ 8월 6일 화요일                       │ 28 date label
│ 14:20 ┊ ▣  [사진 썸네일 72×72]       │
│       ┊    카페에서 본 노을이 예뻤어 │ 88
│       ┊    민지 · 사진 1장 · 우리    │
│───────┼──────────────────────────────│
│ 18:10 ┊ ♪  오늘 훈련 끝!             │ 72
│       ┊    현우 · 음성 0:14 · 우리   │
│───────┼──────────────────────────────│
│ 20:05 ┊    오늘은 조금 쉬고 싶어      │ 72
│       ┊    민지 · 글 · 🔒 나만 보기   │
└──────────────────────────────────────┘
```

작성자 구분은 **이름 텍스트 + 작은 semantic marker + 메타데이터**로 제공한다. 대화처럼 좌우로 흔들지 않기 때문에 시선의 수직 흐름과 날짜별 scanability가 유지된다. 색약·흑백 환경에서도 이름으로 구분된다.

`나만 보기`는 `warning` 배지 + 자물쇠 + 텍스트. 작성자에게만 렌더링. `[구현]`

브리핑에서 진입하면 해당 **timeline row**로 스크롤하고 `record-highlighted` 펄스 2회(reduced-motion에서 1회)를 제공한다. `[구현]`

### 6.5 일정

```text
┌──────────────────────────────────────┐
│ [일정]  여행                      +  │ 52
│ ‹        2026년 8월              ›   │
│  일 월 화 수 목 금 토                │ 72
│         6  7 [8] 9 10 11            │
│         ▪  ▪  ▪▪                    │  ← 유형 점
├──────────────────────────────────────┤
│ 8월 8일 금요일                       │
│                                      │
│ 14:00 – 17:00                        │ caption
│ 면회                          함께   │ card-title + label
│                                      │
│ 19:00                                │
│ 숙소 예약 마감                 나    │
│                                      │
├──────────────────────────────────────┤
│ 같이 할 일                       +   │ card-title
│ ☐ 신분증 챙기기        현우 · 8/8    │ 48
│ ☑ 숙소 예약           함께 · 완료    │ 48 success
│ [ 할 일 빠르게 추가…            ]    │ 48

```

시각을 제목보다 위에 둔다 — 일정 화면에서 사용자가 스캔하는 것은 “몇 시”다. 담당자는 우측 정렬 텍스트. 색이 아니라 텍스트로 말한다.

`PRODUCT_PRD` 가치 3번(“감성 카드 모음이 아니라 날짜·시간·담당자·순서가 명확”)을 만족한다.

오프라인이면 `+`와 체크박스를 비활성 + 상단에 읽기 전용 배너. `[구현]`


**시각 있는 장소는 자동 정렬, 없는 장소는 아래 묶음 + 수동 이동.** `[구현]` 섞어서 정렬하면 순서의 근거가 사라진다.

**OCR 결과에 `확인 필요` 배지를 저장 후에도 유지한다** `[변경]` — 현재는 저장 전 확인만 한다. 사용자가 확인 없이 저장했을 수 있고, 잘못된 주소로 여행지에 못 가는 것은 회복 비용이 큰 실패다. 사용자가 직접 손대면 배지가 사라진다.

캡처 이미지는 서버로 올라가지 않는다. 이 사실을 캡처 시트 안에 캡션으로 명시한다. `[구현]`

## 7. 각 결정의 UX 근거 요약

| 결정 | 근거 |
| --- | --- |
| 군화 홈 기본 위젯 7→3 | 같은 맥락의 4중 반복이 60초 예산을 소모한다. `PRODUCT_REVIEW` §2가 이미 진단했고 기본값만 반영되지 않았다 |
| 브리핑을 스크롤 없이 완결 | 북극성 지표가 `확인 완료까지의 시간`이다. 버튼이 스크롤 아래면 지표가 스크롤 시간을 측정한다 |
| 항목마다 선정 이유 배지 | 곰신이 직접 표시한 것과 앱이 추론한 것의 신뢰도가 다르다. 군화의 질문 순서가 달라진다 |
| 발췌 2줄 고정 | 3개 항목의 한 화면 수납 조건. 동시에 원문 이동의 동기를 남긴다 |
| `더 보기` 접기 | 정보를 삭제하지 않고 시간 예산 결정권을 사용자에게 넘긴다 |
| 곰신 홈을 캡처 런처로 | 빈 입력창은 과제로 읽힌다. “입력보다 선택”(`PRODUCT_PRD` §7.5) |
| 공개 범위를 저장 버튼과 같은 시야에 | 오공유는 되돌릴 수 없다. 결정 시점과 확인 시점이 같아야 한다 |
| 감정에 고정 색 배정 안 함 | 색 매핑은 감정의 서열화로 읽힌다. “점수화 금지” |
| 복무 현황 → `우리` | 정보의 소유자가 아니라 의미로 배치한다. 곰신이 가장 자주 보는 관계 맥락이다 |
| 바텀시트=편집 / 모달=파괴 | 파괴적 행동만 스와이프로 닫히지 않게 해 실수를 막는다 |
| 탭 라벨 항상 표시 | 아이콘만인 탭바는 학습 비용을 사용자에게 전가한다. 320px에서도 5개는 들어간다 |
| 위험 행동에 빨강 배경 안 씀 | 빨간 블록 3개는 눌러야 할 버튼으로 보인다. 확정 순간에만 `danger` |
| OCR 배지를 저장 후 유지 | 잘못된 주소는 여행지에서 발견되고 회복 비용이 크다 |

### 새로 제안하는 기능 (모두 `[신규]` `[검증]`, 무료 운영·개인정보 원칙 준수)

**A. 통화 후 결정 캡처** — `여기까지 확인`을 누른 직후 한 줄:

```text
┌──────────────────────────────────────┐
│ 통화에서 정한 일이 있나요?           │
│ [                              ]     │
│ ○ 할 일   ○ 일정        [ 담기 ]     │
│                        건너뛰기      │
└──────────────────────────────────────┘
```

기존 `shared_tasks`/`schedules`에 쓴다. 새 API·새 비용 없음. 건너뛰기가 기본 경로이며 강제하지 않는다.

**B. 일정·여행의 `결정 필요`를 브리핑 큐에 합류** — 이미 존재하는 `통화 때 꼭 얘기` 플래그를 기록과 같은 우선순위 큐에 넣는다. 3개 상한 유지. 클라이언트 규칙 계산이라 비용 없음.

**C. `확인 필요` 지속 배지** — OCR로 채운 필드에 플래그를 남긴다. 로컬 판정으로 충분.

제안하지 않는 것: AI 요약 확대, 채팅, 장소 추천 피드, 감정 점수, 연속 기록 보상, 유료 지도 의존. 모두 `PRODUCT_REVIEW` §4의 금지 목록과 무료 운영 원칙에 따른다.

## 11. 디자인 프리뷰

### 11.1 무엇인지

`design-preview/` — 프로덕션과 완전히 분리된 독립 Vite 엔트리다.

```bash
npx vite --config design-preview/vite.config.ts        # 띄우기 (port 5199)

# 캡처
npx vite build --config design-preview/vite.config.ts --outDir <dist>
node design-preview/capture.mjs <dist> design-preview/captures
```

프로덕션과의 분리는 구조로 보장된다.

- `npm run build`는 저장소 루트 `vite.config.ts`를 쓰므로 이 폴더를 보지 못한다. `dist`에 유출되지 않음을 grep으로 확인했다.
- Supabase 클라이언트·스토어·라우터가 없다. 화면은 `fixtures.ts`의 정적 데이터만 받는다. **프리뷰를 열어도 사용자 데이터를 읽거나 쓸 수 없다.**
- 프로덕션 토큰(`src/styles/index.css`)을 **수정 없이 import**한다. 색·radius·다크 매핑이 전부 실제 값이다.
- `tsconfig.json` include가 `["src", "vite.config.ts"]`라 타입체크 대상이 아니다. 대신 **eslint 대상이며 `--max-warnings 0`을 통과한다.** 게이트를 약화시키지 않기 위해 `eslint.config.js`의 ignores는 건드리지 않았다.
- 원시 Tailwind 팔레트를 쓰지 않는다(`text-white` 포함). 그래서 `ui.tsx`의 프리미티브는 재작성 없이 PR 3에서 `src/`로 올릴 수 있다.
- 생성물(`captures/`, `dist/`)은 `design-preview/.gitignore`로 제외한다. 토큰이 바뀌면 즉시 낡는 PNG 수 MB를 저장소에 넣지 않는다.

### 11.2 커버리지

18화면 × 2뷰포트(390×844 / 320×568) × 2테마 = **152 프레임**. 상태는 `정상`이 전 화면, `빈 상태·로딩·오류·긴 텍스트`는 레이아웃이 실제로 깨지는 5화면(군화 홈·곰신 홈·기록 탭·여행 상세·연결 대기)에 추가 적용.

| 그룹 | 화면 |
| --- | --- |
| 홈 | 군화 홈 · 브리핑 더 보기 · 상대방의 오늘 전체 · 곰신 홈 |
| 기록 | 기록 탭 · 기록 작성 · 기록 상세 |
| 계획 | 일정 · 일정 상세 · 여행 목록 · 여행 상세 |
| 관계 | 우리 |
| 계정 | 마이 · 설정 · 삭제 확인 |
| 진입 | 로그인 · 온보딩 · 연결 대기 |

`capture.mjs`가 캡처와 동시에 모든 프레임의 `scrollWidth > clientWidth`를 검사한다. **152개 조합 전부 가로 오버플로 0.**

### 11.3 프리뷰가 잡아낸 것

문서상 계산으로는 옳아 보였지만 렌더링에서 틀린 것들이다. 프리뷰를 먼저 만든 이유가 여기 있다.

**1. 320×568에서 `여기까지 확인`이 잘렸다.** 컴팩트 규칙으로 액션 바에 `sticky bottom-0`을 걸었는데, `Card`가 둥근 모서리를 위해 갖고 있던 `overflow-hidden`이 sticky를 그 카드 박스 안에 가둔다. 카드가 뷰포트보다 높으니 sticky 지점이 화면 밖 카드 하단이 되고, 버튼은 탭바 뒤로 숨었다. **60초 완결 보장이 깨지는 결함이다.**

수정: 컴팩트에서 액션 바를 카드 밖으로 꺼내 탭바 위에 고정한다. `sticky`를 쓰지 않으므로 어떤 조상의 `overflow`에도 영향받지 않는다. §5.1의 컴팩트 규칙을 이 방식으로 대체한다.

**2. 여행 상세의 순서 변경 버튼이 행을 88px로 만들었다.** ↑↓를 세로로 쌓으면 44+44px이 되어, 320px에서 체크리스트가 화면 밖으로 밀렸다. 가로 배치로 바꿨다.

**3. 기념일을 채운 셀로 표시하니 “선택된 날”로 읽혔다.** 이 앱의 다른 모든 달력에서 채운 셀은 선택을 뜻한다. 기념일은 마커 점으로 바꿨다(기록 탭의 점 표기와 일치).

### 11.4 남은 판단 필요 항목

- **320×568에서 브리핑의 `첫 질문`이 스크롤 아래로 밀린다.** 핵심 3건과 확인 버튼은 첫 화면에 있다. 첫 질문을 보조로 내리는 것이 맞는지 판단이 필요하다.
- **`--coral-strong` 값은 canvas 실측 전이다.** 프리뷰 값은 제안이며 PR 3에서 확정한다.
- **`AI_HANDOFF` §4.1 #4(설정 버튼 포커스 링 미페인트)는 원인 미확정 상태로 남겼다.** 추측 수정을 하지 않는다는 기존 판단을 유지한다.
