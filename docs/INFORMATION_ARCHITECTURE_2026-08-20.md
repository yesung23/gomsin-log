## 0. 중심축에 대한 판정

Control Tower의 명제: *"곰신로그의 중심은 `기록 → 우리`다."*

**부분적으로 채택한다.** 정확히는 두 개의 중심이 있고, 경쟁하지 않는다.

```text
홈    = 하루 루프의 중심          (현재형)
우리  = 제품의 장기 가치의 중심    (과거형·누적)
```

**탭 순서는 바꾸지 않는다.** `홈 · 기록 · 일정 · 우리 · 마이` 그대로다.
근육 기억을 깨는 비용이 크고, `우리`를 앞으로 옮긴다고 사용자가 더 자주 가지 않는다.
대신 **`우리`가 도달하는 순간을 설계**하고(§6), 화면 자체를 가장 무겁게 만든다.

실패 모드는 하나다: **홈이 `우리`의 일을 하거나, `우리`가 홈의 일을 하는 것.**
홈은 오늘을 다루고, `우리`는 쌓인 것을 다룬다. 겹치면 둘 다 나빠진다.

## 1. `우리` — 기억 아카이브

### 1.1 결정적 판단 — 격자의 단위는 사진이 아니라 **하루**다

Instagram 프로필 격자는 **사진**이 단위다. 그걸 그대로 가져오면 이 제품에서 실패한다.
사진을 자주 올리지 않는 커플은 **구멍 난 격자**를 보게 되고, 그건 내가 대화형 홈에서
이미 확인한 밀도 실패와 정확히 같은 실패다.

**단위를 `하루`로 바꾸면 이 문제가 구조적으로 사라진다.**

- 한 달은 **항상 28~31칸**이다. 비지 않는다.
- 아무것도 없는 날은 *구멍*이 아니라 *조용한 칸*이다.
- 그리고 이것이 이 제품의 진짜 단위다 — §7.2가 이미
  `기록 하나 = 하루의 작은 조각 하나`라고 말한다.
- `함께 기다린 N일`이라는 숫자를 **눈으로 보여주는 것**이 된다.

```text
2026년 8월          기록 42 · 사진 18 · 함께한 날 2

┌──┬──┬──┬──┬──┬──┬──┐
│📷│📷│· │  │📷│★ │· │      📷 사진이 있는 날
├──┼──┼──┼──┼──┼──┼──┤      ·  기록만 있는 날
│  │· │📷│📷│· │  │  │      ★  면회·휴가·기념일
├──┼──┼──┼──┼──┼──┼──┤      □  아무것도 없는 날 (구멍이 아니다)
│📷│· │  │· │📷│📷│· │
└──┴──┴──┴──┴──┴──┴──┘
```

### 1.2 달력이 아니라 질감이다

**요일 정렬하지 않는다.** 7칸씩 채워 넣되 요일을 맞추지 않는다.

이유: 요일 정렬은 **달력**이고, 달력 문법은 `일정` 탭이 소유한다.
`일정`은 미래를 다루고 `우리`는 과거를 다룬다. 같은 격자 문법을 쓰면 두 탭이 섞인다.

`우리`의 격자는 **"이 달에 이만큼이 있었다"** 는 질감이지, 날짜를 찾는 도구가 아니다.

### 1.3 렌즈 토글을 두지 않는다

`[사진] [기록] [일정]` 같은 전환을 **넣지 않는다.**

대안이 얇은 토글은 빈 화면과 경쟁한다. 나는 이미 `RecordPage`에서 `사진` 렌즈를
*기간에 사진이 있을 때만* 나타나게 조건을 걸어야 했다. 여기서는 애초에 만들지 않는다.
**하나의 뷰를 잘 만든다.**

### 1.4 화면 위계

```text
우리
├─ 1. 관계 헤더            함께한 412일 · 다음 만남 D-12 면회
│                          ← 이 화면에서 가장 큰 숫자
├─ 2. 달 섹션 (최신 순)
│     ├─ 2026년 8월  기록 42 · 사진 18 · 함께한 날 2
│     ├─ 하루 격자
│     └─ [ 이 달 다시 보기 ]
│     ├─ 2026년 7월 …
│     └─ …
└─ 3. 여행 · 기념일 진입점   ← 기존 기능. 제거하지 않는다
```

칸을 누르면 **그날의 기록으로 간다.** 정확한 원본이며, 근사치로 대체하지 않는다(§4.2).

### 1.5 `이 달 다시 보기` — AI 없이

그 달에서 **규칙으로** 고르고, **사람이 편집**한다.

우선순위:
1. 일정이 있던 날 (면회 · 휴가 · 외박 · 기념일 · 여행)
2. **둘 다 기록한 날** — 이 관계에서 가장 의미 있는 신호다
3. 사진이 있는 날
4. `이따 이야기하기`가 붙었던 기록

한 달 상한 12개. 사용자가 빼고 넣는다.

**AI가 중요도를 판정하지 않는다**(§15, 사업문서 §17 전략 가드).
이것이 `P-MP`「우리의 한 달」이 그대로 올라탈 구조이며, 지금은 **결제도 제작도 없이
보여주기만** 한다.

## 2. 홈 — 역할별

### 2.1 곰신 홈 — 남기는 곳

```text
홈 (곰신)
├─ 1. 컴포저                    제거 불가 · 항상 펼쳐져 있음
│     [사진] [음성] [한 줄]
├─ 2. 오늘 남긴 것 · 3          제거 불가
│     09:12 · 13:40 · 18:05
├─ 3. 몽룡에게서                제거 불가
│     어제 하루를 남겼어요 →
│     토닥이기 2
├─ 4. 전역까지 302일
└─ 5. 위젯                      선택 · 제거 가능
```

**`오늘 남긴 것`이 읽음 표시를 대체한다.**
곰신의 불안은 "읽었나"가 아니라 **"닿았나"** 이고, 후자는 감시 없이 답할 수 있다.
읽음 표시는 만들지 않는다(§5.1).

**`몽룡에게서`는 상대가 *한 행위*만 담는다.** 접속·열람은 절대 담지 않는다.

### 2.2 군화 홈 — 브리핑

```text
홈 (군화)
├─ 1. 춘향의 놓친 하루          제거 불가 · 이 화면의 본체
│     😞 오전에는 …  →
│     🍚 점심에는 …  →
│     😊 오후에는 …  →
│     [ 다 확인했어요 ]         ← PartnerDay CONFIRMED 유일 경로
├─ 2. 오늘 이야기할 것 · 2      제거 불가
├─ 3. [ 통화 모드 ]             제거 불가 · 출구는 앱 밖이다
├─ 4. 지금 남기기               제거 불가 (§5.1 두 역할 모두 기록한다)
└─ 5. 위젯                      선택 · 제거 가능
```

`CallBriefingWidget`은 위젯이 아니라 **1번 항목 그 자체**가 된다.

### 2.3 두 홈이 공유하는 규칙

- 1~4번은 **제거할 수 없다.** §7.1이 기록 진입점에 쓰는 문법을 홈 전체에 적용한다.
- 위젯 커스터마이즈는 **없애지 않는다.** 코어 아래 선택 계층으로 내린다.
- 어느 홈도 **관계 점수·애정도·연속 기록**을 표시하지 않는다.

## 3. Push — 루프를 잇는 방식

메커니즘 전체는 `PHASE_NEXT_ARCHITECTURE` §1이 소유한다. 여기서는 **IA 결정 하나**만
확정한다.

### 3.1 모든 push는 **홈으로 착지한다**

개별 기록으로 보내지 않는다.

이유:
- push는 **병합된 신호**다(`has_unseen` 플래그 하나). 기록 5건을 나타내는 알림이
  그중 1건으로 데려가면 나머지 4건을 숨긴다.
- 그 기록이 **삭제되거나 비공개로 전환**됐을 수 있다. §6.4는 이 경우 대체를 금지한다.
  홈은 언제나 존재하므로 이 문제가 발생하지 않는다.
- 홈이 이미 `오늘 이야기할 것`을 포함하므로, `이따 이야기하기` 알림도 홈이면 충분하다.

```text
곰신 기록
  → has_unseen: false → true
  → 군화의 연락 가능 시간에 전송
  → "새로운 소식이 있어요"
  → 탭 → 군화 홈 = 브리핑
  → 원본 → 이야기거리 → 통화 모드
```

기존 `notificationDestination`의 record 라우팅은 **인앱 재진입 경로**로 남긴다.
그건 다른 경로이고, 이미 대상 부재를 처리한다.

## 4. 통화 모드

### 4.1 존재 이유

`이야기했어요`는 §8의 완료 신호인데, 지금은 **통화가 끝난 뒤 앱에 다시 들어가
목록을 찾아 눌러야 한다.** 그 마찰 때문에 완료 처리가 안 되고 보관함이 쌓이기만 한다.
**루프의 마지막 화살표가 닿지 않는다.**

### 4.2 화면

```text
통화 모드
┌────────────────────────────┐
│                            │
│   시험 얘기                 │   ← 한 번에 하나. 크게.
│                            │
│   [ 이야기했어요 ]          │   ← 완료 → 다음으로
│   [ 다음 ]                  │   ← 건너뛰기 (완료 아님)
│                            │
│   1 / 2                    │
└────────────────────────────┘
```

### 4.3 결정

- **전화를 걸지 않는다.** 통화는 사용자가 알아서 한다. 이 화면은 그동안 옆에 있을 뿐이다.
- **양쪽 역할 모두 진입할 수 있다.** 통화는 한쪽만 하는 게 아니다.
- 각 `이야기했어요`는 **독립적인 쓰기**다. 중간에 나가도 거기까지 저장된다.
- **통화에 관한 어떤 것도 기록하지 않는다.** 시각·길이·횟수 전부. §19.
- 남은 항목이 0이면 진입점을 숨긴다. 빈 화면으로 보내지 않는다.

## 5. AI / 온디바이스 지능의 자리

### 5.1 이번 단계에서 모델을 넣지 않는다

§6.2가 요약에 LLM을 금지하고, 남는 후보는 감정 6분류 하나인데 결정적 어휘 엔진이
**0 MB · 1 ms 미만 · 완전 오프라인**으로 처리한다. 비결정성은 §6.2와
"교정이 유지된다"는 성질을 **동시에** 깨뜨린다. 사업 로드맵도 온디바이스 AI 실증을
**M6**(M3·M5 이후)에 둔다.

### 5.2 나중에 모델이 자리를 얻을 수 있는 곳은 **한 곳뿐이다**

**`이 달 다시 보기`의 초안 문장.**

그 자리가 유일하게 조건을 만족한다:
- **일상 루프 밖**이다 → 지연·발열이 기록 경험을 해치지 않는다
- **사용자가 명시적으로 눌러서** 시작한다 → 자동 실행이 아니다
- **결과를 사람이 편집한다** → 최종 편집자는 사람(§3 원칙 10)
- **결정성이 요구되지 않는다** → 초안이지 판정이 아니다

실행 조건: 온디바이스 · idle 또는 충전 중 · 사용자 요청 시에만.
지원하지 않는 기기는 **규칙 기반 초안**으로 degrade하며, 그것으로도 제품이 완결된다
(`P-MP`는 AI 성공에 의존하지 않는다 — `ENGINEERING_ROADMAP` §P-MP).

### 5.3 AI가 영구히 하지 않는 것

```text
중요한 기억의 자동 선정
관계 점수 · 애정도 · 궁합
숨은 감정 단정 · 상대 마음 추측
이별 가능성 예측
건강·주기 데이터에 대한 어떤 추론도
접속 시점 예측
```

## 6. 사용자 여정 — 세 시간 축

```text
[ 하루 ]
  곰신: 홈 컴포저 → 남김 → `오늘 남긴 것`에서 닿았음을 확인
  군화: 알림 → 홈 브리핑 → 정확한 원본 → 이야기거리 → 통화 모드 → 이야기했어요

[ 한 달 ]
  달이 끝남 → `우리`에 달 블록이 생김 → 하루 격자 → 이 달 다시 보기
  ※ 앱이 먼저 말을 걸지 않는다. 달이 바뀐 것은 상대가 한 행위가 아니다

[ 관계 ]
  100일 · 첫 휴가 · 1주년 · 전역
  전역 = 비대칭이 끝나는 날 = 제품 이유가 사라지는 날 = 아카이브 가치 최대인 날
       → `우리`가 그날 가장 무거운 화면이 되어야 한다
```

**`우리`에 도달하는 순간을 설계한다** (§0의 약속):

| 언제 | 어떻게 |
|---|---|
| 달이 바뀐 직후 첫 실행 | 홈 상단에 조용한 한 줄 — `7월이 정리됐어요 →` |
| 마일스톤 당일 | 같은 자리에 마일스톤 한 줄 |
| 전역 | `우리`가 기본 진입 화면이 된다 |

셋 다 **알림이 아니라 앱 안의 한 줄**이다. 밀지 않는다.

## 7. 만들지 않는 것

| 금지 | 근거 |
|---|---|
| 사진 단위 격자 | 밀도 실패. 하루 단위로 대체(§1.1) |
| `우리`의 렌즈 토글 | 얇은 대안은 빈 화면과 경쟁한다(§1.3) |
| 요일 정렬 격자 | `일정` 탭의 문법을 침범한다(§1.2) |
| 탭 순서 변경 | 근육 기억 비용 대비 이득 없음(§0) |
| 읽음 표시 | 감시가 되고 압박을 만든다(§2.1) |
| 개별 기록으로 착지하는 push | 병합 신호와 모순 · 대상 부재 위험(§3.1) |
| 통화 시각·길이 기록 | §19 |
| 인스타형 피드 | 만들고 되돌림. 밀도가 다르다 |
| 연속 기록 · 스트릭 · 독촉 | 부재는 이벤트가 아니다 |
| AI의 기억 중요도 판정 | §15 · 사업문서 §17 |

## 8. 구현 순서 (Control Tower 결정)

```text
Gate 1  우리 = 기억 축적            gate 없음 · 클라이언트 전용 · 즉시 착수 가능
        └ MediaArchiveGrid 이동 + 하루 격자 + 달 블록

Gate 2  역할별 홈                   gate 없음
        └ 통화 모드는 여기서 함께 설계된다(군화 홈의 출구이므로)

Gate 3  Push                        보안 review + migration gate (048 이상)
        └ 착지점이 Gate 2로 확정된 뒤에야 gate를 한 번만 통과한다
        └ 해제 시 토큰 무효화를 같은 단계에서

Gate 4  통화 모드                    gate 없음
        └ Gate 2의 이야기거리 위에 올라간다

Gate 5  AI                          M6 이후. 자리는 §5.2 한 곳
```

> **순서 변경의 근거를 기록해 둔다.** 나는 Push를 1번으로 제안했고, 이유는
> "루프의 첫 이벤트가 없다"였다. 진단은 유효하지만 결론이 틀렸다 — 아카이브를 채우는
> 것은 곰신의 *기록*이고 Push가 바꾸는 것은 군화의 *따라잡기*이므로, `우리`는 Push에
> 의존하지 않는다. 그리고 Push는 **착지점이 확정되어야 보안 gate를 한 번만 밟는다.**
> Control Tower 판단이 옳다.

## 9. canonical 개정이 선행되어야 하는 것

## 10. 이 문서의 지위

- **화면에 무엇이 어떤 순서로 있는가**만 소유한다. 메커니즘은 `PHASE_NEXT_ARCHITECTURE`,
  진단은 `PRODUCT_DIRECTION_REVIEW`, 제품 의도는 `PRODUCT_V3`.
- 구현하지 않았고, 원격·Production 상태를 확인하거나 변경하지 않았다.
- §6의 전역 관련 사업 판단은 **검증 대상 가설**이며 수치를 쓰지 않았다.
