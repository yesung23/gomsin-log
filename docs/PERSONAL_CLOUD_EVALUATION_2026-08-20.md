# 개인 클라우드 저장 검토 — Google 경로 포함 (2026-08-20)

> **제안서다. 아무것도 구현하지 않는다.** ARCH-P6 결정의 재검토 자료이며,
> 채택하려면 `ENGINEERING_ROADMAP.md`의 P6 gate를 거쳐야 한다.
> 사업 방향은 [`BUSINESS_MEMORY_ROADMAP_V1.md`](BUSINESS_MEMORY_ROADMAP_V1.md) §8,
> 기존 결정은 [`ENGINEERING_ROADMAP.md`](ENGINEERING_ROADMAP.md) §2 ARCH-P6이 소유한다.

---

## 0. 한 문장 결론

**개인 클라우드는 백업·복구에 쓸 수 있고, 커플 공유에는 쓸 수 없다.**
iCloud도 Google Drive도 마찬가지이며, 이는 벤더 선택 문제가 아니라 구조적 제약이다.
따라서 **공유 경로는 지금처럼 크로스플랫폼으로 유지**하고, 개인 클라우드는
**추가되는 계층**으로만 검토한다.

---

## 1. "구글 클라우드"는 두 가지 서로 다른 것이다

이 구분을 흐리면 전략이 반대 방향으로 간다.

| | Google Drive `appDataFolder` | Google Cloud Storage / Firebase Storage |
|---|---|---|
| 소유자 | **사용자** | **회사** |
| 할당량 | 사용자의 Google 계정 15GB(공유) | 회사가 구매 |
| 비용 곡선 | 사용자 수와 무관 | **사용자 수에 비례** |
| iCloud의 대응물인가 | **예** | 아니오 |
| §17 전략 가드 | 부합 | **"서버에 모든 미디어를 저장하는 구조만 전제" 로 회귀** |

`BUSINESS_MEMORY_ROADMAP_V1` §12의 생존 전략은 **저장 비용이 사용자와 함께 급증하는
구조를 완화**하는 것이다. Google Cloud Storage는 그 문제를 해결하지 않고 이름만 바꾼다.
Supabase Storage를 GCS로 바꾸는 것은 **저장 계층 이전이지 개인 클라우드 전략이 아니다.**

> 따라서 이 문서에서 "Google 경로"는 **Google Drive `appDataFolder`**를 뜻한다.

---

## 2. E2EE가 이 질문을 쉽게 만든다

blob이 이미 암호문이므로 **저장 계층은 교체 가능한 전송 세부사항**이다.

```text
평문 → EXIF/GPS 제거 → 정규화 → 곰신로그 E2EE → [ 불투명한 바이트 ]
                                                      ↓
                          iCloud / Google Drive / Supabase Storage — 무관
```

저장소는 키를 갖지 않으므로 어디에 두든 프라이버시 등급이 같다. 이것이
**한 커플이 서로 다른 플랫폼을 써도 되는 이유**이고, 벤더 락인을 피하는 근거다.

**이 성질은 지켜야 한다.** 저장소가 콘텐츠를 이해해야 하는 기능(서버측 썸네일,
서버측 트랜스코딩, 서버측 검색)을 도입하면 즉시 깨진다.

---

## 3. 결정적 제약 — 개인 클라우드는 공유가 안 된다

여기가 이 검토의 핵심이고, **ARCH-P6의 재검토가 필요한 지점**이다.

| | iCloud (CloudKit) | Google Drive |
|---|---|---|
| 앱 전용 개인 저장 | CKContainer private DB | `appDataFolder` |
| **다른 사용자와 공유** | `CKShare` **있음** | **없음** |
| 앱 삭제 시 | 남는다 | **삭제된다** |
| 사용자에게 보이는가 | 아니오 | 아니오 |
| OAuth 민감 스코프 | 해당 없음 | `drive.appdata`는 **민감 스코프 아님**(검증 불필요) |

### 3.1 ARCH-P6의 `CKShare read-only partner`가 안 되는 이유

ARCH-P6는 파트너 접근을 `CKShare`로 설계했다. 그런데 `CKShare`는 **Apple 계정 간에만**
동작한다. 따라서:

```text
iPhone + iPhone    CKShare 동작
Galaxy + Galaxy    대응물 없음 — Google Drive에는 appDataFolder 공유가 없다
iPhone + Galaxy    동작 불가
```

`ENGINEERING_ROADMAP` §2의 `Android boundary intentionally deferred`는 이 문제를
**미룬 것이지 푼 것이 아니다.** 그리고 이것은 Android 지원 시점의 문제가 아니라
**iPhone+Galaxy 커플이 존재하는 순간의 문제**다 — 즉 베타 첫날부터다.

### 3.2 왜 "양쪽 클라우드에 사본"이 답이 아닌가

업로더는 **파트너의 개인 클라우드에 쓸 권한이 없다.** 파트너가 스스로 내려받아
자기 클라우드에 올려야 하는데, 그러면 파트너가 접속하기 전까지 원본은 업로더 기기에만
있다. 군 복무 커플의 접속 패턴에서 그것은 **몇 주간 사진이 전달되지 않는다**는 뜻이다.

---

## 4. 그래서 제안하는 구조 — 공유와 보존을 분리한다

```text
                    ┌─ 공유 경로 (필수, 크로스플랫폼) ─────────────┐
사용자 기기 → E2EE →│  중립 blob 저장 + Supabase 조율 메타데이터    │→ 파트너
                    └──────────────────────────────────────────┘
                              │
                              └─ 보존 경로 (선택, 플랫폼별) ─────────┐
                                 iCloud / Google Drive appDataFolder │
                                 = 내 기록의 개인 백업·기기 복구      │
                                 파트너 접근 경로 아님                │
                                 ──────────────────────────────────┘
```

- **공유 경로는 하나뿐이고 플랫폼 중립이다.** 세 커플 조합이 전부 동작하는 근거.
- **보존 경로는 있으면 좋고 없어도 제품이 완결된다.** 할당량 초과·계정 미연결·
  플랫폼 미지원이 **공유를 막지 않는다.**
- 사용자가 원래 말한 방향 —
  *"iCloud는 개인 백업/기기 복구에 활용하되, 커플 공유·E2EE canonical 구조는
  크로스플랫폼으로 유지"* — 과 정확히 같다. **그 직관이 맞았다.**

### 4.1 이 구조가 비용에 대해 정직하게 말하는 것

개인 클라우드는 **공유 경로의 비용을 0으로 만들지 않는다.** 공유 blob은 여전히
회사가 비용을 내는 중립 저장소에 있어야 한다. 개인 클라우드가 줄이는 것은
**장기 보존분**이지 유통분이 아니다.

`BUSINESS_MEMORY_ROADMAP_V1` §8이 이미 경고한 대로, *"서버비 0원, 무제한 영상"*
같은 표현은 쓰지 않는다.

## 5. Google Drive `appDataFolder`의 실제 함정

채택한다면 미리 알아야 할 것들. 전부 사용자에게 보이는 결과를 낳는다.

| 함정 | 결과 | 대응 |
|---|---|---|
| **앱 삭제 시 `appDataFolder`가 삭제된다** | "재설치하면 복구된다"는 약속이 거짓이 된다 | 백업을 복구 수단으로 광고하지 않거나, 일반 Drive 폴더 사용(사용자에게 보임) |
| 15GB를 Gmail·Photos와 공유 | 곰신로그와 무관한 이유로 가득 참 | 할당량 초과를 **정상 상태**로 다루고 공유를 막지 않는다 |
| 계정 하나에 기기 여러 대 | 동시 쓰기 충돌 | 파일명에 기기 식별자, 병합 금지 |
| Android에서 Google 계정 미로그인 가능 | 보존 경로 없음 | 선택 기능이므로 문제되지 않음 |
| iOS에서도 Google Drive 사용 가능 | **경로를 하나로 통일할 수 있다** | 아래 §6 |

> `drive.appdata`가 **민감 스코프가 아니라는 점**은 실질적 장점이다. Google의
> 앱 검증(security assessment)을 요구하지 않아 초기 진입 비용이 낮다.
> 이는 문서 작성 시점의 이해이며 **채택 전에 재확인해야 한다.**

---

## 6. 검토할 만한 단순화 — 보존 경로를 Google Drive 하나로

iOS에서도 Google Drive를 쓸 수 있으므로, 보존 경로를 **플랫폼당 하나씩 두 개**가
아니라 **전 플랫폼 하나**로 둘 수 있다.

| | iCloud + Drive (플랫폼별) | Drive 단일 |
|---|---|---|
| 구현·테스트 표면 | **2배** | 1배 |
| iOS 사용자 경험 | OS 기본 계정, 마찰 없음 | Google 로그인 추가 필요 |
| 앱 삭제 후 잔존 | iCloud는 남음 | **삭제됨** |
| 플랫폼 정책 리스크 | 분산 | 한 벤더에 집중 |

**권고: 결정하지 않는다.** 이것은 M5 개인 클라우드 PoC가 답할 질문이고,
지금 고르면 근거 없이 고르는 것이다. 다만 **보존 경로가 선택 계층이라는 전제**를
지키면 이 결정을 나중으로 미룰 수 있다 — 그것이 이 구조의 가장 큰 장점이다.

## 7. 지금 바뀌어야 하는 것 / 바뀌지 않아도 되는 것

### 바뀌지 않는다
- 키 계층(PMK/CSK/HRK), envelope, device bootstrap, RLS — 전부 플랫폼 중립이고
  이미 옳다. **저장 벤더 검토가 여기를 건드릴 이유가 없다.**
- Supabase의 역할(Auth, Postgres, 관계, RLS, 조율 메타데이터).

### 재검토가 필요하다 — P6 gate 항목
1. **ARCH-P6의 `CKShare read-only partner`.** iPhone+Galaxy 커플에서 동작하지 않는다.
   공유 경로를 플랫폼 중립 저장소로 되돌리는 개정이 필요하다.
2. **`Android boundary intentionally deferred`.** 이것은 Android 출시 시점의 문제가
   아니라 **혼합 커플이 존재하는 첫날의 문제**다.
3. 보존 경로 벤더 선택(§6) — M5 PoC 이후.

- **제안서다.** ARCH-P6를 대체하지 않는다. 채택하려면 `ENGINEERING_ROADMAP.md`를
  먼저 개정해야 한다.

  1차 자료로 재확인해야 한다. 이 문서는 그것을 검증된 사실로 주장하지 않는다.
