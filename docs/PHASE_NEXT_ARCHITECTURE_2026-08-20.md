## 0. 이 단계가 바꾸는 것

```text
지금:  곰신이 기록 → (아무 일도 일어나지 않음) → 군화가 언젠가 앱을 염 → 발견
       그리고 그 기록들은 어디에도 쌓이지 않는다

다음:  곰신이 기록 → 군화가 받을 수 있는 시간에 알림 → 브리핑 → 원본 → 통화
       그리고 그 시간이 `우리`에 눈에 보이게 쌓인다
```

두 문장이다. **하루의 루프를 닫는 것**과 **그 하루들이 자산이 되게 하는 것.**

## 1. Push — 루프의 첫 이벤트

### 1.1 지배 규칙 하나

> **상대가 *한 행위*만 알린다. 상대를 *관찰한 결과*는 절대 알리지 않는다.**

이 한 줄이 나머지를 전부 결정하고, §3 원칙 6("불안을 만들지 않는다")을 코드가 아니라
정책 수준에서 지킨다.

| 이벤트 | 알리나 | 왜 |
|---|---|---|
| 상대가 기록을 남김 | **예** | 스스로 한 행위 |
| 상대가 반응함(공감/토닥이기) | **예** | 스스로 한 행위 |
| 상대가 `이따 이야기하기` 표시 | **예** | 스스로 한 행위 |
| 상대가 배려 신호 공유 | **예** | 설계상 명시적 opt-in |
| 커플 연결이 성립됨 | **예** | 양쪽의 행위 |
| 상대가 내 기록을 **읽음** | **절대 아니오** | 관찰. 읽음 압박을 만든다 |
| 상대가 **앱을 염** | **절대 아니오** | 관찰. 접속 감시(§19) |
| 상대가 **N일째 기록 없음** | **절대 아니오** | **부재는 행위가 아니다** |
| 주기·건강 관련 일체 | **절대 아니오** | HRK 도메인 |

마지막 세 줄이 중요하다. **부재를 이벤트로 만들지 않는다**는 규칙이 연속 기록·독촉·
리인게이지먼트 알림을 구조적으로 불가능하게 만든다. 나중에 "리텐션을 위해" 추가하려는
시도가 있으면 이 표를 근거로 거절한다.

### 1.2 상태 모델 — 큐가 아니라 플래그

기록 20건이 쌓인 뒤 군화가 폰을 받으면 알림 20개가 간다. 그건 재앙이다.

**이벤트 큐를 두지 않는다. 수신자별 플래그 하나를 둔다.**

```text
has_unseen : boolean     ← false → true 로 바뀔 때만 push가 나간다
last_notified_at         ← 하루 1회 상한을 판정
                            (앱을 열면 has_unseen 이 false 로 돌아간다)
```

이 모델이 공짜로 주는 것:

- **자동 병합.** 기록 20건 = push 1건.
- **자동 재무장.** 열어서 확인한 뒤 다음 날 새 기록 = 다시 알림.
- **개수를 셀 수 없다.** payload에 넣을 숫자가 애초에 존재하지 않는다.
- **서버 메타데이터가 boolean 하나 + 타임스탬프 하나.** §14.3의 최소 메타데이터 원칙.

> `3개`는 부채처럼 읽히고 `새로운 하루`는 초대처럼 읽힌다. 개수를 없애는 것은
> 프라이버시 결정인 동시에 정서적 결정이다.

### 1.3 언제 보내는가 — 추적 없이

군화는 오후 2시에 훈련 중이다. 그때 온 알림은 소음이거나 불안이다.

**이미 있는 것을 쓴다: `ContactPreferences`.** 사용자가 직접 입력한 연락 가능 시간이다.

```text
알림 발생
  → 수신자의 연락 가능 시간대인가?
      예   → 즉시 전송
      아니오 → 다음 시간대 시작까지 보류 (플래그는 그대로 유지)
  → 시간대가 오늘 이미 지났으면 내일 시작 시각에 전송
```

**접속 패턴을 학습하지 않는다.** 사용자가 말해준 것만 쓴다. §19를 지키면서 같은
목적을 달성하고, 오히려 더 정확하다 — 훈련 일정은 행동 로그보다 본인이 잘 안다.

> **변경 필요:** `ContactPreferences`는 현재 온보딩에서 군화에게만 묻는다(step 6).
> 양쪽 모두에게 묻되, 곰신에게는 `알림 받을 시간`으로 다르게 표현한다.
> 미설정 기본값은 **08:00–22:00** — 새벽에 깨우지 않는다.

### 1.4 payload — 하나의 문구만 쓴다

```text
title : 곰신로그
body  : 새로운 소식이 있어요
data  : { eventType, destination: { kind: 'record', recordId } }   ← 라우팅 전용
```

**이벤트 종류에 따라 문구를 바꾸지 않는다.** 이유는 잠금화면이다.
`이야기하고 싶은 기록이 있어요` 와 `새로운 하루가 도착했어요` 가 구분되면, 옆에서
잠금화면을 본 사람이 커플 사이에 무슨 일이 있었는지를 좁힐 수 있다. 생활관에서
휴대폰이 관찰되는 상황은 이 사용자층에서 가정해야 하는 조건이다.

특히 **배려 신호가 같은 문구를 쓰는 것이 중요하다.** 전용 문구를 주면 그 문자열의
존재 자체가 건강 상태와 상관된다.

이름·개수·본문·감정·주기는 어떤 경우에도 payload에 없다. `notifications.ts`의 기존
계약이 이미 이 모양이므로 **확장이 아니라 준수**다.

### 1.5 권한 요청 시점

앱 시작 시가 아니다. **커플 연결이 성립된 직후**다.

```text
"몽룡과 연결됐어요"
  → "몽룡이 하루를 남기면 알려드릴까요?"   [ 좋아요 ]  [ 나중에 ]
```

이 순간에만 가치가 구체적이다. 그 전에는 알릴 대상이 존재하지 않는다.
거절해도 앱은 온전히 동작한다 — 인앱 재진입 경로가 이미 있다.

### 1.6 반드시 함께 만들어야 하는 것 — 해제

**연결 해제·계정 삭제 시 push 토큰이 즉시 무효화되어야 한다.**

이걸 빠뜨리면 헤어진 상대가 `새로운 소식이 있어요` 를 계속 받는다. §14.4가
"앞으로의 서버 측 권한을 제거한다"고 했고, push는 정확히 그 권한이다.

- 로그아웃 → 그 기기 토큰 제거
- 연결 해제 → 양쪽 모두 상대 이벤트 대상에서 제외
- 계정 삭제 → 토큰 행 삭제
- 계정 전환 → 이전 계정 토큰이 새 계정 이벤트를 받지 않음

**negative test 필수:** 해제된 파트너의 기록이 push를 발생시키지 않음을 증명한다.

### 1.7 데이터 모델 (gate 대상)

```text
device_push_tokens
  user_id      → RLS: 본인만 읽기·쓰기
  token, platform
  created_at, last_seen_at

couple_members  (기존 테이블에 추가)
  has_unseen        boolean
  last_notified_at  timestamptz
```

발신은 Edge Function(service role). **그 함수는 콘텐츠를 읽지 않는다** — 수신자와
generic 종류만 알면 되므로, 평문 접근 권한이 애초에 필요 없다. 이것이 §14.3을
구조적으로 지키는 방법이다.

## 2. 역할별 홈

### 2.1 곰신 홈 — 남기는 곳, 그리고 닿았다는 안심

```text
┌ 곰신로그  춘향 ──────────────────────────┐

  지금 뭐 하고 있어요?
  ┌────────────────────────────────────┐
  │ [사진]  [음성]  [한 줄]              │   ← 항상 펼쳐져 있다. 탭 뒤에 숨기지 않는다
  └────────────────────────────────────┘

  오늘 남긴 것 · 3                          ← "닿았다"는 감각의 근거
    09:12  아침에 …
    13:40  [사진]
    18:05  …

  몽룡에게서                                ← 돌아온 것. 대시보드 카드가 아니다
    어제 하루를 남겼어요  →
    토닥이기 2

  전역까지 302일

  [ 위젯 더 보기 ]                          ← 선택 계층으로 내려간다
└──────────────────────────────────────┘
```

**결정:**
- 컴포저가 첫 번째이고 **제거할 수 없다**(§7.1의 문법을 홈에도 적용).
- `오늘 남긴 것`이 **읽음 표시의 대체재**다. 상대가 읽었는지는 알려주지 않지만,
  내가 남긴 것이 거기 있다는 사실은 보여준다. 곰신의 불안은 "읽었나"보다
  **"닿았나"** 이고, 후자는 감시 없이 답할 수 있다.
- `몽룡에게서`는 상대가 *한 행위*만 담는다. §1.1과 같은 규칙.

### 2.2 군화 홈 — 브리핑, 그리고 출구는 전화

```text
┌ 곰신로그  몽룡 ──────────────────────────┐

  춘향의 놓친 하루                          ← §6.1 요약 층. 위젯이 아니라 화면 그 자체
    😞  오전에는 시험 때문에 속상했어요  →
    🍚  점심에는 친구와 식사했어요       →
    😊  오후에는 좋은 일이 있었어요      →

    [ 다 확인했어요 ]                       ← PartnerDay CONFIRMED. 유일한 경로

  오늘 이야기할 것 · 2                      ← Conversation Bridge
    · 시험 얘기
    · 사진 속 그 카페

  [ 통화 모드 ]                             ← 이 화면의 출구는 앱이 아니다

  지금 남기기                               ← §5.1: 두 역할 모두 기록할 수 있다
└──────────────────────────────────────┘
```

**결정:**
- 요약이 **화면**이다. `CallBriefingWidget`은 위젯이 아니라 이 화면의 본체가 된다.
- 모든 줄이 **정확한 원본**으로 간다(§4.2). 근사치 금지.
- **출구가 앱 밖을 가리킨다.** §11 원칙("앱 안에 오래 머무르게 하는 것이 목적이
  아니다")을 화면 구조로 표현한 것이다.

### 2.3 통화 모드 — 이 단계의 새 기능 하나

통화 중에 이야기거리를 큰 글씨로 보여주고, 말한 것을 그 자리에서 `이야기했어요`로
넘긴다.

```text
┌ 통화 중 ─────────────────────────────┐
                                        
   시험 얘기                             
   ────────────────                      
   [ 이야기했어요 ]   [ 다음 ]           
                                        
   1 / 2                                 
└──────────────────────────────────────┘
```

**왜 필요한가:** `이야기했어요`는 §8의 완료 신호인데, 지금은 통화가 끝난 뒤 앱에
다시 들어가 목록을 찾아 눌러야 한다. 그 마찰 때문에 완료 처리가 안 되고,
보관함이 영원히 쌓이기만 한다. **루프의 마지막 단계가 닫히지 않는다.**

전화를 거는 기능은 아니다. 통화는 사용자가 알아서 한다. 이 화면은 그동안 옆에 있을 뿐이다.

### 2.4 위젯은 어떻게 되는가

**없애지 않는다.** 코어(위 두 화면) 아래에 선택 계층으로 내린다.
`SoldierDashboard` 제거에서 얻었어야 할 교훈은 "커스터마이즈가 필요하다"가 아니라
**"목적이 다른 두 화면을 하나로 묶지 말라"** 였다.

## 3. `우리` — 축적의 증거

### 3.1 구조

```text
┌ 우리 ────────────────────────────────┐

  함께한 지 412일                        ← 이 화면에서 가장 큰 숫자
  다음 만남  D-12 · 면회

  [ 사진 ]  [ 기록 ]  [ 일정 ]           ← 렌즈

  ┌───┬───┬───┐
  │   │   │   │                          ← MediaArchiveGrid — 이미 만들어져 있다
  ├───┼───┼───┤
  │   │   │   │
  └───┴───┴───┘

  ── 2026년 8월 ──────────────
     기록 42 · 사진 18 · 함께한 날 2
     [ 이 달 다시 보기 ]

  ── 2026년 7월 ──────────────
     기록 51 · 사진 27 · 함께한 날 4
     [ 이 달 다시 보기 ]
└──────────────────────────────────────┘
```

**결정:**
- **그리드가 주인공이다.** 시간이 쌓였다는 사실을 눈으로 보여주는 유일한 방법이고,
  Instagram에서 이 제품에 실제로 맞는 유일한 문법이다(피드가 아니라 프로필 그리드).
- `MediaArchiveGrid`는 **이미 구현되어 있고** 기록 탭 안에 묻혀 있다. 옮기면 된다.
- **달이 축적의 단위**다. 그리고 그것이 「우리의 한 달」의 단위이기도 하다 —
  P-MP가 나중에 그대로 올라탈 수 있는 구조를 지금 만드는 것이다.

### 3.2 `이 달 다시 보기` — AI 없이

그 달의 기록·사진·일정을 **결정적으로** 모아 보여준다.

- 선정은 **규칙**이다: 사진이 있는 날, 일정이 있는 날, `이따 이야기하기`가 붙었던 것,
  사용자가 표시한 것.
- **AI가 중요한 기억을 고르지 않는다**(§15, 사업문서 §17 전략 가드).
- 사용자가 빼고 넣을 수 있다. **최종 편집자는 사람이다**(§3 원칙 10).

이것이 `P-MP`의 선행 구조다. 결제·제작 없이, **먼저 보여주기만** 한다.

## 4. 리텐션 루프 — 세 개의 시간 축

### 4.1 하루 (연결)

```text
기록 → push(받을 수 있는 시간에) → 브리핑 → 정확한 원본
     → 이따 이야기하기 → 통화 모드 → 이야기했어요
```

지금 있는 루프에 **첫 화살표(push)와 마지막 화살표(통화 모드)** 를 붙이는 것이다.
양 끝이 열려 있어서 루프가 아니라 직선이었다.

### 4.2 한 달 (축적)

```text
달이 끝남 → `우리`에 그 달 블록이 생김 → 다시 보기 → (나중에) 기억 상품
```

**월 1회, 앱이 먼저 말을 걸지 않는다.** 열었을 때 거기 있다. 알림으로 밀지 않는 이유는
§1.1 — 달이 바뀐 것은 상대가 한 행위가 아니다.

### 4.3 관계 (마일스톤)

`milestones.ts`가 이미 있다. 100일 · 첫 휴가 · 1주년 · **전역**.

#### 전역을 절벽이 아니라 정점으로 설계한다

```text
전역일 = 비대칭 시간이 해소되는 날
       = 이 제품의 존재 이유가 사라지는 날
       = 축적된 것의 가치가 최대인 날
```

세 문장이 같은 날을 가리킨다. 지금 구조에서 전역은 **이탈일**이다.

```text
┌──────────────────────────────────────┐
   함께 기다린 546일                     
   기록 1,204개 · 사진 387장             
   면회 9번 · 휴가 4번                   
                                        
   [ 우리의 546일 다시 보기 ]            
└──────────────────────────────────────┘
```

`BUSINESS_MEMORY_ROADMAP` §9.2는 마일스톤 후보로 `100일·첫 휴가·1주년·전역`을
나열한다. **전역을 1순위로 볼 것을 제안한다.** 서비스 관계가 자연히 끝나는 지점이고,
그때 그 아카이브가 가장 귀하다. 다만 이것은 **가설이며 M7이 검증할 대상**이다 —
지금 가격이나 전환율을 쓰지 않는다.

### 4.4 하지 않는 것

| 금지 | 왜 |
|---|---|
| 연속 기록 · 스트릭 | §16 비목표. 그리고 §1.1이 구조적으로 막는다 |
| `N일째 기록이 없어요` | 부재는 이벤트가 아니다 |
| 매일 질문 강제 | §17 — SumOne 루프를 복제하지 않는다 |
| 리인게이지먼트 알림 | 상대가 한 행위가 아니다 |
| 관계 점수 · 애정도 | §15·§16 |
| 체류시간 KPI | 사업문서 §10 |

**리텐션은 알림 빈도가 아니라 쌓인 것의 가치에서 나온다.** 이 단계 전체가 그 명제에
걸려 있다.

## 5. 사용자 여정 — 처음부터 전역까지

```text
설치
  └ 첫 화면: 문제를 말하고, 상대가 필요하다는 걸 알리고, 동의 후 로그인

역할 · 닉네임 · 공간 생성
  └ 초대코드

⟨ 대기 ⟩                                    ← 지금은 죽은 구간
  └ 혼자서도 기록할 수 있다
  └ 연결되는 순간: "연결 전에 남긴 기록을 보여줄까요?"  (명시적 선택, 자동 공개 금지)

연결 성립
  └ 여기서 알림 권한을 묻는다               ← §1.5

일상 루프  ─────────────────────────────
  곰신: 남긴다 → 오늘 남긴 것에서 확인
  군화: 알림 → 브리핑 → 원본 → 이야기거리 → 통화 모드 → 이야기했어요

월 단위  ───────────────────────────────
  우리 탭에 달 블록이 쌓인다 → 다시 보기

마일스톤  ─────────────────────────────
  100일 · 첫 휴가 · 1주년

전역  ─────────────────────────────────
  함께 기다린 N일 → 전체 아카이브 → (M7) 기억 상품
```

## 6. 구현 순서와 의존

```text
1. Push                    루프의 첫 이벤트
   ├ 보안 review + migration gate
   └ 해제(§1.6)를 같은 단계에서. 나중으로 미루지 않는다

2. 역할별 홈               push가 데려오는 곳
   └ 1 이후여야 의미가 있다

3. 통화 모드               루프의 마지막 화살표
   └ 2의 이야기거리 위에 올라간다

4. 연결 대기 구간          커플 연결 완료율(KPI 1)
   └ 1·2와 독립. 병행 가능

5. 우리 = 축적             MediaArchiveGrid 이동 + 달 블록
   └ 독립. 다만 1·2 없이 하면 아무도 도착하지 않는 아카이브가 된다

6. 이 달 다시 보기         P-MP의 선행 구조
   └ 5 이후
```

## 7. 이 설계가 스스로에게 거는 검증

각 항목은 LV에서 측정 가능해야 한다(§19 허용 목록 안에서).

| 무엇을 고쳤다고 주장하는가 | 어떻게 반증하는가 |
|---|---|
| push가 루프를 시작시킨다 | 알림 → 앱 열기 전환. 열지 않으면 실패 |
| 브리핑이 원본으로 이어진다 | 요약 → 원본 이동률 |
| 통화 모드가 루프를 닫는다 | `이야기했어요` 완료율. 안 오르면 마찰이 원인이 아니었다 |
| 축적이 리텐션을 만든다 | 4주 커플 재사용률, `우리` 재방문 |
| 알림이 압박이 아니다 | **알림 끄기 비율.** 오르면 설계가 틀린 것이다 |

마지막 줄이 가장 중요하다. **알림을 끄는 사람이 늘면 §1의 규칙이 부족했다는 뜻**이고,
그때는 빈도를 줄이는 것이 아니라 규칙을 다시 본다.

## 8. Gate와 canonical 개정

### 8.1 보안·migration gate 필수

| 항목 | 이유 |
|---|---|
| `device_push_tokens` + RLS | 새 테이블, 새 개인 식별 데이터 |
| `couple_members`의 `has_unseen` | 기존 보안 테이블 변경 |
| 발신 Edge Function | 새 service-role 경로 |
| **해제 시 토큰 무효화** | §14.4 계약. negative test 필수 |

`gomsin-security-review` + `gomsin-migration-gate`를 거친다.
**migration 번호는 048 이상**(047이 이미 review 대기 중이다).

### 8.2 canonical 개정이 선행되어야 하는 것

| 제안 | 대상 | 무엇을 |
|---|---|---|
| 역할별 홈 | `PRODUCT_V3` §5·§6 | §6.1의 "한 표면"을 역할별로 해석하는 근거 |
| 알림 정책 | `PRODUCT_V3` §14.3 | §1.1의 행위/관찰 구분, 하루 1회, 단일 문구를 명문화 |
| 대기 중 기록의 사후 공개 | 신규 명세 | §14.2의 네 항목 |
| 통화 모드 | `PRODUCT_V3` §8 | `이야기했어요` 완료 경로 추가 |
| 전역을 1순위 마일스톤으로 | `BUSINESS_MEMORY_ROADMAP` §9.2 | 가설로 표기 |

### 8.3 이 설계가 건드리지 않는 것

키 계층(PMK/CSK/HRK) · envelope · device bootstrap · RLS 기존 정책 ·
주기 도메인 · `generateDailySummary`의 결정성 · PartnerDay state semantics ·
5탭 · 감정 시스템(동결, LV에서 측정).

## 9. 이 문서의 지위

- 설계 제안이며 canonical이 아니다. 충돌 항목은 §8.2가 소유한다.
- 구현하지 않았고, 원격·Production 상태를 확인하거나 변경하지 않았다.
- §4.3의 전역 관련 사업 판단은 **검증 대상 가설**이며 수치를 쓰지 않았다.
