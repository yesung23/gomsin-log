## 2. 감사 결과 — 실제 결함 4개

### D1. 기계 추론이 사용자의 확정 감정으로 저장된다 *(가장 심각)*

`candidatesToFlowItems()`는 살아남은 모든 후보에 `source: 'user_confirmed'`를 **하드코딩**한다.

```ts
// src/lib/emotionCandidates.ts:200
source: 'user_confirmed' as const,
```

사용자가 감정 UI를 한 번도 건드리지 않고 저장해도 기계의 추측이 `user_confirmed`로
기록된다. `emotionFlowForStorage()`가 `source === 'user_confirmed'`로 거르지만, 쓰는
쪽이 전부 `user_confirmed`로 도장을 찍으므로 그 필터는 무력하다. `privacy.ts:88`의
주석이 이 위험을 이미 지적하고 있다 — "a convention, not an invariant".

결과:
- 작성자 본인에게도 자기가 확정한 감정처럼 되돌아온다 (`RecordMoodSection`, `TodayLogWidget` 타임라인)
- `이 마음도 함께 보여주기`를 켜면 **검토조차 하지 않은 기계 추측이 파트너에게 간다**

`PRODUCT_V3.md` §13 위반이자 사용자가 지목한 바로 그 문제다.

### D2. 작성 중에 추론이 돈다

`useEmotionCandidatesForText(debouncedLog)` — 300ms 디바운스는 있지만 **타이핑을 멈출
때마다** 전체 본문에 대해 어휘 스캔 + 절 분할이 다시 돈다. 긴 기록에서는 입력 중
반복 계산이고, 무엇보다 **문장이 끝나기 전에 판정**한다. `무서운 영화` 같은 케이스는
문장이 완성되어야 구분되므로, 작성 중 판정은 사용자에게 틀린 감정이 실시간으로
깜빡이는 것을 보여준다.

### D3. 감정 시각언어가 두 개다

같은 앱에서 감정이 두 가지로 그려진다.

| 화면 | 표현 |
|---|---|
| 기록 상세 `기록 속 마음` | 오리지널 캐릭터 6종 |
| 작성 중 컴포저 | **시스템 이모지** 😊😮😨😣😡😢 |
| 상대 감정 위젯 | **시스템 이모지** |

시스템 이모지는 기기·OS 버전마다 다르게 그려지므로 곰신로그의 감정 언어가 될 수 없다.

### D4. 배려 신호에 전송 전 preview가 없다

주기 *공유 설정*에는 `군화에게 이렇게 보여요` / `이건 보이지 않아요` 두 블록이 있다.
그러나 **배려 신호 컴포저에는 없다.** 사용자는 선택지 카드와 메시지 입력칸만 보고
전송하며, 상대 화면에 무엇이 어떻게 뜨는지는 보낸 뒤에야 안다.

## 3. AI TIMING — 추론을 언제 돌릴 것인가

사용자가 제시한 6개 후보를 실제 비용으로 비교한다.

| 시점 | UX | 배터리·발열 | latency | privacy | 모델 정확도 |
|---|---|---|---|---|---|
| ① 기록 직후 즉시(키 입력마다) | 최악 — 글자마다 결과가 바뀜 | 최악 — 입력 길이×횟수 | 0 | 동일 | 최악 — 미완성 문장 |
| ② 타이핑 멈춘 뒤 idle **(현재)** | 나쁨 — 작성 중 결과가 흔들림 | 나쁨 | 0 | 동일 | 나쁨 — 미완성 문장 |
| ③ **저장 버튼을 누른 뒤** | **좋음 — 작성을 방해하지 않음** | **최선 — 기록당 정확히 1회** | 1프레임 | 동일 | **최선 — 완성된 문장** |
| ④ 하루가 끝난 뒤 묶어서 | 나쁨 — 그날 확인 못 함 | 좋음 | 최대 24h | 동일 | 문맥은 넓지만 개별 기록 귀속이 흐려짐 |
| ⑤ 상대가 폰을 받기 직전 예측 | — | 낭비 | — | **불가 — 아래 참조** | — |
| ⑥ 충전 중·백그라운드 idle | 무거운 작업에 적합 | 최선 | 지연 큼 | 동일 | — |

### 결정: ③ 저장 경계가 V1의 유일한 추론 시점

이유:

1. **저장은 사용자가 "이 기록은 끝났다"고 선언하는 유일한 지점이다.** 그 전에는 어떤
   문장도 완성되었다고 가정할 수 없다.
2. **비용이 기록 수에 비례하고 글자 수에 비례하지 않는다.** ②는 긴 기록일수록
   기하급수적으로 비싸진다.
3. **작성 중 감정을 읽어 보여주는 것은 그 자체로 불쾌하다.** 일기를 쓰는 중에 앱이
   "지금 화나셨네요"를 실시간으로 갱신하면, 그것이 로컬 계산이라는 사실과 무관하게
   감시받는 느낌을 만든다.

무거운 작업은 ⑥(idle/charging)으로 미룬다. **다만 V1에는 무거운 작업이 없다** (§4).

### ⑤ "군화가 폰을 받기 직전 미리 처리" — 기각

사용자가 직접 판단을 요청한 항목이다. **하면 안 된다.**

1. **그 시점을 알려면 상대의 접속 패턴을 추적·모델링해야 한다.** `PRODUCT_V3.md` §19가
   명시적으로 금지하는 행동 감시이고, §16 비목표의 `접속 감시`에 해당한다. 원칙 6
   "불안을 만들지 않는다 — 접속 감시를 만들지 않는다"와 정면 충돌한다.
2. **애초에 미리 만들 대상이 없다.** `상대방의 오늘` 요약은 이미 결정적 로컬 계산이고
   §6.2는 요약에 LLM을 **금지**한다. 기다릴 계산이 존재하지 않는다.
3. **미리 만들면 오히려 나빠진다.** 서버 저장은 §14.3 위반이고, 기기 캐시는
   `CURRENT_STATE.md` §6이 "확인된 좋은 설계"로 지목한 *"요약이 캐시되지 않아 stale이
   구조적으로 존재하지 않는다"* 를 깨뜨린다. 원본이 수정·삭제되면 캐시가 거짓말을 한다.

**더 안전한 대안:** 아무것도 예측하지 않는다. 기다림의 원인은 계산이 아니라
**네트워크**이므로, 미리 준비할 것은 요약이 아니라 **데이터**다 — 이미 도착한 기록에
대해 요약은 항상 즉시 계산된다.

### 재추론 방지

같은 내용을 다시 읽지 않는다. 본문의 정규화 해시가 같으면 이전 결과를 그대로
재사용하고, 사용자가 손댄 항목(`userEdited`)은 어떤 재분석도 덮어쓰지 않는다.

## 4. 온디바이스 AI — 무엇이 실제로 필요한가

### 필요한 AI 작업의 재정의

| 작업 | 모델이 필요한가 | 판정 |
|---|---|---|
| `상대방의 오늘` 요약 | **금지** — §6.2 "결정적으로. 난수·시계 의존 문구·LLM 금지" | 결정적 규칙만 |
| 기록에서 감정 읽기 | 선택 | 현재 결정적 어휘 엔진으로 충분 |
| 기억상품 편집 보조 | 있으면 좋음 | **P-MP / M6 영역, V1 범위 밖** |
| 검색 | — | 서버 전문검색은 어떤 버전에서도 약속하지 않음(§17) |

### 결정: V1은 신경망 모델을 탑재하지 않는다

정직한 계산:

- 요약은 LLM이 **금지**되어 있으므로 후보에서 제외된다.
- 남는 후보는 감정 6분류 하나뿐인데, 현재 결정적 어휘 엔진이 **0 MB 다운로드,
  0 MB 상주 RAM, 1 ms 미만, 완전 오프라인**으로 처리한다.
- 실용 가능한 가장 작은 대안(4-bit 양자화 0.5B급)조차 수백 MB 다운로드와 수백 MB~1 GB
  상주 RAM, 첫 응답까지 수백 ms, 지속 사용 시 발열을 요구한다. **감정 6분류 하나를 위해
  구형 iPhone과 보급형 갤럭시가 지불할 비용이 아니다.**
- 결정적으로, **비결정성이 §6.2를 위반하고 "수정이 유지된다"는 성질을 깨뜨린다.**
  같은 기록을 두 번 열었을 때 다른 감정이 나오면 사용자의 교정이 무의미해진다.

`BUSINESS_MEMORY_ROADMAP_V1.md`도 온디바이스 AI 실증을 **M6**에 두고 있고, M6는
M3(LV)·M5 이후다. 지금 모델을 넣는 것은 세 단계를 건너뛰는 것이다.

### 그래도 만드는 것: capability tier와 스케줄러

모델을 넣지 않는다고 구조까지 없을 이유는 없다. 세 tier를 **지금** 정의하고 현재는
셋 다 결정적 엔진으로 매핑한다. M6에서 모델이 검증되면 tier 하나만 갈아 끼운다.

```text
full     — 여유 있는 기기. 향후 온디바이스 모델 슬롯
compact  — 중간 기기. 향후 축소 모델 슬롯
rules    — 저사양·저전력·미지원. 결정적 엔진
             ↑ V1에서는 세 tier 모두 여기로 매핑된다
```

tier 판정에 쓰는 신호는 **실측 가능한 것만**:
`navigator.deviceMemory` · `hardwareConcurrency` · native 여부 · 저전력 모드/충전 상태.
**기기 모델명 fingerprinting은 쓰지 않는다** — 그 자체가 추적 식별자다.

## 5. 주기 / 배려 공유

### 통증 공유 — 요청 그대로 구현하지 않는다

사용자 요청: *"통증은 사용자가 명시적으로 선택했을 때만 공유"*.

`PRODUCT_V3.md` §21은 **"증상·출혈량·통증·기분·메모는 어떤 설정에서도 공유되지
않는다"** 고 못 박고 있다. 이를 뒤집으려면 §23에 따라 canonical 문서를 먼저 개정해야
한다.

**그럴 필요가 없다.** 같은 의도를 위반 없이, 더 낫게 달성하는 경로가 이미 있다.

| | HRK projection에 통증 추가 *(요청 문자 그대로)* | 배려 신호로 표현 *(채택)* |
|---|---|---|
| §21 | 위반 — canonical 개정 필요 | 위반 없음 |
| HRK 경계 | 건강 원본이 CSK로 넘어가는 경로가 새로 생긴다 | 경계 그대로 |
| 주기를 안 쓰는 사용자 | 쓸 수 없다 | **똑같이 쓸 수 있다** |
| 표현력 | `severe` 같은 enum 하나 | 사용자가 고른 종류 + 자기 문장 |
| 철회 | 설정 토글 | 당일 만료 + 즉시 철회 |

배려 신호는 이미 **주기에서 파생되지 않는 독립 opt-in 신호**이고, 이는
`CURRENT_STATE.md` §6이 "되돌리지 말 것"으로 지목한 설계다. 통증을 여기에 태우면
HRK 경계를 건드리지 않고 사용자 의도를 100% 만족한다.

→ 새 종류 하나를 추가한다: **`feeling_unwell` — "오늘은 몸이 힘들어요"**.
   나머지 3종(쉬고 싶어요 / 챙겨줬으면 / 나중에 확인해줘)은 이미 존재한다.

> **이것은 migration을 요구한다.** `cycle_support_signals.kind`에 CHECK 제약이 있다
> (migration 014). §7의 gate 분리를 따른다.

### 전송 전 preview

배려 신호 컴포저에 **상대 화면 그대로의 preview**를 넣는다. 설정 화면의
`이렇게 보여요` / `이건 보이지 않아요` 두 블록 문법을 그대로 재사용해, 앱 안에서
프라이버시를 설명하는 방식이 한 가지가 되게 한다.

## 6. 감정 UX

### suggestion과 확정을 분리한다

```text
기계가 읽은 것   → source: 'rule_suggested'  → 저장되지 않는다. 파트너에게 가지 않는다
사람이 누른 것   → source: 'user_confirmed'  → 저장된다. 공유는 여전히 별도 행위
```

`이렇게 느꼈나요?`는 **저장 직후** 묻는다. 작성 중이 아니다(§3).
확인은 한 번의 탭, 변경도 한 번의 탭, 무시하면 아무것도 저장되지 않는다.

무시했을 때 아무것도 저장되지 않는 것이 손실처럼 보일 수 있다. 그러나 그 대안은
**사람이 확인하지 않은 추측을 그 사람의 감정으로 기록하는 것**이며, 그것이 D1이다.

### 시각언어 통일

시스템 이모지를 전부 오리지널 캐릭터로 교체한다. 캐릭터는 이미 있고,
실루엣이 1차 신호이므로 무채색·소형에서도 구분된다.

### AI가 하지 않는 것 (코드로 보장)

숨은 감정 단정 · 관계점수 · 애정도 · 상대 마음 추측 · 이별 예측 · 중요 기록 자동 선정 —
**어느 것도 코드에 존재하지 않으며, 이번 작업에서 추가하지 않는다.**

## 8. 저장 / 크로스플랫폼 — 방향만 확정, 구현하지 않음

사용자 질문: iPhone+iPhone / Galaxy+Galaxy / iPhone+Galaxy가 모두 자연스럽게 동작해야 함.

**이미 결정되어 있고 그 결정이 옳다.** ARCH-P6(`ENGINEERING_ROADMAP.md` §2)는
`Supabase는 coordination metadata only`, `uploader-owned CloudKit private DB`,
`Android boundary intentionally deferred`로 정리되어 있다. 핵심은:

> **커플 공유·E2EE의 canonical 구조는 이미 크로스플랫폼이다.** 키 계층(PMK/CSK/HRK),
> envelope, device bootstrap, RLS는 전부 Supabase + WebCrypto 위에 있고 Apple에
> 종속되어 있지 않다. iCloud는 **미디어 blob의 저장 위치 후보**일 뿐이며 공유 구조가
> 아니다.

따라서 세 조합은 다음과 같이 동작한다.

```text
iPhone + iPhone   미디어는 각자의 iCloud, 공유는 CSK + Supabase 조율
Galaxy + Galaxy   미디어는 대체 저장 계층, 공유는 동일한 CSK + Supabase 조율
iPhone + Galaxy   업로더의 저장 계층이 서로 달라도 조율·복호 경로는 같다
```

**"특정 회사 클라우드에 커플 공유 데이터 구조 전체를 종속시키지 마"** 는 요청은
현재 아키텍처가 이미 만족한다. 이번 작업에서 바꿀 것이 없고, 바꾸면 안 된다.

기기 변경·재설치·새 기기·복구·연결 해제·계정 삭제는 P5.2 Device Bootstrap과 §14.4
계약이 이미 소유한다. 실기기 검증은 여전히 `UNVERIFIED`이며 이번 작업이 그것을
바꾸지 않는다.
