## A. 이번에 새로 요청받은 것 (2026-08-23)

### A1. 탭 `+` = 스토리와 게시물을 조합한 **나만의 일기장**

지금 `+`는 컴포저(`/compose`)다. 요청은 **엮는 화면**이다 — 그날의 스토리와 게시물을
골라 한 지면으로 만드는 것.

`일기장`(`/diary`)이 이미 월 단위로 그 일을 하지만 **자동으로 엮기만** 하고 고르지
못한다. 둘을 합쳐야 한다: 자동으로 엮어 오되 무엇을 넣고 뺄지는 사용자가 정한다.

- 남는 질문: 컴포저는 어디로 가는가. 홈 레일의 `+`와 `우리`·`찾기`의 펜이 이미 §7.1을
  지고 있으므로 탭에서 빠져도 계약은 깨지지 않는다
- 영향: `PRODUCT_V3` §5 탭 표 개정 필요
- 상태: **NOT BUILT**

### A2. `우리` 탭의 격자 = 캘린더가 아니라 **게시물**

> **요청 원문:** "마이탭에는 캘린더가 아니라 게시물(본인이 원하는 사진과 글을 쓸 수 있게
> 함, 인스타그램의 게시물과 동일)하게 만들어"

로컬 출시 후보의 `우리` 헤더 왼쪽 `+`는 기기 사진, 여행 사진, 공유 스토리 사진을 골라
순서를 바꾸고 글·공개 범위를 정하는 3단계 게시물 작성기를 연다. 게시물은 기존
`daily_records`와 Storage 경로를 재사용하며, 사진이 모두 저장된 마지막 업데이트에서만
명시적 발행 표시를 남긴다. 첫 탭은 그 기록만 3열 격자로 보여 주고, 일반 스토리 사진은
자동으로 들어오지 않는다. 타일은 동일 record ID의 상세와 원본으로 이어진다.

- 기존 공유 사진은 사용자의 발행 의도를 알 수 없으므로 추측 backfill하지 않는다. 구버전은
  모든 공유 사진을 계속 격자에 보여 줄 수 있어 DB-first 적용 뒤 앱 업데이트가 필요하다
- 하이라이트는 게시물 격자와 독립된 커플 데이터다. 새 하이라이트 편집기에서 격자의
  사진을 고르거나 공유 사진 스토리의 `하이라이트에 추가` 동작으로 편집기를 열 수 있다.
  현재 모델이 기록 ID를 저장하므로 다중 첨부 기록의 특정 두 번째 사진만 단독으로 고르는
  기능은 별도 미디어 항목 모델 없이는 만들지 않는다
- `사진` 탭은 기존의 기록 중심 목록(내용·미디어·상세·타임라인)을 담당하고, `여행` 탭은
  현재·예정·지난 여행을 최대 세 개까지 간단히 보여준 뒤 카드 상세와 `/trips` 전체 보기로
  이어진다
- 상태: **LOCAL IMPLEMENTED / PRODUCTION HOLD** (2026-08-28, migration 067 원격 미적용,
  실제 두 계정·두 기기 동기화 미검증)

### A3. `찾기` 탭에 역할별 정보

> **요청 원문:** "찾기 탭에는 군화는 군 관련 정보들을 넣고, 곰신은 생리주기 체크 및
> 상대방에게 공유 기능을 넣어줘"

그 내용은 이미 `/me`(오늘 내 상태)에 다 있다 — 복무 현황·연락 가능 시간·주기·배려
신호. 지금은 `우리`의 칩으로만 닿는다. 요청은 그것을 **`찾기` 탭으로** 올리는 것.

- 검색어가 없을 때 군화는 복무·연락 가능 시간·다음 휴가/면회를, 곰신은 기존 주기 표면을
  먼저 본다. 검색어를 입력하면 기존 날짜/내용 검색 결과만 보여준다
- 군화의 복무 카드에는 입력 날짜 기반 1초=1 EXP, 실시간 퍼센트, 내부 Lv.200 EXP와
  사용자에게 보이는 7단계 복무 레벨(신병·일초·일꺾·일말·상초·상꺾·왕고)이 추가되었다.
  기본 화면에는 현재 레벨과 실시간 EXP만 두고, 전체 단계는 44px `전체 단계` disclosure를
  눌렀을 때만 펼친다.
  2026-08-26 업데이트로 실시간 EXP 게이지 및 수치 표시는 7개 티어 경계(0/10/25/40/55/70/85/100%)마다
  0으로 리셋되어 해당 티어 내 달성도(0→100%)를 보여주며, 전체 누적 복무율은 요약에 독립 유지된다.
  꺾이는 단계에는 전환 번개 연출을, 왕고에는 카드 내부 왕관 강조를 사용한다. 실제
  행정 진급·관계 점수·보상·닉네임 등급으로 해석하지 않는다 (실제 입대일/전역일 기준 및 관계 점수 미포함 유지)
- 곰신에게 상대 복무 정보를 보여줄 위치는 **찾기 탭 검색창 아래, 주기 표면 앞의
  `상대 복무` 카드**다. 로컬 작업 트리에 active couple 대상의 읽기 전용 sanitized allowlist RPC(`get_partner_service_info`, migration 063), `sync.ts` 연동, 수정 버튼이 없는 읽기 전용 `SearchPage` UI가 구현되어 집중 로컬 테스트를 통과했다. 실제 입대일·전역일 기준 날짜 계산만 사용하고 관계·애정도 점수는 없으며, 메모를 제외한 읽기 전용 허용목록만 프로젝션된다.
  단, migration 063은 LOCAL FILE ONLY로 원격 프로덕션 Supabase에 NOT APPLIED 상태이며,
  원격 Supabase 및 physical iPhone 동작은 UNVERIFIED 상태다(미배포·미출시).
- 상태: **군화 표시형 V1.1 (티어별 EXP 리셋 및 복무율 분리) DONE (2026-08-26)** / **곰신 상대 복무 projection 로컬 구현 및 집중 테스트 PASS (2026-08-26)**
  - 백로그 잔여 게이트: migration 063 원격 프로덕션 Supabase 적용(LOCAL FILE ONLY / NOT APPLIED), 원격 실환경 real actor 권한 검증, physical iPhone 실기기 검증(UNVERIFIED), 릴리즈/배포 게이트

### A4. 일정 — 여러 개를 한 번에

- 데이터: 흩어진 날 N개는 이벤트 N건이다. 같은 제목·종류로 한 번에 만들면 된다
- 상태: **DONE** (2026-08-23). 끌면 구간이 더해지고 톡 누르면 그 하루가 켜지고 꺼진다.
  저장할 때 `groupIntoRuns` 가 연속 구간으로 잘라 **구간 하나가 일정 하나**가 된다 --
  붙은 날은 기간 하나로, 흩어진 날은 각각 하루로. 일부만 성공하면 몇 건이 되었는지
  그대로 말한다

### A5. 일정 — 시간 입력이 깨지던 것 ✅ DONE

`우리 할 일 빠르게 추가`가 `flex-1`로 남는 폭을 다 먹어 시간 입력이 80px에 갇혔다.

두 줄로 나눴다 — 제목이 한 줄, 시간과 버튼이 아래 줄. 시간에 최소 폭 `7.5rem`과

- 상태: **DONE** (2026-08-23)

### A7. iPhone 온디바이스 하루 요약 보조

- 상태: **IMPLEMENTED / DEFAULT-ON ON SUPPORTED iOS / MANUAL STORY TRIGGER / PHYSICAL DEVICE UNVERIFIED**
- 상대의 오늘 적격 기록 전체를 시간순으로 유지하고 처음 5개만 보여 준다. 나머지는
  `N개 더 보기`로 펼친다. 스토리를 여는 것만으로 모델을 자동 실행하지 않고, 표지의
  `AI로 다듬기`를 누르면 Apple Foundation Models가 5개 고정 배치에서 문장 표현만 즉시
  다듬는다. AI가 중요한 기록을 고르거나 감정·관계·건강을 추론하지 않는다.
- 기본 ON은 **지원되는 iOS native에서 기능을 사용할 수 있다는 뜻**이다. 웹·Android·미지원
  iPhone에는 AI 버튼/모델 경로가 없고, `false|0|off`는 긴급 kill switch다.
- timeout, 취소, 검증 실패, malformed output이면 이미 화면에 있던 규칙 요약을 그대로 유지한다.
- Xcode 26.6 iOS Simulator build는 PASS. 남은 gate는 Apple Intelligence 지원 **실물 iPhone**의
  한국어 품질, airplane mode 네트워크 0, cold/warm latency, 발열·배터리, 화면 이탈 취소다.
- Google Play 출시는 현재 출시 범위가 아니다. Android는 기존 웹/PWA를 유지한다.

## F. 최적화 — gpt-5.6-sol 전수 검토 (2026-08-23)

새 코드 넷은 전부 통과했다(결함 없음). 아래는 저장소 전체에 대한 지적 중 **남은 것**이다.
`signalsFrom` 통합은 지었다.

### F1. `select('*')` — 값은 페이로드가 아니라 **드리프트를 일찍 잡는 것**

sol 은 "페이로드 5–15% 감소" 로 값을 매겼지만, 이 저장소는 이미 다른 이유로 다쳤다.
`sync.ts:139` 의 주석이 그것을 기록한다 — `select('*')` 가 **`military_info` 를 잃은
운영 스키마를 조용히 받아들여** 로그인은 성공하고, 실패는 사용자가 복무 정보를 저장할
때까지 미뤄졌다. 컬럼을 적어 두면 그 순간 쿼리가 실패한다.

남은 자리: `events.ts:28` · `records.ts:256` · `tasks.ts:37` · `trips.ts:176,194,281` ·
`sync.ts:180,210`.

**짓기 전에 필요한 것:** 컬럼을 손으로 나열하다 하나 빠뜨리면 그 필드가 조용히
`undefined` 가 된다 -- 과다 페치보다 나쁘다. 각 함수의 row 매퍼가 읽는 컬럼과 `select`
목록이 일치하는지 **실행해서 확인하는 테스트**를 먼저 붙인다. 그 테스트 없이 하는
치환은 이 항목이 막으려는 결함을 그대로 만든다.

### F2. 정렬 안에서 `new Date()` — `RecordPage.tsx:371`

비교 함수 안에서 매번 Date 를 만든다. 하루 기록이 100건을 넘으면 재는 값이 나온다.
정렬 전에 키를 한 번 뽑으면 된다. **먼저 재고 고친다** -- 지금은 그 정도 기록을 가진
커플이 있는지 모른다.

### F3. 마운트되지 않는 위젯 트리 (~1,080줄)

`RoleHome` 480줄 + 위젯 생태계 ~600줄. 번들에는 안 들어간다(어느 라우트도 참조하지
않아 트리셰이킹된다). **지우지 않는다** -- `CURRENT_STATE.md` §4가 되돌릴 자리를
기록해 두고 있다. 되돌리지 않기로 정해지면 그때 지운다.

### F4. 번들 645 kB (gzip 193 kB)

Supabase 218 kB + React 50 kB + 앱 코드. sol 의 권고는 **운영에서 먼저 재라**는 것이고
그 판단이 옳다. 4G 에서 ~1.4초이며, 첫 페인트가 이미 괜찮다면 손댈 값이 아니다.
