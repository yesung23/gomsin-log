# 곰신로그 구현 청사진 (implementation_blueprint.md)

이 문서는 `yesung23/gomsin-log` 저장소(master, 2026-07-28 시점)의 실제 파일을 읽고 작성한 구현 지시서다.
다른 구현 AI는 이 문서를 단독 기준으로 삼되, **저장소에서 직접 확인되지 않은 항목은 "확인 필요"로 표기했으므로 임의 추정으로 구현하지 않는다.**

핵심 전제:
- Supabase는 이미 구축되어 있다. **재구축 금지, 감사·재사용·보완만 한다.**
- `supabase/migrations/001~004`는 **절대 수정하지 않는다.** 모든 DB 변경은 `005` 이후 신규 마이그레이션으로만 한다.
- 외부 AI API, 서버 LLM, 로컬 ML은 **사용하지 않는다.** 감정은 한국어 규칙 사전 기반 최대 3개 후보 + 작성자 직접 확정만 저장한다.
- `is_private = true` 기록은 작성자 외 어떤 경로로도 노출되지 않는다(상대 홈·요약·감정·힌트·캘린더·알림·Realtime·Signed URL 전부).

## 1. 실제 구현 현황

### 1.1 스택과 규모
React 19 + TypeScript + Vite 6 + Tailwind CSS v4 + React Router v7, `@supabase/supabase-js` v2, `lucide-react`, `sonner`, `date-fns`, `@dnd-kit`(위젯 정렬용). 테스트는 `vitest`(`npm test`)로 구성되어 있고 `src/lib/briefing.test.ts`, `src/lib/utils.test.ts`, `src/lib/__tests__/emotionRuleEngine.test.ts`가 존재한다. 소스는 약 44개 파일, 약 9,800줄이다.

### 1.2 이미 잘 되어 있는 것 (재사용 대상)
- **4탭 하단 셸**: `src/components/MobileShell.tsx`가 홈/기록/우리/마이 4탭을 `role="tablist"`, `aria-selected`, 최소 48px 터치 타깃, safe-area 패딩으로 구현했다. 확정 원칙과 일치한다.
- **역할 분기 홈**: `src/pages/HomePage.tsx`가 `profile.role`로 `WidgetDashboard`(곰신)와 `SoldierDashboard`(군화)를 분기한다.
- **규칙 기반 브리핑 엔진**: `src/lib/briefing.ts`에 이미 완성도 높은 구현이 있다. `generateDailySummary`는 private 기록을 입력에서 제외하고, 각 요약 항목에 근거 `recordIds`를 함께 반환하며, 공유 기록이 2개 미만이면 카드를 생략하고, 3개 이하면 1개·4개 이상이면 최대 3개로 항목 수를 제한한다. `generateEmotionFlowBriefing`은 `source === 'user_confirmed'`이고 `visibility === 'shared'`인 감정만 `sequence` 순으로 이어 "오늘의 마음: A → B" 문장을 만든다.
- **규칙 감정 엔진**: `src/lib/emotionRuleEngine.ts`의 `recommendEmotionFlow`가 한국어 정규화 후 최대 3개 후보만 반환하고, `src/lib/aiEmotion.ts`는 외부 호출 없이 이 엔진을 감싸는 순수 어댑터다. 원칙과 일치한다.
- **기록 화면 골격**: `src/pages/RecordPage.tsx`가 월간 캘린더 토글 + 날짜별 타임라인 + 미디어 필터 + 상세 시트를 갖췄고, 상대 기록 중 `isPrivate`인 항목을 목록 계산 단계에서 제외한다. 또한 `state.highlightedRecordId`를 읽어 해당 카드로 스크롤·하이라이트하고 일정 시간 후 해제하는 로직이 이미 있다.
- **생리주기**: `src/lib/cycle.ts`는 세션 사용자 기준 owner-only CRUD만 제공하고, `004_create_cycle_tables.sql`의 RLS도 owner-only다. 브리핑·감정·Realtime 어디에도 연결돼 있지 않다. **현 상태가 정답이며 건드리지 않는다.**
- **여행 데이터 계층**: `src/lib/trips.ts`가 trips / trip_items / trip_checklists CRUD를 제공한다. 지도·장소 검색·예약·결제 연동은 없다(원칙과 일치).

### 1.3 원칙과 충돌하거나 미완인 것 (이번 구현의 실제 과제)
1. **군화 홈이 목업이다.** `src/features/home/SoldierDashboard.tsx`는 에너지 수치, 한 줄 요약, 배려 힌트, 키워드를 **하드코딩된 목 데이터**로 렌더링하며 `lib/briefing.ts`를 전혀 호출하지 않는다. 즉 화면에 보이는 요약이 실제 공유 기록에 근거하지 않는다 — 제품 원칙 위반이자 최우선 수정 대상이다.
2. **요약 → 근거 이동이 끊겨 있다.** 한 줄 요약을 탭하면 `/record`로 이동만 하고 근거 `recordId`를 전달하지 않는다. 반대편 수신 로직(`highlightedRecordId`)은 이미 있으므로 **전달만 연결하면 되는 최소 수정**이다.
3. **설정 진입 경로 불일치.** `WidgetDashboard.tsx`의 설정 버튼이 `/settings`가 아니라 `/my`로 이동한다. 알림 벨은 동작하지 않는다.
4. **커플 연결 해제가 로컬 전용이다.** `src/lib/store.tsx`의 `disconnect()`는 로컬 상태만 바꾸고 `disconnect_couple` RPC를 호출하지 않는다. 게다가 DB의 `disconnect_couple`은 호출자 본인 행의 status만 바꾸므로 상대는 `active`로 남아 **비대칭 접근**이 발생한다.
5. **개인 일정이 상대에게 노출된다.** `events` 테이블에 `visibility`와 `is_private` 컬럼이 둘 다 있는데 RLS는 커플 전체 `FOR ALL` 방식이라 컬럼이 무의미하다.
6. **레거시 잔존물.** 라우트에 `/schedule`(`pages/SchedulePage.tsx`)이 남아 있고, `features/home/GomshinHome.tsx`, `features/home/SoldierHome.tsx`, `pages/ServicePage.tsx`도 남아 있다. 4탭 정보구조와 중복된다.
7. **위젯 레지스트리 대부분이 정적 목업이다.** `src/lib/widgets.tsx`의 12개 위젯 중 실제 데이터에 연결된 것은 `TodayLogWidget`, `DDayWidget`, `UpcomingScheduleWidget` 정도다. 나머지(복무 진행률 45% 고정, 연락 가능 시간 18:00~21:00 고정, 오늘의 식단, 다음 기념일 D-45, 다음 휴가 D-12, 추억 다시보기, 오늘의 컨디션, 메모장)는 하드코딩 값이다. **특히 "오늘의 식단"은 부대 정보 성격이 있어 확정 원칙(부대 정보 비노출)과 충돌하므로 존치 여부에 사용자 승인이 필요하다(9절).**
8. **우리 탭 캘린더가 요구 수준에 못 미친다.** `pages/UsPage.tsx`는 월간 캘린더를 전면 배치했으나 점 표시가 "여행/일정" 2종뿐이고, D+N은 표시하되 **기념일·면회·휴가·외박 구분, 날짜 선택 시 하단 상세, 체크리스트 진입이 없다.** 여행 카드는 전체 목록을 그대로 나열한다(다가오는 여행 필터 없음).
9. **마이/설정 기능 상당수가 토스트 스텁이다.** `SettingsPage.tsx`의 프로필 편집·알림·생체잠금·내보내기·약관·개인정보처리방침이 토스트만 띄운다. `MyPage.tsx`에도 알림·PWA 스텁과 별도 연결 해제 모달이 중복 존재한다.
10. **localStorage에 전체 상태를 평문 저장한다.** `store.tsx`는 `gomsinlog.state.v1` 키로 **private 기록 본문을 포함한 앱 전체 상태**를 저장한다. 로그아웃 시 기본 상태로 덮어쓰긴 하나, 공용/분실 단말 리스크가 있다.

## 2. 아키텍처 결정

- **데이터 접근은 `src/lib/*` 계층에만 둔다.** 화면 컴포넌트가 `supabase` 클라이언트를 직접 호출하지 않는다. 현재 `records.ts`, `events.ts`, `trips.ts`, `cycle.ts`, `sync.ts`가 그 역할을 하며 이 경계를 유지·강화한다.
- **권한의 단일 진실 공급원은 RLS다.** 클라이언트 필터(예: RecordPage의 private 제외)는 UX용 2차 방어일 뿐이며, 클라이언트 필터가 있다는 이유로 RLS를 완화하지 않는다.
- **브리핑은 클라이언트 규칙 연산 결과를 화면에서 즉시 생성한다.** 외부 AI가 없으므로 비용·키 노출 이슈가 없고, `briefings` 테이블은 "동일 날짜 재계산 방지/이력 보존"이 필요해질 때만 쓴다(현재는 미사용 상태로 두는 것을 권장, 9절 승인 항목).
- **감정은 항상 제안 → 작성자 확정 2단계.** 저장되는 감정은 `source: 'user_confirmed'`만 브리핑에 사용한다. `rule_suggested` 상태는 상대에게 절대 노출하지 않는다.
- **생리주기는 독립 사일로.** `cycle_*` 테이블은 어떤 조인·브리핑·Realtime 채널·알림에도 포함하지 않는다. 화면상으로도 마이 탭(곰신 전용) 안에서만 읽고 쓴다.
- **오프라인 정책은 "읽기 관대, 쓰기 보수적".** localStorage 하이드레이션으로 마지막 상태를 보여주되, 쓰기 실패 시 낙관적 UI를 유지하지 말고 실패를 명시한다(현재 `addRecord`는 낙관적 반영 후 DB 저장을 시도하므로 실패 롤백 처리를 보완해야 한다).
- **레거시 화면은 삭제 대신 라우트에서 먼저 분리한다.** 삭제는 회귀 위험이 있으므로 라우트 제거 → 참조 없음 확인 → 파일 정리 순서로 진행한다.

## 3. 화면·상태 명세

### 3.1 홈 — 곰신 (`/home`, `features/home/WidgetDashboard.tsx`)
- **목적**: 곰신이 오늘의 기록을 남기도록 유도하고, 커플 공통 정보를 위젯으로 빠르게 확인한다.
- **구성**: 상단 인사/커플 요약, 설정 진입(→ `/settings`로 교정), 위젯 그리드(`lib/widgets.tsx` 레지스트리 + `@dnd-kit` 정렬, 레이아웃은 `setWidgetLayout`으로 저장).
- **정상**: 실제 데이터에 연결된 위젯만 노출한다. 목업 위젯은 실데이터 연결 전까지 레지스트리에서 제외하거나 "준비 중" 상태를 명시한다.
- **로딩**: 위젯 단위 스켈레톤. 전체 화면 스피너 금지(짧은 접속 시간 고려).
- **빈 상태**: 오늘 기록 0건이면 "오늘 하루 한 줄 남기기" 단일 CTA만 노출한다.
- **오류**: 위젯 개별 실패는 해당 카드만 "불러오지 못했어요 · 다시 시도"로 격리한다.
- **권한 없음(미연결)**: 커플 미연결 시 상대 관련 위젯 전부 숨기고 초대 코드 발급/입력 CTA만 노출한다.
- **오프라인**: 캐시된 값 + "마지막 동기화 시각" 배지. 쓰기 버튼은 비활성 대신 "연결되면 전송" 안내를 명시한다.
- **비노출 규칙**: 생리주기 관련 정보는 홈에 어떤 형태로도 등장하지 않는다.

### 3.2 홈 — 군화 (`/home`, `features/home/SoldierDashboard.tsx`)
- **목적**: 짧은 통화 전 30초 안에 곰신의 상태를 파악한다. **긴 타임라인 금지.**
- **구성(확정 순서)**: "오늘 통화 전, 이것만 알아두세요" 헤더 → ① 곰신의 에너지 → ② 오늘의 한 줄 요약 → ③ 오늘의 배려 힌트. 그 아래에는 카드 3개를 넘는 목록을 두지 않는다.
- **데이터 근거**: 세 항목 모두 `lib/briefing.ts`의 실제 계산 결과여야 한다. 에너지는 공유 기록의 `reaction`/확정 감정 분포에서 파생한 값이어야 하며, **산출식이 확정되지 않았으므로 확정 전까지 수치(%) 대신 정성 라벨을 쓰거나 표시를 보류한다(9절 승인 항목).**
- **정상**: 한 줄 요약 탭 → 근거 `recordId`를 담아 `/record`로 이동 → 해당 기록 하이라이트.
- **로딩**: 3개 카드 스켈레톤.
- **빈 상태**: 오늘 공유 기록이 2건 미만이면 요약 카드를 만들지 않고 "아직 오늘 기록이 도착하지 않았어요"만 보여준다(`generateDailySummary`의 기존 규칙과 동일하게 맞춘다). 이때 배려 힌트도 생성하지 않는다.
- **오류**: 요약 생성 실패 시 원문 기록 목록으로 대체하지 말고 "요약을 만들지 못했어요 · 기록 보러 가기" 링크만 제공한다.
- **권한 없음**: 커플 미연결 또는 연결 해제 상태면 전 카드 숨김 + 연결 안내.
- **오프라인**: 마지막 계산 결과와 기준 시각을 함께 표기한다.
- **비노출 규칙**: private 기록은 요약·에너지·힌트·키워드 어느 입력에도 들어가지 않는다. 부대 위치·군번·작전 정보는 어떤 카드에도 넣지 않는다.

### 3.3 기록 (`/record`, `pages/RecordPage.tsx`)
- **목적**: 월간 캘린더로 날짜를 고르고 그날의 타임라인을 본다.
- **구성**: 상단 제목 + 캘린더 토글, 접이식 월간 그리드, 날짜별 타임라인, 미디어 필터(전체/사진/음성/영상/텍스트), 기록 상세 시트, 작성 진입.
- **정상**: 내 기록 전체 + 상대의 공유 기록만 표시. 하이라이트 대상이 있으면 해당 카드로 스크롤 후 강조를 자동 해제한다.
- **로딩**: 캘린더 골격 유지 + 타임라인만 스켈레톤.
- **빈 상태**: 선택 날짜에 기록이 없으면 "이 날의 기록이 없어요" + 오늘이면 작성 CTA.
- **오류**: 저장 실패 시 작성 내용을 유지한 채 재시도 버튼을 제공한다. 실패한 기록을 성공한 것처럼 타임라인에 남기지 않는다.
- **권한 없음**: 미연결 상태에서는 내 기록만 보이며 공유 범위 토글은 "연결 후 사용" 안내와 함께 비활성화한다.
- **오프라인**: 캐시 기록 열람 가능, 첨부 미디어는 Signed URL 만료로 실패할 수 있으므로 플레이스홀더를 노출한다.
- **비노출 규칙(엄격)**: 상대에게는 private 기록의 **존재 자체**가 드러나면 안 된다. 캘린더의 점, 날짜별 개수 배지, 미디어 카운트(사진/음성/영상/텍스트), 첨부 존재 표시 모두 **상대 화면에서는 shared 기록만으로 계산**해야 한다. 현재 코드의 카운트 계산은 이 관점에서 재검증이 필요하다(6절 "최소 수정" 항목).
- **접근성**: 캘린더 셀은 날짜와 상태를 함께 읽어주는 레이블, 타임라인 카드 최소 44~48px 터치 타깃, 강조 색상 외 텍스트 단서 병행.

### 3.4 우리 (`/us`, `pages/UsPage.tsx`)
- **목적**: 진입 즉시 커플 공유 캘린더를 보고, D+N·기념일·공유 일정·면회/휴가/외박·여행·체크리스트로 이동한다.
- **구성(확정 순서)**: ① 월간 공유 캘린더 전면 → ② D+N/다음 기념일 → ③ 공유 일정 및 면회·휴가·외박 → ④ 여행과 체크리스트 진입.
- **정상**: 캘린더 날짜 탭 시 하단에 그날의 공유 일정·여행 구간이 펼쳐진다. 일정 종류별로 점 색을 구분한다(기념일 / 면회·휴가·외박 / 일반 공유 일정 / 여행).
- **로딩**: 캘린더 그리드 유지 + 점과 하단 목록만 스켈레톤.
- **빈 상태**: 일정이 없으면 "함께할 날을 하나 추가해볼까요" 단일 CTA.
- **오류**: 캘린더는 유지하고 목록 영역만 재시도 UI.
- **권한 없음**: 미연결 시 캘린더는 개인 일정만, 공유 영역은 초대 CTA로 대체한다.
- **오프라인**: 캐시 표시 + 쓰기 차단 안내.
- **비노출 규칙**: 개인(비공개) 일정은 상대의 우리 탭에 **점조차 표시되지 않는다.** 생리주기는 우리 탭에 절대 등장하지 않는다.

### 3.5 여행 (`/trips`, `/trips/:id`)
- **범위 고정**: 제목, 기간, 장소 텍스트, 날짜별 항목, 공동 체크리스트, 메모까지만. **지도·장소 검색·예약·결제·경로 안내는 구현하지 않는다.**
- **주의**: `trips` 테이블에 장소/destination 컬럼이 없다. 장소 텍스트를 저장하려면 005 마이그레이션이 필요하다(9절 승인 항목).
- **상태**: 로딩=항목 스켈레톤, 빈=날짜별 "항목 추가" 인라인 CTA, 오류=항목 단위 재시도, 오프라인=읽기 전용.

### 3.6 마이 (`/my`, `pages/MyPage.tsx`)

## 4. 핵심 데이터 흐름

### 4.1 하루 기록 작성
입력(본문, 시각, 반응, 첨부, 공유 범위) → 클라이언트 검증(본문 또는 첨부 최소 1개, 날짜 형식, 첨부 용량·MIME) → 첨부를 private Storage에 업로드 → `daily_records` insert(작성자 id, 활성 couple_id, `is_private`) → 성공 시 로컬 상태 반영 및 Realtime으로 상대 갱신 → 실패 시 낙관적 반영을 되돌리고 입력값을 보존한 재시도 UI.
**권한 경계**: insert 시 `user_id`가 본인이고 `couple_id`가 본인이 속한 활성 커플인지 **서버 측(WITH CHECK)에서** 검증돼야 한다. 현재는 `user_id`만 검증하므로 005에서 보완이 필요하다.

### 4.2 감정 흐름 확정
기록 본문 → `lib/aiEmotion.ts` → `emotionRuleEngine.recommendEmotionFlow`(로컬 규칙, 최대 3개) → 사용자에게 후보 제시 → 사용자가 고른 항목만 `source: 'user_confirmed'`, `visibility`를 지정해 `daily_records.emotion_flow`에 저장.
**권한 경계**: `visibility === 'shared'`이고 소속 기록이 `is_private = false`인 감정만 상대에게 보인다. 두 조건 중 하나라도 어긋나면 상대 쪽 계산 입력에서 제외한다. 미확정 후보는 저장·전송하지 않는다.

### 4.3 군화 홈 브리핑
오늘 날짜 + 활성 couple_id로 상대의 **shared 기록만** 조회 → `generateDailySummary`로 요약 항목과 근거 `recordIds` 생성 → `generateEmotionFlowBriefing`으로 감정 흐름 문장 생성 → 에너지/한 줄 요약/배려 힌트 카드 렌더 → 요약 탭 시 `setHighlightedRecordId(recordId)` 후 `/record` 이동 → RecordPage가 해당 날짜로 이동·스크롤·강조 후 자동 해제.
**실패 처리**: 조회 실패는 재시도, 요약 생성 실패는 카드 생략(원문 대체 금지).
**권한 경계**: 조회 자체가 RLS로 private을 배제해야 하며, 클라이언트에서 걸러내는 방식에 의존하지 않는다.

### 4.4 커플 연결
발급자: `create_invitation`(또는 `create_couple_and_invitation`) 호출 → 평문 코드는 화면 1회 노출, DB에는 해시만 저장, 24시간 만료.
수신자: 코드 입력 → `consume_invitation` → 활성 커플 1개 제약 검증 → `couple_members` 양측 active.
**현재 결함**: `consume_invitation`이 역할을 `'soldier'`로 하드코딩한다. 수신자가 곰신인 경우 역할이 뒤집힌다 → 005에서 역할 인자화 또는 연결 후 역할 확정 단계 필요.

### 4.5 커플 연결 해제
사용자 확인 → `disconnect_couple` RPC → **양쪽 `couple_members` 행을 함께 `disconnected`로 전이** → 공유 데이터 접근 즉시 차단 → Realtime 채널 해제 → 로컬 캐시에서 상대 관련 데이터 제거.
**현재 결함 2건**: 클라이언트가 RPC를 호출하지 않는다. RPC 자체도 본인 행만 갱신한다. 둘 다 수정 대상이다.

### 4.6 미디어
업로드 → private 버킷 `couple-media`, 경로 `커플id/uuid.확장자` → 조회 시 Signed URL(현재 3600초).
**문제**: private 기록의 첨부도 커플 단위 경로에 저장되므로 경로 규칙만으로는 작성자 전용 보호가 되지 않는다. 또한 1시간 만료는 "짧은 만료" 원칙과 어긋난다. **경로 규칙과 만료 시간은 005 + Storage 정책에서 함께 다뤄야 한다.**

### 4.7 생리주기
마이 탭에서만 입력 → `cycle_entries` / `cycle_settings`에 본인 id로 저장 → 본인만 조회. 어떤 브리핑·감정·알림·Realtime·분석에도 포함하지 않는다. 이 흐름은 현재 구현이 원칙에 부합하므로 변경하지 않는다.

## 5. DB · RLS · RPC · Storage · Realtime

### 5.1 현재 스키마 (001~004에서 확인)
`profiles`(display_name, role, avatar_path, military_info JSONB, onboarding_completed_at), `couples`(anniversary_date), `couple_members`(couple_id, user_id, role, status: pending/active/disconnected — 사용자당 활성 커플 1개, 커플당 조합 1행 유니크 인덱스), `invitation_codes`(SHA-256 code_hash, 24시간 TTL, used/used_by/used_at), `daily_records`(user_id, couple_id, record_date, record_time, log_text, reaction, attachments JSONB, is_private, emotion_flow JSONB, emotion_updated_at), `briefings`(couple_id, recipient_id, briefing_date, summary_items — UNIQUE), `events`(title, event_type, start_date, end_date, visibility, is_private), `trips`(title, start_date, end_date, status), `trip_items`(item_date, title, category, memo, url, sort_order), `trip_checklists`(item_name, completed), `contact_preferences`(평일/주말 시작·종료), `cycle_settings`, `cycle_entries`.

RPC(모두 SECURITY DEFINER, `search_path=public`, PUBLIC 권한 회수 후 authenticated에만 부여): `get_my_active_couple_id`, `get_partner_profile`, `create_invitation`, `consume_invitation`, `disconnect_couple`, `create_couple_and_invitation`.

### 5.2 확인된 보안 결함 (모두 005 이후에서만 수정)
1. **`couple_members` SELECT 정책이 `USING (true)`** — 002에서 재귀 회피를 위해 완화한 결과로, 인증된 모든 사용자가 전체 커플 멤버십 행을 읽을 수 있다. **가장 심각한 항목.** SECURITY DEFINER 헬퍼 함수를 이용해 재귀 없이 본인 소속 행만 보이도록 되돌려야 한다.
2. **`couples` INSERT가 `WITH CHECK (true)`** — 임의 커플 행 생성이 가능하다.
3. **`daily_records` INSERT WITH CHECK가 `user_id`만 검증** — 타 커플 `couple_id`로 기록을 주입할 수 있다.
4. **`events` RLS가 커플 전체 FOR ALL** — `visibility`/`is_private` 컬럼이 있어도 개인 일정이 상대에게 노출된다. 두 컬럼이 공존하는 것도 모호하므로 하나를 정본으로 삼아야 한다(9절).
5. **`consume_invitation`의 역할 하드코딩(`'soldier'`)**.
6. **`disconnect_couple`의 단측 갱신** — 상대가 `active`로 남아 비대칭 접근이 가능하다.
7. **Storage 버킷/정책 마이그레이션이 저장소에 없다** — 코드가 `couple-media` 버킷을 사용하지만 버킷 생성과 접근 정책이 코드로 관리되지 않는다. 실제 프로젝트 콘솔 설정은 **확인 필요**.
8. **`002`가 두 개다** — `002_fix_rls_and_rpc.sql`과 `002_fix_rls_recursion.sql`이 공존해 적용 순서와 최종 유효 정책이 모호하다. **어떤 정책이 실제 운영 DB에 적용돼 있는지 콘솔 대조가 반드시 선행되어야 한다(확인 필요).**
9. **`notification_preferences` 테이블이 없다** — 계획서상 엔터티지만 미구현이다. 현재 알림 UI가 스텁인 것과 일치한다.

### 5.3 Realtime
`store.tsx`가 `daily_records`, `events`, `trips` 세 채널을 `couple_id` 필터로 구독하고, 변경 payload를 신뢰하지 않고 매번 `fetchFullStateFromDB`로 재조회한다. 재조회는 RLS를 거치므로 결과는 안전하지만, **postgres_changes payload 자체가 RLS를 준수하도록 Realtime 권한이 설정돼 있는지는 저장소만으로 확인할 수 없다(확인 필요).** payload에 상대의 private 기록 본문이 실려오면 원칙 위반이므로 콘솔에서 반드시 검증한다. `cycle_*` 테이블은 구독 대상이 아니며 앞으로도 추가하지 않는다.

### 5.4 클라이언트 저장소
`gomsinlog.state.v1` 키에 private 기록 본문 포함 전체 상태를 평문 저장한다. 최소한 (a) 저장 대상에서 private 본문·첨부 URL 제외, (b) 로그아웃·연결 해제 시 즉시 키 삭제를 적용한다.

## 7. 단계별 구현 순서

### 0단계 — 운영 DB 실제 상태 대조 (선행 필수)
- **목표**: 002 중복으로 인해 실제 적용된 RLS·RPC·Storage 정책이 무엇인지 확정한다.
- **선행 조건**: 없음. 다른 모든 단계보다 먼저 수행한다.
- **대상**: Supabase 콘솔의 정책·함수·버킷 목록, 저장소 migration 파일.
- **최소 변경**: 코드 변경 없음. 대조 결과를 문서화만 한다.
- **수용 테스트**: 테이블별 유효 정책 목록과 저장소 마이그레이션의 차이가 표로 정리된다.
- **중단 조건**: 콘솔 접근이 불가하면 5·6단계(DB 변경)를 시작하지 않는다.

### 1단계 — 군화 홈을 실데이터로 전환
- **목표**: 목 데이터 제거, `briefing.ts` 결과로 3카드 구성.
- **선행 조건**: 없음(프론트 단독).
- **대상**: `features/home/SoldierDashboard.tsx`, 필요 시 요약 조회 헬퍼.
- **최소 변경**: 하드코딩 값 제거 → 오늘 shared 기록 조회 → `generateDailySummary`/`generateEmotionFlowBriefing` 호출 → 빈/오류 상태 처리. 에너지 수치는 산출식 승인 전까지 표시 보류.
- **수용 테스트**: 공유 기록 0~1건이면 요약 카드 미생성. private 기록만 있으면 아무것도 노출되지 않음. 카드 3개 초과 목록 없음.
- **롤백**: 기존 컴포넌트를 커밋 단위로 되돌린다.

### 2단계 — 요약 → 근거 기록 연결
- **목표**: 한 줄 요약 탭 시 근거 기록으로 이동·하이라이트.
- **선행 조건**: 1단계.
- **대상**: `SoldierDashboard.tsx`(전달), `store.tsx`의 `setHighlightedRecordId`(기존), `RecordPage.tsx`(수신, 기존).
- **최소 변경**: 요약 항목의 첫 `recordId`를 하이라이트로 설정하고 해당 날짜로 이동.
- **수용 테스트**: 이동 후 해당 카드가 화면 중앙에 스크롤·강조되고 일정 시간 뒤 강조가 해제된다. private 기록 id는 절대 전달되지 않는다.
- **롤백**: 이동만 하는 기존 동작으로 복귀.

### 3단계 — 화면 정리와 라우팅 정합
- **목표**: 설정 진입 경로 통일, 레거시 라우트 제거, 마이/설정 중복 제거.
- **선행 조건**: 1~2단계.
- **대상**: `App.tsx`, `WidgetDashboard.tsx`, `MyPage.tsx`, `SettingsPage.tsx`.
- **최소 변경**: `/schedule` 라우트 제거, 설정 버튼 `/settings`로 교정, 알림·PWA·연결 해제 항목 설정으로 단일화.
- **수용 테스트**: 4탭 + `/settings` + 여행 라우트 외 진입 경로가 없고, 동일 기능이 두 화면에 중복되지 않는다.
- **롤백**: 라우트 복원(파일 삭제는 하지 않았으므로 즉시 가능).

### 4단계 — 우리 탭 캘린더 고도화
- **목표**: 월간 공유 캘린더 중심 정보구조 완성.
- **선행 조건**: 3단계. 개인 일정 정책(9절)의 승인.
- **대상**: `UsPage.tsx`, `lib/events.ts`.
- **최소 변경**: 일정 종류별 점 구분, 날짜 선택 시 하단 상세, 다음 기념일·면회/휴가/외박 요약, 여행·체크리스트 진입.
- **수용 테스트**: 상대 화면에서 개인 일정은 점과 목록 모두 나타나지 않는다. 생리주기는 어떤 형태로도 나타나지 않는다.
- **중단 조건**: `events` 정본 컬럼이 결정되지 않았으면 개인/공유 구분 구현을 중단한다.

### 5단계 — RLS 재강화 (005)
- **목표**: `couple_members` 노출, `couples` 무제한 INSERT, `daily_records` couple 미검증, `events` 개인 일정 노출을 함께 해소한다.
- **선행 조건**: 0단계 완료.
- **대상**: 신규 `005` 마이그레이션.
- **최소 변경**: SECURITY DEFINER 헬퍼로 재귀 없이 소속 검증, 각 테이블 정책 교체. 001~004는 손대지 않는다.
- **수용 테스트**: 제3자 계정으로 타 커플의 멤버십·기록·일정 조회가 모두 0행. 본인 커플 정상 동작. 재귀 오류 미발생.
- **롤백**: 005를 되돌리는 역방향 마이그레이션을 사전에 준비한 뒤에만 적용한다. 스테이징 선적용 필수.

### 6단계 — 연결·해제 정합성 (006)
- **목표**: 역할 하드코딩 제거, 양측 동시 해제.
- **선행 조건**: 5단계.
- **대상**: 신규 `006` 마이그레이션, `store.tsx`의 `disconnect()`.
- **최소 변경**: `consume_invitation` 역할 인자화(또는 연결 후 역할 확정 단계), `disconnect_couple` 양측 전이, 클라이언트가 RPC 호출 후 결과에 따라 로컬 상태 갱신.
- **수용 테스트**: 곰신이 코드를 입력해도 역할이 곰신으로 유지된다. 한쪽이 해제하면 상대도 즉시 공유 데이터에 접근할 수 없다.
- **롤백**: 이전 함수 정의로 복원하는 마이그레이션 준비.

### 7단계 — 미디어·로컬 캐시 보안
- **목표**: private 첨부 보호와 Signed URL 만료 단축, 로컬 평문 저장 축소.
- **선행 조건**: 5단계.
- **대상**: Storage 정책(신규 마이그레이션), `lib/records.ts`, `store.tsx`.
- **최소 변경**: private 기록 첨부는 작성자 전용 경로·정책, 만료 시간 단축, localStorage 저장 대상에서 private 본문·첨부 URL 제외, 로그아웃·연결 해제 시 캐시 삭제.
- **수용 테스트**: 상대 계정으로 private 첨부 Signed URL 발급이 실패한다. 로그아웃 후 브라우저 저장소에 기록 본문이 남지 않는다.
- **중단 조건**: 기존 업로드 자산의 경로 마이그레이션 계획이 없으면 경로 변경을 보류하고 정책 강화만 먼저 적용한다.

### 8단계 — 위젯·설정 스텁 정리
- **목표**: 동작하지 않는 UI를 없애거나 실데이터에 연결.
- **선행 조건**: 1~7단계.
- **대상**: `lib/widgets.tsx`, `SettingsPage.tsx`, `MyPage.tsx`.
- **최소 변경**: 하드코딩 위젯 비활성화, 실데이터 연결 가능한 위젯만 노출, 스텁 항목 "준비 중" 명시.
- **수용 테스트**: 사용자가 조작 가능한 항목은 모두 실제 결과를 만든다.
- **롤백**: 레지스트리 항목 복원.

### 9단계 — 레거시 파일 정리
- **목표**: 중복 화면 제거.
- **선행 조건**: 3단계 이후 참조 0건 확인.
- **대상**: `GomshinHome.tsx`, `SoldierHome.tsx`, `SchedulePage.tsx`, `ServicePage.tsx`.
- **수용 테스트**: 빌드·테스트 통과, 모든 라우트 정상 진입.
- **중단 조건**: 참조가 하나라도 남아 있으면 삭제하지 않는다.

## 8. A/B/C 권한 매트릭스

A = 작성자 본인, B = 연결된 상대(활성 커플), C = 제3자(다른 사용자·비로그인)

| 대상 | A (작성자) | B (연결된 상대) | C (제3자) |
|---|---|---|---|
| 공유(shared) 기록 본문 | 읽기·쓰기·수정·삭제 | 읽기만 | 접근 불가 |
| 비공개(private) 기록 본문 | 읽기·쓰기·수정·삭제 | **접근 불가 · 존재 여부(날짜·개수·점·첨부 표시)까지 비노출** | 접근 불가 |
| 공유 기록 첨부 미디어 | 읽기·업로드·삭제 | 짧은 만료 Signed URL로 읽기만 | 접근 불가 |
| 비공개 기록 첨부 미디어 | 읽기·업로드·삭제 | **Signed URL 발급 자체가 거부되어야 함** | 접근 불가 |
| 확정 감정(shared) | 읽기·수정 | 읽기만 | 접근 불가 |
| 미확정 감정 후보 | 로컬에서만 확인 | 접근 불가 | 접근 불가 |
| 공유 일정 (기념일·면회·휴가·외박·여행 일정) | 읽기·쓰기·수정·삭제 | 읽기·쓰기(공동 편집 범위는 9절 승인 필요) | 접근 불가 |
| 개인(비공개) 일정 | 읽기·쓰기·수정·삭제 | **접근 불가 · 캘린더 점도 비노출** | 접근 불가 |
| 여행(제목·기간·장소 텍스트·항목·메모) | 읽기·쓰기 | 읽기·쓰기 | 접근 불가 |
| 여행 공동 체크리스트 | 읽기·쓰기·토글 | 읽기·쓰기·토글 | 접근 불가 |
| 개인 체크리스트(마이) | 읽기·쓰기 | 접근 불가 | 접근 불가 |
| 생리주기(설정·기록) | 읽기·쓰기 | **접근 불가 · 존재 여부 비노출 · 브리핑/감정/알림/Realtime/분석 전면 제외** | 접근 불가 |
| 군화 개인 정보(전역 D-Day·연락 가능 시간·휴가) | 읽기·쓰기 | 본인이 공유하기로 한 항목만 읽기 | 접근 불가 |
| 부대 위치·군번·작전 상세·실시간 위치 | **저장·입력 자체를 하지 않음** | 접근 불가 | 접근 불가 |
| 커플 멤버십 행(couple_members) | 본인 행 읽기 | 같은 커플 행 읽기 | **접근 불가 (현재 결함: 전체 노출 → 005에서 수정)** |
| 초대 코드 | 발급 직후 1회 노출(평문), DB는 해시만 | 입력·소비만 가능 | 접근 불가 |
| 연결 해제 후 기존 공유 데이터 | 본인 데이터는 계속 읽기 | **즉시 접근 차단(과거 공유 기록 포함)** | 접근 불가 |
| Realtime 이벤트 | 본인 변경 수신 | shared 데이터 변경만 수신, private 본문 payload 수신 금지 | 구독 불가 |
| Signed URL 재사용 | 본인 발급분 사용 | 만료 전 shared 자산만, 연결 해제 시 재발급 불가 | 사용 불가 |

## 9. 구현 전 사용자 승인 필요 사항

각 항목은 **기본 권장안**을 함께 제시했다. 사용자가 별도 지시를 하지 않으면 권장안대로 진행하되, 승인 없이 진행하면 안 되는 항목은 그렇게 표시했다.

1. **`002` 중복 마이그레이션 처리 방식** — 권장: 두 파일 모두 보존하고, 실제 운영 DB의 유효 정책을 기준으로 005에서 최종 상태를 명시적으로 재선언한다. 영향: 마이그레이션 이력은 지저분해지지만 운영 중단 위험이 가장 낮다. **DB 접근이 필요하므로 승인 필수.**
2. **군화 홈 "에너지" 산출 방식** — 권장: 백분율 수치 대신 공유 기록의 반응·확정 감정 분포에 기반한 3단계 정성 라벨(예: 여유 / 보통 / 지침)로 시작한다. 영향: 정확도 오해를 줄이지만 시각적 임팩트는 감소한다. 승인 전에는 카드에 수치를 표시하지 않는다.
3. **`events`의 정본 컬럼 결정** — 권장: `visibility`를 정본으로 삼고 `is_private`는 읽기 전용 파생으로 취급한 뒤 이후 단계에서 폐기한다. 영향: 기존 데이터의 두 컬럼 값이 불일치하면 일회성 정합 작업이 필요하다.
4. **공유 일정의 상대 편집 권한** — 권장: 상대가 만든 공유 일정을 서로 수정·삭제할 수 있게 한다(커플 앱 특성). 영향: 편의성은 높지만 실수 삭제 위험이 있어 삭제에 확인 모달이 필요하다. 반대로 "작성자만 수정"으로 좁히면 갈등 소지는 줄지만 협업성이 떨어진다.
5. **연결 해제 후 과거 공유 기록 처리** — 권장: 상대 접근을 즉시 차단하되 데이터는 각자 소유분으로 보존한다(삭제하지 않음). 영향: 재연결 시 복구가 쉽다. "해제 시 상대 기록 즉시 삭제"를 원하면 별도 승인이 필요하다.
6. **Signed URL 만료 시간** — 권장: 현재 3600초를 300초로 단축하고 만료 시 자동 재발급한다. 영향: 요청 수가 늘지만 유출 창이 크게 줄어든다.
7. **첨부 저장 경로 변경 여부** — 권장: 신규 업로드부터 private/shared 경로를 분리하고 기존 자산은 정책으로만 보호한다(대량 이동 없음). 영향: 과도기에는 경로 규칙이 두 가지가 된다.
8. **`briefings` 테이블 사용 여부** — 권장: 현재는 사용하지 않고 클라이언트 계산만 유지한다. 영향: 이력 보존과 재계산 방지가 없으므로 훗날 도입 시 재작업이 생길 수 있다.
9. **위젯 "오늘의 식단" 존치 여부** — 권장: 부대 정보 성격이 있어 **제거**한다. 영향: 위젯 선택지가 줄지만 원칙 위반 소지를 없앤다.
10. **여행 `장소 텍스트` 컬럼 추가** — 권장: 005에 텍스트 컬럼 하나만 추가한다. 영향: DB 변경이 필요하므로 승인 필수. 승인 전에는 여행 메모 필드로 임시 대체한다.
11. **`notification_preferences` 및 알림 기능 착수 시점** — 권장: 위 1~7단계 완료 후로 미룬다. 영향: 알림 관련 설정 UI는 그때까지 "준비 중"으로 표시된다.
12. **레거시 파일 삭제 승인** — 권장: 라우트 분리 후 참조 0건이 확인되면 삭제한다. 영향: 되돌리려면 커밋 복원이 필요하다.
13. **localStorage 저장 범위 축소** — 권장: private 기록 본문과 첨부 URL을 저장 대상에서 제외하고, 로그아웃·연결 해제 시 키를 삭제한다. 영향: 오프라인에서 본인 비공개 기록을 볼 수 없게 되므로 UX 트레이드오프가 있다.
14. **데모 폴백 모드의 운영 노출 여부** — 권장: 운영 빌드에서 데모 경로를 완전히 비활성화한다. 영향: 데모 시연 흐름이 필요하면 별도 플래그가 필요하다. 현재 운영 빌드 동작은 **확인 필요.**

---

### 이 문서에서 "확인 필요"로 남은 항목 요약
운영 DB에 실제 적용된 RLS 정책(002 중복), Realtime payload의 RLS 준수 여부, Storage 버킷·정책의 현재 설정, `events` 두 컬럼의 실데이터 정합성, `briefings` 테이블의 실사용 여부, 레거시 4개 파일의 참조 유무, 데모 폴백의 운영 빌드 동작. **이 7가지는 저장소 파일만으로 판단할 수 없으므로 추정 구현을 금지한다.**
